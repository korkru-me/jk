# งานกลุ่มและงานเดี่ยวในห้องเรียน — ผ่าน Staging; ยังไม่ปล่อย Production

## ขอบเขต

เข้าจากห้องวิชา → **งานกลุ่มและงานเดี่ยว** ครูต้องเลือกรูปแบบ หากเป็นงานกลุ่มกำหนดขั้นต่ำ–สูงสุดและนับรวมผู้ส่ง นักเรียนค้นชื่อ/เลขที่จาก roster ของห้องเดิม แนบ PDF รูป และเอกสารได้ หรือส่งคำตอบที่เขียนโดยไม่มีไฟล์ก็ได้ แผงตรวจแสดงผลงานหนึ่งชุดและคะแนนหนึ่งช่อง นักเรียนที่มีชื่อในงานเปิดผลงานและอ่านผลประกาศชุดเดียวกัน

งานกลุ่มไม่เปลี่ยนชนิดแบบฝึกหัด/ข้อสอบเดิม กลุ่มย่อยประจำห้อง หรือการนำเข้าจาก Word ผลประกาศบันทึกในฐานข้อมูลและอ่านได้ในหน้างานนี้; ยังไม่รวมเข้าตารางคะแนนแบบฝึกหัดเดิมหรือการส่งออกเดิม ครูตรวจใหม่ทั้งกลุ่มได้ ไม่มีคะแนนรายคน กำหนดส่งเป็นข้อมูลและป้ายส่งช้า ไม่ใช่เวลาปิดรับ ไม่มีการซิงก์สมาชิกทั้งกลุ่มหลังส่งในรุ่นนี้

## สิทธิ์และข้อมูล

Migration `20261115142622_classroom_group_work.sql` แยกตารางออกจาก schema ที่ Data API เปิด ฟังก์ชันสาธารณะเป็น invoker เรียก implementation ที่ตรวจ `auth.uid()` และสิทธิ์ห้องทุกครั้ง ครูเจ้าของ/ผู้ช่วยที่จัดการได้เท่านั้นที่สร้างและให้คะแนน นักเรียนที่ active ในห้องจึงเลือกได้ API ให้สถานะและคะแนนฉบับประกาศโดยไม่ให้ร่าง แถวสมาชิกที่ unique ต่อหนึ่งงานและการจอง transaction ระดับงานกันการส่งซ้อน รูปแบบการเพิ่มชิ้นงานและการแก้คะแนนรองรับ receipt/revision เพื่อตรวจข้อผิดพลาดระหว่างการส่งซ้ำ

Bucket `classroom-group-work` เป็น private อ่านด้วย session และนโยบายตามผลงาน เก็บชื่อจริงของไฟล์เป็นข้อมูลแสดง ส่วน object path เป็น UUID ของงาน ผู้ส่ง และไฟล์ ตรวจว่ามี object และผู้ส่งเป็นเจ้าของก่อนบันทึก รองรับ 10 ไฟล์ต่อชิ้น สูงสุด 10 MB ต่อไฟล์ จองได้ไม่เกิน 20 object ต่อผู้ส่งต่องานเผื่อการลองใหม่ ไฟล์ที่ยังไม่ถูกอ้างอิงยังต้องมีแผนการเก็บกวาดก่อนปล่อยกว้าง ห้ามใช้ deletion ของ Storage ผ่าน SQL แทนการลบ blob ผ่าน Storage API

## สิ่งที่กั้น Production

## บันทึกเกตเดิมก่อนทดสอบและขั้นปล่อยถัดไป

- ตรงกันทั้ง 166 migration ระหว่าง `origin/staging` และฐาน Korkru Staging ก่อนปรับ ผ่าน Supabase MCP แบบอ่านอย่างเดียว CLI ที่เครื่องนี้ยังไม่มี Management access token
- TypeScript, token lint, Webpack production build และ Vitest (348 ชุด / 4,906 กรณี) ผ่าน; รวม PGlite ใช้ SQL migration จริง 4 กรณี (สิทธิ์/ห้อง, RLS ไฟล์, งานร่วมหนึ่งชิ้น, ร่างและคะแนนเดียว)
- ยังไม่มีการใช้ migration นี้บน hosted Staging หรือ Production และยังไม่มีผลรับรอง hosted Auth, Storage หรือ browser UAT สำหรับผู้สมัครนี้

1. เชื่อม CLI ด้วยสิทธิ์ Staging ที่พอสำหรับ migration และบัญชีสมมติ ใช้ `supabase migration list` เจาะจง project ref ตรวจอีกครั้ง ใช้เฉพาะ migration ที่คอมมิตด้วยเลขเดิม ห้ามใช้การซ่อมประวัติแบบย้อนเวอร์ชันหรือดึง environment ทั้งชุด
2. ติดตั้ง migration ที่อนุมัติบน Staging และยืนยันว่า version เดียวกันปรากฏในประวัติ แล้วรวม candidate ผ่าน `staging` และตรวจ Vercel READY, commit และ alias `staging.korkru.com`
3. เรียก `scripts/verify-group-work-staging.mjs --help` เตรียม environment เฉพาะ two keys ของ Staging ในไฟล์ชั่วคราว 0600 หรือ process env; ไม่ดึงหรือใช้คีย์ Production สคริปต์จะสร้างและลบเฉพาะข้อมูลรอบนั้น ตรวจการกำหนดกลุ่ม, Storage, การปฏิเสธคนนอกห้อง/ชื่อซ้ำ, ซ่อนร่าง และคนละบัญชีได้คะแนน 18/20 จากผลงานเดียวกัน
4. ทดสอบ UI ด้วยบัญชีสมมติแยก browser sessions บนโดเมน Staging ที่มีป้าย: ครูสร้างกลุ่ม 3–5 คน → นักเรียนเลือกเพื่อนไม่ครบแล้วปุ่มถูกปิด → ส่งคำตอบเขียนกับ PDF/รูปแทน 4 คน → ครูเปิดไฟล์ บันทึกร่าง แล้วเผยแพร่ 18/20 → ตรวจบัญชีสมาชิกทั้งสี่และคนนอกกลุ่ม รวมมือถือ หลังทดสอบลบเฉพาะข้อมูลสมมติ
5. เมื่อผ่าน Hosted Staging จริงและพร้อมปล่อย ให้แยก candidate บน `master` เฉพาะฟีเจอร์นี้ (ห้ามรวม staging ทั้งสาขา) ตรวจ migration parity ของ Production ก่อนใช้เลขเดียวกัน ยืนยัน Vercel READY และ canonical domain จาก commit ที่ถูกต้อง smoke test อ่านอย่างเดียว และ sync ไฟล์ที่เกี่ยวข้องเข้า primary localhost:3000 โดยไม่แทนงานเดิมของผู้ใช้
