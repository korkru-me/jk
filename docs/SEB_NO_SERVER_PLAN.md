# SEB ไม่เพิ่ม SEB Server — แผนใหม่และจุดตัดสินใจเฟส 1

อัปเดต: 5 กันยายน 2026 · ตรวจฐานโค้ด `c9757c0`

## สถานะและอำนาจที่ได้รับ

ผู้ใช้ให้เริ่ม **เฟส 1 ของแผนใหม่ 8 เฟส**: ตรวจทางเลือก กำหนดข้อจำกัด และระบุสิ่งที่ต้องตัดสินใจก่อนทำระบบต่อ ไม่ใช่อนุมัติลดการตรวจ CK + BEK หรือเปิดบริการรหัสรายครูจริง

**ผลปัจจุบัน: ตรวจทางเทคนิคและจัดทำบันทึกแล้ว แต่ยังไม่ผ่านจุดตัดสินใจเฟส 1** รอคำตอบด้านพฤติกรรมการออก และยังไม่มีวิธีที่พิสูจน์แล้วสำหรับการเผยแพร่ config ใหม่แบบอัตโนมัติพร้อมรักษา CK + BEK ด้วยเว็บบน Vercel/Supabase เพียงอย่างเดียว

เอกสารนี้เป็นแผนปัจจุบันสำหรับงานรหัสรายครู แทนลำดับงานที่สมมติว่าจะต่อ SEB Server ใน `SEB_PHASE1.md`, `SEB_PHASE2.md` และ `SEB_PASSWORD_ROLLOUT.md` เอกสารเหล่านั้นยังเก็บไว้เป็นประวัติ/คู่มือของต้นแบบเดิม ไม่ลบโค้ดหรือแปลว่าผลทดสอบเดิมผ่านเฟสใหม่

รอบนี้แก้เอกสารเท่านั้น: ไม่เปิด native SEB, ไม่แก้ไฟล์ `.seb`, application runtime, env, migration, Supabase, Vercel หรือแพ็กเกจค่าใช้จ่าย

## เป้าหมายที่ผู้ใช้ระบุแล้ว

1. ครูตั้งและเปลี่ยนรหัสออกของตัวเองได้ ไม่ใช้รหัสฉุกเฉินกลางร่วมทุกครู
2. นักเรียนไม่ต้องใส่รหัสเปิด SEB เพิ่ม การล็อกอิน KorKru เป็นคนละส่วน; งานนี้ยังไม่เปลี่ยน access code ของข้อสอบเดิม
3. ครูกดอนุญาตให้นักเรียนออกเป็นรายคนจากหน้าคุมสอบ
4. นักเรียนส่งสำเร็จแล้วออกได้โดยไม่ใส่รหัสออก
5. ใช้ Vercel/Supabase ที่มีอยู่ ไม่เพิ่มระบบติดตาม/SEB Server ที่ต้องเช่าเพิ่ม ไม่ซื้อบริการโดยอนุมานจากคำว่าเริ่มเฟส
6. เป้าหมายธุรกิจคือบริการให้ครูทั่วประเทศ ไม่ใช่สัญญาว่าจะให้เจ้าของเว็บเตรียม Key ด้วยมือให้ทุกคนตลอดไป
7. ผู้ใช้เป็นผู้เปิดและทดสอบ SEB บนอุปกรณ์จริง Agent ไม่เปิดแทน และต้องเตรียมทางออกก่อนทุกครั้ง

### ขอบเขตแพลตฟอร์ม

เป้าหมายวางแผนคง Mac, iPad และ Windows ตามบริบทเดิม ไม่ลดเหลือ Mac/iPad โดยถือว่าผู้ใช้ยินยอมแล้ว รุ่น OS/SEB/build ที่จะรับรองต้องระบุจากเครื่องจริงในเฟส 2

- Mac และ iPad: ผู้ใช้มีเครื่องและเคยเปิดไฟล์เดิม แต่ยังไม่มีผลตรวจครบสำหรับ config แบบใหม่
- Windows: ยังไม่ยืนยันว่ามีเครื่อง/ผู้ช่วยทดสอบและ BEK สำหรับรุ่นที่จะใช้จริง จึงยังไม่ประกาศว่ารองรับ production จากการอ่าน source หรือผล Mac
- หากไม่มี Windows ในรอบทดลอง ให้บันทึกว่า pending; การเปิดขายเฉพาะ Mac/iPad ต้องให้ผู้ใช้เลือกขอบเขตนั้นก่อน
- Android monitored mode เดิมไม่ใช่ SEB และไม่ถูกนับเป็นแพลตฟอร์ม SEB ที่ผ่านการตรวจชุดนี้

## สิ่งที่พบในโค้ดปัจจุบัน

- `lib/seb.ts` อ่าน CK หนึ่งค่าและรายการ BEK จาก environment และ `verifySebRequestHashes()` บังคับทั้งสอง ไม่ได้มีทะเบียน config/Key รายครูหรือ revision แล้ว
- `lib/actions/seb.ts` และ session เดิมผูกการเข้าข้อสอบกับผู้ใช้/assignment ห้ามข้ามกลไกนี้เพื่อให้ไฟล์ใหม่เข้าได้
- `scripts/seb-phase1/config.mjs` สร้างเฉพาะ `pswd` ที่มี opening password; `quitURL` ของ fixture ว่าง ต้นแบบนี้ยังไม่รองรับข้อกำหนดเปิดโดยไม่ถามรหัสหรือออกผ่าน Quit URL
- หน้า `/assignments/[id]/seb-password` และ encrypted vault เป็น **ร่างที่ยังไม่เผยแพร่** ฟีเจอร์ปิดโดย default ไม่ใช่รหัสที่ native SEB ใช้แล้ว
- สถานะที่บันทึกไว้ของ migration `20260905072556_add_exam_seb_password_drafts.sql` คือยังไม่ apply live และ keyring ยังไม่ provision; เฟส 1 รอบนี้ไม่ได้ตรวจ migration ledger สดหรือเชื่อมบัญชี deployment ซ้ำ ต้องตรวจใหม่ก่อนเปลี่ยนฐาน
- `components/exam/exam-client.tsx` หลัง `submitSubmission()` สำเร็จไปหน้า `/submissions/[id]`; `document.exitFullscreen()` ที่พบเป็น DOM fullscreen ไม่ใช่คำสั่งปิด native SEB
- SEB Server lab เดิมมีเพียงเครื่องมือทดลอง/read-only probe ยังไม่ใช่ server ที่ติดตั้งหรือ runtime integration การเปลี่ยนแผนไม่ได้ลบ lab

## ข้อค้นพบที่ต้องใช้ตัดสินใจ

### 1. รหัสรายครูทำได้ แต่ยังมีภาระ BEK

ตาม [SEB integration specification](https://safeexambrowser.org/developer/seb-integration.html) BEK เปลี่ยนเมื่อ config หรือ native build เปลี่ยน วิธีมาตรฐานคือเปิดไฟล์สุดท้ายบนแต่ละ build ที่รองรับแล้วเก็บ Key โดยไม่บันทึกไฟล์ซ้ำ ส่วน [Config Key](https://safeexambrowser.org/developer/seb-config-key.html) คำนวณบนเว็บได้

**ภาระลงทะเบียนนับต่อ config revision ที่แตกต่าง × build ที่รองรับ ไม่จำเป็นต้องนับต่อข้อสอบหรือต่อนักเรียนเสมอไป** ไฟล์รายครูที่ใช้ Start URL เป็นหน้ารวมข้อสอบสามารถใช้ซ้ำหลายข้อสอบได้ ถ้าค่าภายในไม่เปลี่ยน เว็บยังต้องตรวจว่าครูเจ้าของ revision ตรงกับข้อสอบที่นักเรียนมีสิทธิ์เข้า

ทางเลือกที่มีหลักฐานรองรับคือให้ผู้ดูแลที่เชื่อถือได้เปิดไฟล์นั้นบนแอปจริงและลงทะเบียน BEK ก่อนเผยแพร่ ใช้ได้กับการทดลอง/บริการที่มีคนดูแล แต่ **ยังไม่ตอบโจทย์ครูเปลี่ยนรหัสแล้วเผยแพร่เองได้ทันทีโดยไม่มีคนเตรียม Key**

การใช้ไฟล์รายครูร่วมหลายข้อสอบก็มีข้อแลกเปลี่ยน: รหัสที่หลุดกระทบทุกข้อสอบที่ยังใช้ revision นั้น และ Quit URL ร่วมไม่ใช่สิทธิ์ออกเฉพาะ attempt จึงเป็นทางเลือกเสนอ ไม่ใช่สถาปัตยกรรมที่เลือกแล้ว

ยังไม่พบวิธี standalone ที่ตรวจยืนยันแล้วสำหรับสร้าง/ลงทะเบียน BEK ที่เชื่อถือได้อัตโนมัติด้วย Vercel/Supabase เท่านั้น ไม่ใช้ Key ที่นักเรียนอ้างมาเป็น trusted enrollment และไม่สร้าง BEK จาก CK เอง

CK-only ไม่เท่ากับ CK + BEK: ผู้ที่อ่าน config ได้คำนวณ CK เองได้ จึงห้ามเปลี่ยนไปใช้ CK-only เงียบ ๆ ตาม `SECURITY.md` การใช้ ASK/server-driven BEK ที่พบใน native source อยู่ใน server-session handshake ไม่ใช่ตัวเลือกแทนจาก JavaScript API ปกติ ดู [Windows server operation](https://github.com/SafeExamBrowser/seb-win-refactoring/blob/397f8e124387c54a9a770809003dd2e31946dcd5/SafeExamBrowser.Runtime/Operations/Session/ServerOperation.cs#L42)

ข้อสรุปคือ **ยังไม่ผ่านเงื่อนไขอัตโนมัติ** ไม่ใช่ข้อพิสูจน์ว่าการออกแบบแบบไม่ใช้ SEB Server ทุกวิธีเป็นไปไม่ได้ การทำ native workers หรือ protocol ใหม่ต้องประเมิน/ขอขอบเขตแยก ไม่อ้างว่าฟรีหรือทำสำเร็จแล้ว

### 2. ไม่ถามรหัสเปิด ไม่ได้แปลว่าไฟล์เป็นความลับ

เส้นทางอ่าน `plnd`/plain XML ใน [Apple config reader](https://github.com/SafeExamBrowser/seb-mac/blob/b56ae815a30f35cc26cc78a5c2597c9bdcfb1a53/Classes/ConfigFiles/SEBConfigFileManager.m#L222) รองรับข้อมูลไม่เข้ารหัส ขณะที่ `pswd` ขอ exam password จึงไม่ใช้การใส่รหัสว่างในต้นแบบเดิมเป็นหลักฐานว่าเปิดเงียบได้ทุก OS

ไฟล์ไม่เข้ารหัสทำให้ค่าตั้ง, Quit URL และ password hashes อ่านได้ รหัสจริงไม่ได้เก็บเป็น plaintext ใน field ของ quit password แต่ hash แบบ SHA-256 ไม่ป้องกันการเดารหัสอ่อนแบบ offline ดู [Apple password hashing](https://github.com/SafeExamBrowser/seb-mac/blob/88b7f8df3c96781197efe400b8a2cbd818524736/Classes/Cryptography/SEBKeychainManager.m#L209)

Admin password ป้องกันการแก้ผ่านหน้าตั้งค่า ไม่ได้ทำให้ไฟล์ plain อ่าน/แก้จากภายนอกไม่ได้ ยังต้องตรวจ config ที่เว็บ และใช้รหัสออกที่เดายาก ไม่มีค่าเริ่มต้นร่วมทุกครู รุ่นที่จะใช้จริงต้องผ่าน native test ก่อนรับรอง

### 3. ปุ่มอนุญาตบนเว็บไม่ใช่การอนุญาต native quit ทุกเส้นทาง

ตรวจ [Apple navigation handler](https://github.com/SafeExamBrowser/seb-mac/blob/b56ae815a30f35cc26cc78a5c2597c9bdcfb1a53/Classes/BrowserComponents/SEBAbstractWebView.m#L721) และ [Windows request handler](https://github.com/SafeExamBrowser/seb-win-refactoring/blob/20ca462306636421fe53a804cc8f55941f9d21b6/SafeExamBrowser.Browser/Handlers/RequestHandler.cs#L78): native จับ Quit URL และยกเลิก navigation ก่อน HTTP handler/URL filtering

ดังนั้น auth, ลายเซ็น, หมดอายุ หรือใช้ครั้งเดียว **ที่ HTTP endpoint ของ Quit URL สุดท้าย** ไม่สามารถบังคับการออกของ native ได้เอง วิธีเว็บปกติคือแยก endpoint ตรวจสิทธิ์/ผลส่งออกจาก Quit URL แล้วค่อยเสนอทางออกเมื่อผ่าน แต่ผู้ที่รู้ Quit URL และสามารถทำให้แอปนำทางไปถึงอาจออกก่อนเว็บอนุญาตได้ การสุ่ม URL ลดการเดา/แชร์ข้ามคน ไม่ทำให้ลับต่อผู้ถือไฟล์ที่อ่านได้

หากผู้ใช้ไม่ยอมรับข้อจำกัดนี้ ให้หยุดเลือก Quit URL เป็นวิธีออกตามเงื่อนไขดังกล่าว และกลับไปประเมินวิธีอื่น ไม่บันทึกว่าแค่เพิ่ม endpoint ก็แก้ข้อจำกัดแล้ว

แอปหน้าเว็บที่ออฟไลน์/ค้างรับคำสั่งครูไม่ได้ตามปกติ ต้องมีรหัสออกของครูเป็นทางสำรอง แต่ native ค้างบางแบบอาจยังต้องกู้คืนตามแนวทางระบบปฏิบัติการ การออกฉุกเฉินไม่รับประกันว่าคำตอบที่ยังไม่ sync จะถูกบันทึก

ไม่มี acknowledgement การปิดแอปที่ตรวจยืนยันได้จาก HTTP Quit URL ที่ถูกยกเลิก และ [standalone JavaScript API](https://safeexambrowser.org/developer/seb-config-key.html) ที่ตรวจไม่มี signed-exit/closed acknowledgement ห้ามตีความการ disconnect ว่าออกแน่นอน บน iPad เกณฑ์คือจบ exam session/ปลด assessment lockdown ไม่บังคับว่าต้องปิดตัวแอปกลับ Home

### 4. ค่าโฮสต์ของเว็บยังแยกจากค่า SEB Server

ไม่เพิ่ม SEB Server ไม่ใช่รับรองว่าระบบขายจริงใช้ฟรีตลอด: [Vercel commercial usage](https://vercel.com/docs/limits/fair-use-guidelines#commercial-usage) ต้อง Pro/Enterprise ไม่ใช่ Hobby ส่วน [Supabase Free](https://supabase.com/pricing) มีข้อจำกัดทรัพยากรและ Realtime ซึ่งนับการเชื่อมต่อของนักเรียนด้วย รอบนี้ไม่ได้ตรวจแพ็กเกจจริงหรือซื้อ/อัปเกรดบัญชี

## นโยบายเสนอ — ยังไม่ถือว่าผู้ใช้อนุมัติ

- เจ้าของข้อสอบตั้งรหัสและอนุญาตออกได้เฉพาะขอบเขตที่ตนมีสิทธิ์ ไม่ให้ครูร่วม/ผู้ดูแลข้าม owner policy ของรหัสโดยอัตโนมัติ
- ไฟล์ที่แจกแล้วเป็น immutable revision: รหัสใหม่ใช้กับการเริ่มใหม่ด้วยไฟล์ใหม่ ไม่เปลี่ยนรหัสในเครื่องที่กำลังสอบทันที
- ยกเลิก revision ได้ที่สิทธิ์เริ่มสอบบนเว็บ ไม่อ้างว่าลบไฟล์จากเครื่องนักเรียน เปลี่ยนรหัสเดิม หรือเพิกถอน Quit URL ใน session ที่กำลังเปิดอยู่ได้
- การออกหลังส่งรอผล commit สำเร็จก่อน การส่งล้มเหลว/คำขอซ้ำต้องไม่กลายเป็นส่งสำเร็จหรือทำคะแนนซ้ำ
- การออกกลางคันเก็บสถานะอนุญาตออก/ขัดจังหวะแยกจาก submitted ไม่ลบคำตอบ ไม่ให้คะแนนเสร็จเอง และไม่สร้าง attempt ใหม่เอง
- หากให้ทำต่อ: ครูต้องอนุญาตกลับเข้า ใช้ attempt เดิม คำตอบที่บันทึกแล้ว และ revision เดิม เวลายึด deadline ฝั่ง server เดิม ไม่หยุดหรือรีเซ็ตอัตโนมัติ; ถ้าหมดเวลาแล้วทำตามนโยบายหมดเวลา ไม่เปิดคำตอบที่ส่งแล้วกลับมาแก้เอง
- การออกปกติรอให้บันทึกคำตอบค้างสำเร็จก่อนเสนอปุ่ม หากบันทึกล้มเหลวแจ้ง retry และไม่สัญญาว่าข้อมูลครบ รหัสฉุกเฉินยังเป็นทางออกแต่มีความเสี่ยงข้อมูลที่ไม่ sync
- การอนุญาตผูก exact teacher/assignment/student/attempt/revision; snapshot/reconnect ต้องไม่ใช้สิทธิ์จากคนอื่นหรือรอบเก่า
- audit ใช้เฉพาะสถานะที่ยืนยันได้ เช่น อนุญาตแล้ว/ส่งคำตอบสำเร็จ/ส่งคำสั่งให้หน้าเว็บแล้ว ไม่เขียนว่า native SEB ปิดแน่นอน

### คำตอบที่รอจากผู้ใช้

- **D1 — ออกกลางคัน:** รอเลือกพักรอบเดิมและกลับมาทำต่อเมื่อครูอนุญาต (เวลาไม่หยุดอัตโนมัติ) หรือยุติรอบนั้นโดยไม่ถือว่าส่งแล้ว
- **D2 — ข้อจำกัด Quit URL:** รอเลือกยอมรับสำหรับรุ่นแรกที่มีครูคุมสอบ หรือยังไม่ยอมรับและประเมินทางอื่นก่อน
- **D3 — BEK:** ยังไม่อนุมัติให้เปลี่ยนเป้าหมายเต็มเป็นบริการ manual หรือให้ลดเหลือ CK-only การทดลองลงทะเบียนด้วยมือเป็นเพียงข้อเสนอจำกัดขอบเขต ไม่ใช่คำตอบสำหรับ automation การจะเดินหน้าต้นแบบแบบนั้นต้องแจ้งภาระและให้ผู้ใช้เลือกก่อน
- **D4 — Windows:** ก่อนรอบ native test ต้องทราบเครื่อง/ผู้ทดสอบและรุ่นที่มี; หากไม่มี ห้ามอนุมานว่าผ่านหรือถอดออกจากขอบเขตเปิดขายเอง

การแสดงตัวเลือกที่เลือกไว้ล่วงหน้าใน UI คำถามไม่ใช่การตอบหรืออนุมัติ เก็บ pending จนมีคำตอบจริง

## แผนใหม่ 8 เฟสและเกณฑ์ผ่าน

### N1 — ขอบเขตและการตัดสินใจ (ปัจจุบัน: รอข้อยุติ)

บันทึกเป้าหมาย หลักฐาน ช่องว่าง ข้อจำกัด ทางเลือก และขอบเขตที่ผู้ใช้ยอมรับ คุณช่วยตัดสินใจ D1–D3 และยืนยันเป้าหมายแพลตฟอร์ม ไม่ต้องแก้โค้ด

ผ่านเมื่อมีคำตอบและวิธีไปต่อที่ระบุสถานะได้ตรงจริง หากยังไม่มีวิธี automation ให้ระบุ **NO-GO สำหรับสร้างบริการอัตโนมัติเต็ม**; อาจเปิดทาง **GO เฉพาะต้นแบบที่ผู้ใช้ยอมรับขอบเขตแล้ว** ไม่เลื่อนข้อจำกัดไปซ่อนท้ายโครงการ

### N2 — ต้นแบบเล็กและพิสูจน์ native

เตรียมไฟล์ไม่มี opening password แยกรหัส A/B, Key ที่ถูกต้อง/ผิด, modified config และหน้าทดลองเข้า–ออกพร้อมข้อมูลสมมติ ผู้ใช้เปิด Mac/iPad/Windows ที่จะรองรับและช่วยเก็บผลตามขั้นตอน Agent ตรวจโค้ด/ค่าที่ต้องตรง ไม่รับ production secrets ในแชต ไม่เปิด native แทน

ผ่านเมื่อเปิดโดยไม่ถามรหัส, CK/BEK ถูกต้อง, รหัสออกแยกกัน, เส้นทางปกติส่งแล้ว/ครูอนุญาตออกทำงานและ iPad ปลด lockdown มีทางกู้คืน และมีวิธีจัดการ Key ที่ตรงกับขอบเขตที่อนุมัติ ถ้าผ่านแค่ manual pilot ให้บันทึก pilot ไม่ใช่ผ่าน nationwide automation **N3–N8 สำหรับเป้าหมายเต็มยังหยุดอยู่**

### N3 — ข้อมูล รหัส และ revision

ต่อยอด vault/owner checks หลัง gate ผ่าน ออกแบบ release/retire/retention และการเปลี่ยนรหัสโดยไม่ทำรอบสอบที่กำลังทำเสียหาย ตรวจ ledger/backup ก่อน migration คุณไม่ต้องช่วยเขียนโค้ด

ผ่านเมื่อสิทธิ์และ atomic version changes ทดสอบข้ามบัญชีได้ และรอบเก่า/ใหม่มีพฤติกรรมชัดเจน

### N4 — สร้างไฟล์และตรวจเข้า

เชื่อมตัวสร้างกับทะเบียน Key ที่ผ่าน N2 ไม่ reuse global BEK โดยเดา ตรวจ owner/version/assignment/student ที่ server ทดสอบไฟล์ผิด/เก่า/แก้ไขโดยไม่ผ่อน gate คุณช่วยเฉพาะกรณี native ที่ยังต้องยืนยัน

ผ่านเมื่อไฟล์และ verifier ตรงกันด้วยวิธีที่ได้รับอนุมัติ ไม่ใช่เพียงสร้างไฟล์ดาวน์โหลดได้

### N5 — หน้าครูและทางเข้าสอบ

ต่อ UI ตั้ง/เปลี่ยนรหัส เผยแพร่ ดาวน์โหลด/เปิดไฟล์ และ preflight ไม่เริ่ม timer ใช้การแจ้งผลตรงตาม readiness ไม่ให้ครูกรอก environment เอง คุณช่วยลองความเข้าใจง่ายของหน้าจอ

ผ่านเมื่อครู/นักเรียนทำเส้นทางใน staging ได้จริง และข้อความไม่ซ่อนขั้นตอน manual หากยังอยู่ในขอบเขตนำร่อง

### N6 — การส่งและอนุญาตออก

ทำเฉพาะนโยบายที่ D1/D2 ยอมรับ ตรวจ server authority/answer persistence/grant binding/reconnect และ fallback รหัสรายครู คุณไม่ต้องช่วยเขียนระบบ

ผ่านเมื่อ workflow ปกติ/ผิดพลาดทดสอบได้ ไม่มีการอ้างว่าปุ่มเว็บป้องกัน native exit ทุกทาง หรือ native ปิดแน่นอนจาก presence

### N7 — ตรวจรับและความผิดพลาด

Agent ตรวจ authorization/replay/revision, build/tests, load/connection budget ผู้ใช้ทดสอบ native ทุกแพลตฟอร์มที่ประกาศรองรับ: สองครู/สองนักเรียน, ส่งสำเร็จ/ล้มเหลว, เน็ตหลุด/กลับมา, emergency exit/resume, เปลี่ยนรหัส/ไฟล์เก่า ไม่จงใจทำให้เครื่องค้างหรือใช้ข้อสอบจริงเป็น fixture

ผ่านเมื่อไม่มีข้อผิดพลาดร้ายแรงด้านสิทธิ์/ข้อมูล/เข้าออก และระบุสิ่งที่ยังไม่ตรวจได้ชัด ผล unit test ไม่แทนผล native

### N8 — นำร่องและเปิดจริง

เตรียม deployment/backup/rollback, support checklist, usage/billing budget และเลือกกลุ่มเล็ก ผู้ใช้อนุมัติ production/ขอบเขตค่าใช้จ่ายและกลุ่มนำร่องก่อน ไม่เปิดทุกคนจากการ build ผ่าน

ผ่านเมื่อการใช้งานครบเส้นทางในกลุ่มนำร่องและมีการกู้คืนที่ตรวจแล้ว จึงพิจารณาขยาย ไม่ถือว่าไม่มีค่า SEB Server แปลว่าไม่มีค่าโฮสต์เว็บ

## ขอบเขตงานต่อและการส่งต่อ

- งาน N1 นี้ยังไม่ประกาศผ่าน ไม่เริ่ม N2/native test หรือตั้งฐาน/Key/deploy โดยอาศัยการอนุมัติเฟส 1
- รอ D1/D2 ที่ถามผู้ใช้แล้ว จากนั้นสรุปความหมาย D3 ด้วยภาษาการใช้งาน ไม่ให้ผู้ใช้เลือกวิธีเข้ารหัสเองโดยไม่มีคำอธิบาย
- หากไม่ยอมรับ Quit URL หรือยังยืนยัน automation เดิม ให้รายงานข้อจำกัดและทางเลือกก่อนขยายสถาปัตยกรรม ไม่กลับไปเช่า SEB Server หรือลด integrity อัตโนมัติ
- ก่อนแก้ runtime ต้องทบทวน `ARCHITECTURE.md`, `DOMAIN.md`, `DATA_MODEL.md`, `SECURITY.md` และ migration ledger ตาม `AGENTS.md`; เอกสารนี้ไม่ override guardrail เดิม
- บันทึกคำตอบและผลทดสอบจริงต่อในเอกสารนี้/รายงาน N2 ภายหลัง ไม่คัดลอก raw Key, รหัส, token, answers หรือข้อมูลนักเรียนลง Git

## ผลตรวจเอกสารรอบ N1

- อ่านโค้ดที่เกี่ยวข้องและเทียบกับ official specification/native source ตามลิงก์ข้างต้น; ผู้ตรวจอิสระสองรายตรวจประเด็น config/Key และ exit/policy ไม่พบข้อแก้ไขในขอบเขตที่ตรวจ
- `npm run seb:phase1:test`: 24 tests / 2 files ผ่านในรอบนี้ เป็นการตรวจ regression ของต้นแบบ **เดิมที่มี opening password** ไม่ใช่ผล native หรือหลักฐานว่า N2 ผ่าน
- ตรวจ relative Markdown links 21 จุดในเอกสารที่เปลี่ยน 6 ไฟล์ ไม่พบปลายทางหาย และ `git diff --check` ผ่าน
- ไม่รัน full suite, TypeScript, build หรือ UI lint เพราะแก้เฉพาะ Markdown ไม่มี application/UI change
- ไม่มี migration ใหม่หรือ apply migration, ไม่ provision keyring, ไม่เปลี่ยน deployment/env และไม่ได้เปิด native SEB
