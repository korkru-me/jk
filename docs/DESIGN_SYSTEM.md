# Brand, language และ UI rules

อัปเดตล่าสุด: 11 ตุลาคม 2026

## Brand

- ชื่อหลัก: **ก่อครู**
- English mark: **KorKru**
- โลโก้หลักใช้รูปกวางเรียบจากภาพที่เจ้าของผลิตภัณฑ์ส่ง 6 ตุลาคม 2026 ผ่าน `components/brand-logo.tsx` ร่วมกันทั้ง header หน้าเว็บสาธารณะและหน้าบัญชี โดย UI ใช้ geometry จาก `public/brand/deer-mark.svg` เป็น CSS mask สีเดียว จึงคงขอบคมทุกระดับการซูมและไม่มี glow/blur/bitmap ฝังอยู่ · ตาม UI-063 กวางทั้งตัวและตัว `o` ในคำว่า `KorKru` ใช้ token `brand-accent` เดียวกัน ซึ่งอ้างอิง `primary` ของ preset ปัจจุบันและเปลี่ยนตาม light/dark mode ส่วนตัวอักษรอื่นใช้ `brand-foreground` กรมท่า `#002262` ในโหมดสว่าง/ขาวในโหมดมืด ไม่ใช้สีดำของ UI foreground · เก็บภาพต้นฉบับ โลโก้เต็มเดิมที่ `public/logo.png` และไอคอนเดิมที่ `public/brand/legacy-*.png` ไว้ ไม่ลบหรือเขียนทับ
- แนวคิดภาษา: **“ก่อ…โดยครู”**
- ขนาดภาพกวางใน `BrandLogo`: stacked `h-10`, horizontal `h-11` และ compact `h-8`; ทุก layout ต้องใช้กวางสีเดียวกับตัว `o` ผ่าน `brand-accent` ห้ามแยกสีเขาหรือฝังสี hex ใน component · ปุ่มสามขีดใน header ใช้ `pl-3` เพื่อให้ขอบพื้นปุ่มตรงกับขอบซ้ายของแถบเมนูหลักเมื่อแถบเต็ม

คำตรงกลางเป็นข้อความที่เปลี่ยนได้ตามบริบท ไม่ใช่คำที่หายหรือ error state ตัวอย่างเช่น “ก่อข้อสอบโดยครู” บนหน้าสร้างข้อสอบ และ “ก่อห้องเรียนโดยครู” บนหน้าห้องเรียน

หากทำ motion/rotation:

- ต้องอ่านประโยคได้เมื่อ animation ถูกปิด
- หลีกเลี่ยงการสลับเร็วหรือทำ layout shift
- ใช้คำที่เจ้าของผลิตภัณฑ์อนุมัติหรือคำที่ตรงกับบริบทจริง
- รักษา accessibility สำหรับ `prefers-reduced-motion`

## ภาษา

- Product copy, labels, validation และคำอธิบายสำหรับผู้ใช้เป็นภาษาไทย
- Code, filenames, routes, database fields และ standard technical terms เป็นอังกฤษ
- ใช้คำสั้นและเป็นภาษาครู ไม่ใช้ศัพท์เทคนิคเพื่อทำให้ผลิตภัณฑ์ดูซับซ้อน
- แยกคำว่า “งาน”, “แบบฝึกหัด” และ “ข้อสอบ” ตามพฤติกรรมจริง ไม่ใช้สลับกันเมื่อมีผลต่อเวลา attempt หรือผลคะแนน
- Error message ต้องบอกว่าผู้ใช้ทำอะไรต่อได้ ไม่แสดง raw database error เมื่อเป็น production

## Visual language ที่มีอยู่

- Primary ปัจจุบันอยู่ในโทน magenta/violet (preset `playful` — ตั้งไว้ที่ `app/layout.tsx`) ค่าเริ่มต้นของระบบยังเป็น indigo
- Success ใช้ emerald/green, warning ใช้ amber, destructive ใช้ red
- ใช้ rounded cards, borders และ spacing แบบค่อนข้างโปร่ง
- ใช้ Lucide icons และ primitives ใน `components/ui/`
- เมนูหลักและเมนูย่อยครู/นักเรียนใช้ Lucide outline `size-4` ผ่าน `NavItemIcon` ร่วมกัน ไม่ใช้ emoji ผสมกับไอคอนเส้น; สีไอคอนตามสถานะเมนูเดิม
- ไอคอนประจำห้องใช้ `ClassroomIcon` ร่วมกันทั้งเมนู รายการห้อง ตัวเลือกห้อง Dashboard และหน้าสร้าง/ตั้งค่าห้อง (UI-016) เลือกได้อิสระ 21 รูป ไม่ผูกกับชื่อวิชา; picker แสดงเฉพาะรูป ไม่มีชื่อวิชาตามคำยืนยันล่าสุด ส่วน aria-label/tooltip เป็นคำอธิบายรูปกลาง ๆ ห้องเดิมหรือไม่เลือกใช้ `School` (อาคารเรียน) ต่อไป เก็บ presentation key ผ่าน description metadata เดิม ไม่เปลี่ยน schema; ไอคอนหมวด “ห้องเรียน” แบบทั่วไปยังเป็น School และ `BookOpen` ยังแทนงาน/ชุดข้อสอบ ครู ผู้ช่วยสอน และประเภทโฮมรูมคงความหมายเดิม
- รองรับ light/dark theme ในหลายส่วน แต่ต้องตรวจ contrast ทุกหน้าที่แก้
- ตาม UI-079 dialog สร้าง/แก้ไขแฟ้มย่อยต้องวางกลุ่ม “อยู่ในแฟ้มย่อยนี้” ก่อนช่องค้นหา และให้คำค้นกรองเฉพาะ “โจทย์ทั้งหมด” ด้านล่างโดยไม่ซ่อนสำเนาที่เลือก; แถวใน dialog มีเฉพาะรูปตาสำหรับดูตัวอย่าง ไม่วางปุ่มดินสอ ส่วน dialog แก้ไขต้องมีปุ่มถังขยะ “ลบแฟ้มย่อย” ที่ท้ายหน้าต่างและเปิด `ConfirmDialog` ก่อนลบเสมอ
- ตาม UI-100 ชื่อแฟ้มย่อยเดิมใน dialog แก้ไขเป็นข้อมูลอ่านอย่างเดียวจนกดปุ่ม “แก้ไขชื่อ” ที่มีดินสอ แล้วจึงแสดงช่องกรอกพร้อมปุ่มยืนยัน/ยกเลิกชื่อแยกจากปุ่มยืนยันสมาชิกแฟ้มย่อย · ทั้งหัว dialog และการ์ดแฟ้มย่อยต้องมีทางเปิด “ดูโจทย์ทั้งหมด” ในหน้าต่างเดียว โดยปิด control เมื่อไม่มีโจทย์ · การค้นหาโจทย์ทุกจุดต้องใช้กติกาคำต่อคำร่วมกันและค้นทั้งชื่อ เนื้อหาที่อ่านได้ แท็ก ระดับความยาก ประเภทโจทย์ และวิชา; ผลที่ไม่ได้มาจากแท็กหรือชื่อจัดอยู่ในกลุ่ม “เนื้อหาและข้อมูลกำกับ”
- ตาม UI-101 การบันทึกแฟ้มโจทย์อัตโนมัติทำงานอยู่เบื้องหลังโดยไม่แสดงสถานะรอ กำลังบันทึก หรือบันทึกสำเร็จในหัวหน้า เพื่อลดสิ่งรบกวนและหลีกเลี่ยงตัวหมุนค้าง; หากบันทึกล้มเหลวยังต้องแจ้งข้อผิดพลาดพร้อมทางลองใหม่ และยังเตือนก่อนปิดหน้าระหว่างมีข้อมูลที่รอบันทึกหรือบันทึกไม่สำเร็จ
- ตาม UI-080/UI-081 รายการ “เพิ่มจากแฟ้มโจทย์ที่มีอยู่” ในหน้าสร้างงานต้องให้การกดแฟ้มที่มีแฟ้มย่อยเปิดตัวเลือกแฟ้มย่อยแต่ละรายการก่อน แล้ววาง “ทุกข้อในแฟ้ม” เป็นตัวเลือกสุดท้าย แทนการเลือกทั้งแฟ้มทันที; ทุกระดับใช้สถานะเลือกและปุ่มดูตัวอย่างรูปแบบเดียวกัน ส่วนแฟ้มที่ไม่มีแฟ้มย่อยยังเลือกตรงจากแถวหลักได้ และคำค้นต้องค้นชื่อแฟ้มย่อยพร้อมเปิดผลที่ตรงให้เห็น
- ตาม UI-077 รายการเลือกสมาชิกแฟ้มย่อยต้องทำสำเนาข้อที่ติ๊กไว้ในกลุ่ม “อยู่ในแฟ้มย่อยนี้” ด้านบน แต่คงแถวต้นฉบับไว้ตามลำดับเดิมใต้ “โจทย์ทั้งหมด” พร้อม checkbox สถานะเดียวกัน; รายการ “เพิ่มโจทย์จากคลัง” ต้องมีปุ่มรูปตาแยกจาก label ของ checkbox เพื่อเปิดตัวอย่างโดยไม่เปลี่ยนการเลือก
- ตาม UI-076 คำอธิบายยาวเกี่ยวกับช่องแนบรูปวิธีทำในหน้าตัวอย่างโจทย์ต้องอยู่ใน Hover Card ของปุ่มเครื่องหมายคำถามข้าง “แนบรูปวิธีทำ” ไม่วางเป็น Card เต็มความกว้างใต้คำตอบ; trigger ต้องเปิดได้ด้วย hover และ keyboard focus ส่วนหน้าทำข้อสอบจริงไม่แสดงคำอธิบายสำหรับครูนี้

การเปลี่ยน palette หรือ component language หลักต้องเป็นการตัดสินใจระดับระบบ ไม่ปรับทีละหน้าโดยไม่มีแผน

ตัวกรองประเภทงาน “ทั้งหมด / แบบฝึกหัด / ข้อสอบ” ใช้ `components/assignments/assignment-type-filter.tsx` ร่วมกันทั้งรายการงานครู ตารางคะแนน และรายการงานนักเรียน: `ToggleGroup variant="primary" size="sm"` ในพื้น `muted` มุมโค้งชุดเดียว ปุ่มที่เลือกใช้ `primary-foreground` และคงหนึ่งตัวเลือกเสมอ; ส่ง `counts` ได้เมื่อหน้าต้องแสดงจำนวนงาน ไม่สร้างปุ่มแยกสีดำหรือสไตล์เฉพาะหน้าใหม่สำหรับตัวกรองนี้

ตาม UI-022 ตัวกรองระดับความยากใน `QuestionPicker` ใช้ `ToggleGroup variant="primary" size="sm"` เช่นเดียวกับตัวกรองหลักอื่น ปุ่มที่เลือกใช้ `bg-primary`/`text-primary-foreground` ไม่ใช้ `bg-foreground` สีดำ; ปุ่มที่ไม่เลือกยังมีกรอบ `border-border` และคงหนึ่งระดับไว้เสมอ การเปลี่ยนนี้ใช้ร่วมกันทุกจุดที่ฝัง `QuestionPicker` โดยไม่เปลี่ยนกติกาการค้นหาหรือกรอง

ตาม UI-020/UI-084/UI-085/UI-086/UI-087/UI-088/UI-089/UI-090/UI-091/UI-092/UI-093/UI-094 หน้าสร้างงานรวมการเลือกโจทย์ คะแนนรายข้อ จำนวนข้อต่อหน้า และเวลาทำใน `Card` เดียวชื่อ “โจทย์ คะแนน และเวลา” โดยเรียงตาม dependency ของงานจริง: เลือกโจทย์ → ตั้งคะแนนรายข้อ → ตั้งเวลา และไม่เสนอการสร้างแฟ้มโจทย์ระหว่างมอบหมายงาน; ครูจัดแฟ้มจากหน้าคลังแฟ้มก่อน แล้วเลือกแฟ้มหรือโจทย์ที่มีอยู่มาใช้ในงาน ส่วน “คะแนนเต็มที่แสดงผล” ต้องอยู่ใน `Card` “ชุดโจทย์ที่นักเรียนได้รับ” เดียวกัน และเมื่อสุ่มต้องวางคู่กับจำนวนข้อที่ให้นักเรียนทำในแถวเดียวกันตั้งแต่จอ `sm` ขึ้นไปโดยไม่ใช้กรอบซ้อน และหัวข้อ “เลือกโจทย์” ต้องมี `*` สี `destructive` พร้อมข้อความ “จำเป็น” สำหรับ screen reader เพราะไม่อนุญาตให้สร้างงานที่ไม่มีโจทย์ ส่วน “เพิ่มจากแฟ้มโจทย์ที่มีอยู่” และ “เลือกโจทย์รายข้อ” ต้องพับเมื่อคลิกนอกกรอบ แต่ไม่พับจาก interaction ภายในหรือ dialog ตัวอย่าง และต้องสลับกรอบที่เปิดได้ในคลิกเดียว ส่วน “คะแนนแต่ละข้อ” ต้องมีปุ่ม “ดูโจทย์ทั้งหมด” เพื่อเปิดตัวอย่างครบตามลำดับปัจจุบันในหน้าต่างเดียว มีคำสั่งเล็ก “ทุกข้อ 1 คะแนน” และ “คะแนนตามข้อย่อย” สำหรับปรับคะแนนโจทย์ที่เลือกทั้งชุด; คำสั่งล่าสุดที่ใช้สำเร็จต้องคงพื้น `primary` และเครื่องหมายถูกพร้อม `aria-pressed`/live status จนกว่าจะเปลี่ยนคะแนนรายข้อหรือสมาชิกโจทย์ เพื่อยืนยันผลโดยไม่ทำให้ครูเข้าใจผิด และใช้การกดค้างลากบริเวณหมายเลข/ชื่อโจทย์เพื่อเรียงแทนลูกศรขึ้นลง โดยคงช่องเลขที่พิมพ์ตำแหน่งแล้วกด Enter ได้และไม่ให้ gesture ลากครอบปุ่มดูตัวอย่าง ช่องคะแนน หรือปุ่มลบ; ภายใน dialog ดูทั้งหมด เลขข้อของแต่ละการ์ดเป็นดรอปดาวน์สำหรับย้ายตรงไปยังตำแหน่งปลายทาง ต้องแสดงคำอธิบาย “เลือกเพื่อย้ายโจทย์ไปยังลำดับที่ต้องการ” เมื่อวางเมาส์หรือโฟกัสด้วยแป้นพิมพ์ และต้องอัปเดตลำดับจริงชุดเดียวกับรายการคะแนนโดยไม่โหลดเนื้อหาโจทย์ซ้ำ ส่วน preview จากแฟ้มยังเป็น read-only ไม่มีตัวควบคุมลำดับ เมื่อเลือกสุ่มให้ปิดช่อง/คำสั่งคะแนนรายข้อ แสดงทุกข้อเป็น 1 คะแนน และอธิบายว่าคะแนนดิบเท่ากับจำนวนข้อที่ตอบถูก ส่วนหน้าแก้ไขงานใช้กติกาเดียวกันแต่ยังรวมคะแนนรายข้อกับคะแนนเต็มแสดงผลไว้ใน `Card` “ตั้งค่าคะแนน” เดิม มีหัวข้อย่อยและ `Separator` แบ่งส่วน ไม่ใช้กรอบซ้อนหรือซ่อนความต่างของคะแนนจริงกับคะแนนที่แสดง; แถวคะแนนขึ้นหลายบรรทัดเมื่อจอเล็กเพื่อให้ชื่อโจทย์ ลำดับ ปุ่ม และช่องคะแนนไม่ถูกตัด และคงแถวเดียวตั้งแต่ `sm` ขึ้นไป

ตาม UI-010/011/020/082/UI-090/UI-092/UI-094 หลังเลือกโจทย์แล้ว หน้าสร้างงานวาง “ชุดโจทย์ที่นักเรียนได้รับ” เป็นกรอบถัดจาก Card รวม “โจทย์ คะแนน และเวลา” และรวม “คะแนนเต็มที่แสดงผล” ไว้ในกรอบเดียวกันก่อนเงื่อนไขจบงาน โดยไม่แสดงกรอบคะแนนแยกขณะยังไม่มีโจทย์: โหมดทำทุกข้อเว้นว่างเพื่อใช้ผลรวมจริง ส่วนโหมดสุ่มกำหนดทุกข้อเป็น 1 คะแนนและวางจำนวนข้อที่ให้นักเรียนทำกับคะแนนเต็มใน grid สองคอลัมน์เดียวกันตั้งแต่จอ `sm` ขึ้นไป โดยเว้นว่างคะแนนเต็มเพื่อใช้จำนวนข้อที่สุ่มเป็นค่าอัตโนมัติ หรือกรอกค่าบวกเพื่อปรับสเกลคะแนนรวมได้ หน้าแก้ไขยังวางกรอบชุดโจทย์ถัดจาก Card “ตั้งค่าคะแนน” ตามเดิม จำนวนข้อต่อหนึ่งหน้าอยู่ภายใน Card คะแนนทั้งสองหน้า; งานใหม่ที่ไม่ได้ทำสำเนาหรือใช้ชุดการตั้งค่าที่บันทึกไว้เริ่มต้นที่ 5 ข้อต่อหน้า ส่วนโหมด streak ยังคงแสดงคำอธิบายทีละ 1 ข้อแทนช่องตามเดิม

ตาม UI-095/UI-096 `NativeSelect` สำหรับเรียกใช้ชุดการตั้งค่าใน Card ต้องอยู่ใน `FieldGroup` ที่กว้างเต็มพื้นที่บนจอเล็ก แต่จำกัดความกว้างสูงสุดที่ `max-w-xl` บนพื้นที่กว้าง เพื่อไม่ให้ลูกศร native select ลอยไปชิดขอบขวาของ Card; ส่วนตัวเลือกเป้าหมายบันทึกอยู่ใน Dialog ตาม UI-096 และใช้ความกว้างของ Dialog เพื่อให้ข้อความกำกับกับตัวควบคุมอยู่ในแนวเดียวกัน

ตาม UI-012/UI-020 ช่อง “เวลาทำ (นาที)” ของ wizard สร้างงาน/ข้อสอบยังอยู่ในขั้น “รายละเอียด โจทย์ และคะแนน” และไม่อยู่ในขั้นตั้งค่า แต่ย้ายจาก Card ข้อมูลพื้นฐานเข้า Card “โจทย์ คะแนน และเวลา” ต่อจากส่วนคะแนน คงค่าและการเว้นว่างเพื่อไม่จำกัดเวลาเดิม ตาม UI-013 เมื่อเปลี่ยนขั้นทั้งถัดไป/ย้อนกลับให้กลับบนสุดทันทีหลัง render ทั้ง main panel ของ app shell และ window ของหน้าเดี่ยว ไม่เลื่อนตอนเปิดครั้งแรกหรือเพียงแก้ข้อมูลในขั้นเดิม และไม่ล้าง state

ตาม UI-017/UI-019/UI-021/UI-096 ชุดการตั้งค่าส่วนตัวแยกทางเรียกใช้และทางบันทึก: Card ก่อน stepper ปรากฏเฉพาะหน้าแรกและพับไว้เป็นค่าเริ่มต้น แสดงชื่อค่าที่ใช้อยู่บนหัวกรอบและกดขยายเมื่อต้องการเปลี่ยน; รายการเดียวมีทั้งค่าระบบและชุดส่วนตัวโดยไม่มีปุ่มคำสั่งซ้ำใต้รายการ หน้าสุดท้ายมีปุ่ม “บันทึกการตั้งค่า” อยู่ในกลุ่มคำสั่งเดียวกับ “บันทึกแบบร่าง” และ “สร้าง…” โดยเปิด Dialog เป็นช่องบันทึก 3 ช่อง ต้องเลือกช่องก่อนจึงแสดงช่องตั้งชื่อและตัวเลือกตั้งเป็นค่าเริ่มต้น ช่องที่มีข้อมูลบันทึกทับหรือลบได้ ส่วนช่องว่างถัดไปใช้สร้างชุดใหม่ การบันทึกชุดไม่บังคับและไม่บันทึก/สร้างงาน การเลือกช่องไม่เรียกค่าเก่าทับ draft; ใช้ provider เดียวเก็บ state ตลอด wizard แยก exercise/exam ประเภทละ 3 ชุดต่อบัญชี แสดงโควตาใน Dialog และ default ในตัวเลือก ใช้ค่าระบบได้โดยไม่กินช่อง สำเนาใช้ค่าต้นฉบับ ไม่อ่าน default ทับ หน้าแก้ไขไม่มีส่วนนี้ สลับชุดหลังปรับค่าให้แสดง diff และยืนยันเฉพาะ settings ไม่แตะเนื้อหางานหรือรหัสผ่าน ถ้าสุ่มจำนวนเกินคลังต้องเตือนและให้ครูเลือกแก้เอง ไม่ลดจำนวนเงียบ ๆ การตรวจสอบข้อมูลล่าสุดเกิดอัตโนมัติและไม่เปลี่ยนค่าฟอร์มหรือล้าง draft · การคลิกฉากหลังของ Dialog บันทึกชุดต้องยกเลิก outside-dismiss แล้วเปิด `ConfirmDialog` แบบ sibling ก่อนทิ้งข้อมูล โดยมีทางกลับไปตั้งค่าต่อและคืน focus สู่ Dialog หลัก

ตาม UI-021 เมื่อเข้าหน้าสร้างงานจากบริบทห้องเรียน กรอบ “มอบหมายให้ห้องเรียนอื่นด้วย” และตัวเลือกกลุ่มของห้องที่เพิ่มอยู่ในขั้น “กำหนดการสอบ” ต่อจากวันเปิด/ปิดรับและก่อน “แสดงผลลัพธ์”; ขั้น “ตั้งค่า” เหลือเฉพาะพฤติกรรมการทำงาน/ความปลอดภัย ส่วนผู้รับของห้องหลักยังอยู่ขั้นแรก ทางเข้าที่ไม่มีห้องบริบทยังเลือกทุกห้องและกลุ่มในขั้นแรกตามเดิม การตรวจกลุ่มที่ยังเลือกไม่ครบต้องพากลับขั้นกำหนดการ ไม่ใช่ขั้นตั้งค่า

ตาม UI-023 `AssignmentReviewSummary` ไม่รับสีหน้าปกห้องเรียนและไม่ลงสีพิเศษ ใช้ Card มาตรฐาน `bg-card` พร้อม `text-foreground`/`text-muted-foreground` และ `border-border` เหมือนส่วนอื่นของฟอร์ม · ขั้น “กำหนดการสอบ” เรียง “กำหนดวันทำ” แบบพับ → รหัสผ่านเข้าทำ → ห้องเรียนอื่น → แสดงผลลัพธ์ → สรุปก่อนสร้าง; ช่องวันเปิด/ปิดซ่อนไว้เมื่อยังไม่กำหนดและเปิดอัตโนมัติสำหรับงานสำเนาที่มีวันเดิม ตัวเลือกแสดงผลใช้ `ToggleGroup orientation="vertical"` โดยแต่ละตัวเลือกเป็นแถวเต็มความกว้าง (ชื่อ + ไอคอนช่วยเหลือ → เครื่องหมายถูก) และแต่ละแถวเรียงลงมาด้านล่าง คงหนึ่งตัวเลือกเสมอ; คำอธิบายแสดงผ่าน Hover Card ของปุ่มทั้งแถวและ keyboard focus จึงไม่เพิ่มความสูงของรายการหรือทำให้จอเล็กล้น

ตาม UI-097 ในขั้น “กำหนดการสอบ” disclosure “กำหนดวันทำ” และ “มอบหมายให้ห้องเรียนอื่นด้วย” ต้องพับเมื่อคลิกนอกกรอบของตัวเอง แต่ interaction ภายในเนื้อหาที่เปิดอยู่ต้องไม่ทำให้พับ; เมื่อคลิก trigger ของอีกส่วน ต้องพับส่วนเดิมและเปิดส่วนใหม่ได้ในคลิกเดียว trigger “มอบหมายให้ห้องเรียนอื่นด้วย” ต้องคงพื้นและสีสถานะ neutral แม้เปิดอยู่ ไม่ใช้พื้นเทาเป็น selected state และสื่อสถานะด้วยทิศทาง chevron พร้อม `aria-expanded` ที่ตรงกับการแสดงเนื้อหา

ตาม UI-098 ซึ่งแทนพฤติกรรมเดิมของ UI-023 ในหน้าสร้างงาน: “แสดงผลลัพธ์” ต้องใช้ Select/Dropdown มาตรฐานหนึ่งช่องและแสดงคำอธิบายของค่าปัจจุบันใต้ช่อง ไม่ใช้ ToggleGroup หลายแถว; “รหัสผ่านเข้าทำ” ต้องอยู่ขั้น “ตั้งค่า” ในรูปแบบ checkbox “กำหนดรหัสผ่านเข้าทำ” เหมือนตัวเลือกอื่น เปิดแล้วจึงแสดงช่องกรอกและต้องมีค่าก่อนผ่านขั้น ปิดแล้วต้องไม่ส่งค่าไปบันทึก และต้องไม่รวมรหัสผ่านไว้ในชุดการตั้งค่าที่บันทึกใช้ซ้ำ; กรอบสุดท้ายใช้ชื่อ “ตรวจสอบรายละเอียดก่อนสร้าง” หรือ “ตรวจสอบรายละเอียดก่อนทำสำเนา” และแสดงสถานะรหัสผ่านอย่างชัดเจน Select/Dropdown ต้องพับเมื่อคลิกนอกกรอบตามกฎ overlay ส่วนตัวตรวจ click-away ของ disclosure ที่มี DOM เปลี่ยนระหว่างเหตุการณ์ต้องตรวจทั้ง `contains()` และ `event.composedPath()` เพื่อไม่ให้คลิกภายในถูกตีความผิด

ตาม UI-099 หน้าสร้าง/ทำสำเนาแบบฝึกหัดและข้อสอบต้องติด `beforeunload` เฉพาะเมื่อค่าที่จะบันทึกต่างจากค่าเริ่มต้น เพื่อเตือนก่อนรีเฟรช ปิดแท็บ หรือปิดหน้าต่าง และต้องถอด listener เมื่อค่ากลับเหมือนเดิมหรือ component ออกจากหน้า; ห้ามนับ state เพื่อการนำทางหรือการมองเห็นชั่วคราว เช่น ขั้นปัจจุบัน ดรอปดาวน์ disclosure คำค้นหา และ preview เป็นข้อมูลที่ยังไม่บันทึก ข้อความในคำเตือนใช้ของเบราว์เซอร์เพราะ browser security policy ไม่รับประกันข้อความกำหนดเอง

## Style presets

สไตล์ทั้งเว็บคุมด้วย CSS variable ใน `app/globals.css` ไม่ใช่ class ในแต่ละไฟล์ แกนที่หมุนได้:

- `--primary`, `--success`, `--warning`, `--flag`, `--destructive` และ token สีอื่น — ความหมาย ไม่ใช่การตกแต่ง
- `--radius` — ความมนทั้งเว็บ (Tailwind คำนวณ `rounded-*` จากค่านี้)
- `--spacing` — ความโปร่ง/แน่น (Tailwind คำนวณ `p-*`, `gap-*`, `m-*` จากค่านี้)
- `--elevation-sm|md|lg|xl` — เงา

เปลี่ยนสไตล์ทั้งเว็บด้วยการใส่ `data-style` บน `<html>` ใน `app/layout.tsx`:

```
<html lang="th" data-style="warm">
```

preset ที่มีให้:

| preset | ลักษณะ |
| --- | --- |
| `soft` | มน โปร่ง เงานุ่มฟุ้ง |
| `sharp` | เหลี่ยม แน่น ไม่มีเงา ใช้เส้นขอบแทน |
| `warm` | พื้นครีม primary terracotta |
| `minimal` | เกือบขาวดำ น้ำหนักตัวอักษรเบา เส้นขอบบาง |
| `playful` | หนา มนมาก เงาทึบแบบ offset |

ไม่ใส่ = ค่าเริ่มต้น (indigo, มนปานกลาง) — ปัจจุบันแอปตั้ง `data-style="playful"` ไว้

ทุก preset ผ่าน WCAG AA (ตัวอักษรบนปุ่ม primary ≥ 4.5:1) ทั้งโหมดสว่างและมืด ถ้าเพิ่ม preset ใหม่ต้องวัด contrast ก่อนใช้

สีแบ่งเป็น 2 ชนิด — อย่าสลับกัน:

- **สีที่มีความหมาย** (`--primary`, `--success`, `--warning`, `--flag`, `--destructive`) เปลี่ยนค่าได้ แต่ห้ามเปลี่ยนว่าอะไรหมายถึงอะไร
- **ฉากหลังทึบ** (`--overlay`) ใช้กับ modal และภาพที่ต้องหรี่ — preset ปรับความเข้ม/โทนได้
- **พื้นมืดกลับสี** (`--surface-inverse` + `-foreground` / `-muted` / `-border`) ใช้กับแบนเนอร์ การ์ดหัวเรื่อง และ chrome ของ super-admin ที่ตั้งใจให้มืดทั้งสองโหมด — preset ปรับโทนได้
- **สีตกแต่ง** (`--tint-1` … `--tint-4`) ใช้แยกแยะรายการเฉยๆ เช่น stat card, ไอคอน, ป้ายหมวดหมู่ — สลับได้อิสระ preset ควรปรับให้เข้ากับ primary ของตัวเอง (เช่น `playful` ใช้ primary ม่วงแดง จึงดัน tint-1 ไปทางน้ำเงินไม่ให้ดูเหมือนพลาด)

preset ปรับได้ 5 แกน: สี, `--radius`, `--spacing`, `--elevation-*` และ typography (`--font-weight-*`, `--text-*`, `--tracking-*`) — Tailwind v4 คำนวณ utility จากตัวแปรเหล่านี้อยู่แล้ว จึงไม่ต้องแก้ component

ดูผลของแต่ละ preset บนคอมโพเนนต์จริงได้ที่ `/style-preview` (เปิดเฉพาะตอน `next dev` — production จะ 404)

เพิ่ม preset ใหม่โดยคัดลอกบล็อก `[data-style="..."]` ท้าย `globals.css` แล้วแก้ค่า ไม่ต้องแก้ไฟล์อื่น

**preset เปลี่ยนได้เฉพาะการตกแต่ง** ห้ามเปลี่ยนว่าสีไหนหมายถึงอะไร — เขียวยังคงหมายถึงสำเร็จ ส้มยังคงหมายถึงโจทย์ที่ถูกรายงาน ในทุก preset

สิ่งที่ยังเป็นค่าคงที่โดยตั้งใจ: แถบสเกลเปอร์เซ็นไทล์ — เป็นเนื้อหาและความหมาย ไม่ใช่การตกแต่ง preset จึงไม่ควรเปลี่ยน

ชุดสีปกห้องเรียน (`COVER_PRESETS` ใน `app/(app)/classrooms/_components/classroom-meta.ts`) เคยเป็น hex ไล่เฉดคงที่ แต่เปลี่ยนมาเป็นสีพื้นเรียบที่อ้าง token ตามที่เจ้าของผลิตภัณฑ์สั่ง จึงเปลี่ยนตาม preset และโหมดสว่าง/มืดด้วย ผลที่ตามมาคือการสลับ preset จะเปลี่ยนโทนสีปกที่ครูเลือกไว้ — แลกกับการได้ contrast ที่ผ่าน AA ทั้งสองโหมดโดยไม่ต้องดูแลชุด hex เอง

ภาพปกห้องเรียนใช้ `ClassroomCoverPattern` และ stable key จาก `lib/classroom-cover-patterns.ts` จำนวน 11 แบบ ทุกรูปทรงใช้ `currentColor` สีเดียวหลายระดับ opacity โดยไม่มี hex หรือ palette ฝังในภาพ จึงเปลี่ยนตาม `COVER_PRESETS`, preset และ light/dark mode ได้ · ตาม UI-057 พื้นที่ภาพอยู่ในครึ่งสามเหลี่ยมขวาบนเหนือเส้นทแยงจากซ้ายบนไปขวาล่าง ส่วนซ้ายล่างต้องสงบเพื่อรองรับชื่อห้อง ภาพใช้รูปทรงทึบโปร่งแสงร่วมกับเส้นรายละเอียดได้ ไม่จำกัดเป็น line art และใช้ `placement="end"` กับ `meet` เพื่อรักษาตำแหน่งโดยไม่ crop · ชุดนี้เป็นองค์ประกอบต้นฉบับของ KorKru ไม่คัดลอกหรือเลียนแบบชุดปกของ Google Classroom และลายกวางต้องอิงเครื่องหมายแบรนด์ที่อนุมัติใน `public/brand/deer-mark.svg` ไม่ใช้กวางสต็อก · ตาม UI-083 ส่วนเลือกภาพปกแสดงหัวข้อ “ภาพปกห้องเรียน” แล้วตามด้วยตัวเลือกทันที ไม่แสดงข้อความอธิบายงานออกแบบหรือการเปลี่ยนสีตามธีม · ตัวเลือกปกต้องแสดงภาพอย่างเดียวโดยไม่มีชื่อวิชาหรือคำอธิบายชี้นำทั้ง caption และ tooltip ผู้ใช้เป็นผู้กำหนดความหมายเอง ส่วน accessible name ใช้เลขลำดับกลาง เช่น “ภาพปกแบบที่ 1” · หน้าเริ่มสร้างห้องต้องสุ่ม stable key หนึ่งครั้งต่อฟอร์มและคงค่านั้นจนบันทึก ไม่สุ่มใหม่จาก re-render; การทำสำเนาคงปกต้นฉบับและสุ่มเฉพาะห้องเก่าที่ไม่มี key · ห้องเก่าหรือ key ที่ไม่รู้จักในจุดแสดงผลยังใช้ลาย `classroom` และต้องไม่ render markup/URL ที่มาจาก metadata โดยตรง

ตัวอักษรบนหน้าปกต้องผสมกับ `--foreground` ด้วย `color-mix` เสมอ ห้ามวางสี token เต็มความเข้มบนพื้น `/10` เพราะวัดจริงแล้วได้เพียง 1.9–4.5:1 ซึ่งตกเกณฑ์ AA เกือบทุกสี

องค์ประกอบใหม่ต้องใช้ token และ primitive ใน `components/ui/` ไม่เขียน class สีหรือทรงเอง — `npm run lint:tokens` ตรวจข้อนี้ 4 อย่าง:

| ตรวจอะไร | ใช้อะไรแทน |
| --- | --- |
| สี palette ดิบ (`bg-gray-100`, `text-white`, `bg-black/50`) | token ใน `globals.css` |
| การ์ดเขียนมือ | `<Card>` |
| form control เขียนมือ | `<Input>` / `<Textarea>` / `<NativeSelect>` |
| ปุ่มเขียนมือ | `<Button>` / `<IconButton>` |
| class ผิดรูป (`bg-primary/10/40`) | — Tailwind ทิ้งเงียบๆ ต้องแก้ |

`<NativeSelect>` คือ `<select>` ธรรมดาที่จัดสไตล์ให้ตรงกับ `<Input>` ส่วน `<Select>` (base-ui) เป็น dropdown แบบเต็มรูปแบบสำหรับกรณีที่ต้องการมากกว่านั้น

## UI behavior

- ตาม UI-078 การ์ดแฟ้มย่อยใช้ทั้งกรอบเป็น click target เพื่อเปิดและเป็น sortable activator เพื่อสลับตำแหน่ง โดยเมาส์มี distance threshold, จอสัมผัสใช้ press delay เพื่อไม่ขัดการ scroll และคีย์บอร์ดใช้ Space + ลูกศร · เมนู ⋮ ต้องเหลือเพียง “ลบแฟ้มย่อย” และการลบต้องผ่าน `ConfirmDialog` ที่บอกผลต่อโจทย์ก่อนเสมอ
- ตาม UI-074 ป๊อปอัปตั้งค่าห้องเรียนไม่แสดงคำอธิบายซ้ำใต้หัว “ตั้งค่าห้องเรียน” หรือข้อความเตือนใต้ข้อมูล read-only; Card ประเภทห้องเรียนและรหัสห้องเรียนใช้ grid สองคอลัมน์กะทัดรัดที่สูงตามเนื้อหา โดยยังแสดงค่าทั้งสองครบและไม่เปลี่ยนให้แก้ไขได้
- ตาม UI-061 Topbar ของ app shell ใช้ความสูง `h-12` และโลโก้ KorKru แบบ horizontal ขนาด compact ให้รูปกวางกับชื่ออยู่บรรทัดเดียวกัน เพื่อลดพื้นที่เหนือเนื้อหา โดยคง hit area ของปุ่มเมนู การแจ้งเตือน ตัวสลับธีม และโปรไฟล์เดิม · mobile sidebar กับ backdrop ต้องเริ่มที่ `top-12` ตรงใต้ Topbar เสมอ ห้ามเหลือช่องว่างหรือซ้อนทับแถบหัว
- ตาม UI-044 ส่วนสรุปหน้ารายละเอียดงานใช้ Card หลักแบบกระชับเพียงสองชั้น: ข้อมูลกำหนดการทั้งห้าไม่มีกรอบย่อยและเรียงเป็น grid แถวเดียวเมื่อพื้นที่พอ ส่วนสถิติสามค่ากับความคืบหน้าอยู่ใน Card เดียว; mobile ยังคงอ่านครบโดยให้เงื่อนไขจบและความคืบหน้ากินเต็มแถว และห้ามลดขนาดข้อความหรือ touch target ของ action ใน sidebar
- Mobile-first และใช้งานได้อย่างน้อยบน mobile/tablet/desktop
- ตาม UI-014/UI-018 การย่อ/ขยายแถบเมนูของ app shell เปลี่ยนขนาดทันที (`transition-none`) และ drawer มือถือเปิด/ปิดทันที ไม่มีแอนิเมชัน width/transform 200ms เดิม ปุ่มใน contextual sidebar ใช้ `transition-colors` แทน `transition-all` เพื่อให้ความสูง/padding กับตำแหน่งไอคอนเปลี่ยนทันทีตามแกน Y แต่ยังคงแอนิเมชันสีของ hover/focus คง icon rail, การจำสถานะ, inert, backdrop และ Escape เดิม ไม่เปลี่ยนแอนิเมชันเมนูย่อยหรือส่วนอื่นของเว็บ
- ตาม UI-049 เมื่อ sidebar ย่อเป็น icon rail บน desktop การ hover ที่ rail ต้องเปิด panel เต็มแบบ overlay ทับ main content โดยไม่เปลี่ยนความกว้างของ layout; เอา pointer ออกจาก rail แล้วหุบทันที ปุ่ม hamburger เท่านั้นที่ปักหมุด panel เต็มและดัน main content ส่วน mobile drawer คงพฤติกรรมเดิม
- ตาม UI-050 เมื่อสลับ sidebar ระหว่าง panel เต็มกับ icon rail บน desktop ตำแหน่งกึ่งกลางของไอคอนแต่ละรายการในแกน Y ต้องคงเดิม โดยโหมดย่อซ่อนข้อความแต่ยังสงวนความสูงของหัวข้อ การ์ดบริบท padding และแถวเมนูเดิมไว้; การ hover เปิด preview จึงไม่ทำให้ไอคอนกระโดดขึ้นหรือลง
- ตาม UI-051 ชุดไอคอนห้องเรียนที่ขยายต้องอยู่ใน Card ขอบชัดเช่นเดียวกับชุดธีมสี และในหน้าสร้าง/ทำสำเนาห้องเรียน การกดนอกกรอบจริงของทั้งสอง picker—รวมถึงช่องว่างระหว่างคอลัมน์หรือใต้คอลัมน์ที่สั้นกว่า—ต้องพับ disclosure ที่เปิดอยู่ทั้งหมดโดยไม่เปลี่ยนค่าที่เลือก; การกดภายในกรอบใดกรอบหนึ่งยังไม่ถือว่าเป็น outside interaction
- ตาม UI-052 การ์ดห้องเรียนวิชาที่กำลังลากเพื่อจัดลำดับใช้ opacity สื่อสถานะได้ แต่ห้ามเพิ่ม `shadow-xl` หรือเอฟเฟกต์ที่กลายเป็นแถบสีใต้การ์ด; drag handle, hit area, การเคลื่อนตำแหน่ง และการบันทึกลำดับคงเดิม
- ตาม UI-053/UI-064 `QuestionPicker` แสดงโจทย์ที่เลือกเป็นกลุ่มสำเนาด้านบนโดยต้องคงแถวต้นฉบับไว้ในลำดับคลังพร้อม checkbox ที่สะท้อนสถานะเดียวกัน และรักษาตำแหน่งเลื่อนเมื่อเลือกจากแถวต้นฉบับ · ข้อที่เพิ่งเลือกห้ามแสดงข้อความ “+ จะเพิ่มเข้าแฟ้ม” ซ้ำ ให้แสดงข้อความย่อของโจทย์แทน ส่วนข้อที่ยกเลิกจาก baseline ยังแสดง “− จะเอาออกจาก…” เพื่อแยกจากข้อที่ไม่เคยอยู่ในชุด; dialog ที่มีร่างเลือกโจทย์ซึ่งยังไม่ยืนยันต้องใช้ `ConfirmDialog` เตือนก่อนปิดจากฉากหลัง ปุ่มปิด Escape หรือยกเลิก โดยบอกชัดว่ารายการครั้งนี้จะหายและมีทางกลับไปเลือกต่อ
- ตาม UI-065 ปุ่มหลักท้าย dialog เพิ่ม/เอาโจทย์และ dialog จัดแฟ้มย่อยใช้ข้อความสั้น “ยืนยัน” ไม่ใช้ “ยืนยันการเปลี่ยนแปลง”; คำเตือนร่างและ tooltip ต้องเรียกชื่อปุ่มเดียวกัน โดยไม่เปลี่ยน guard หรือขอบเขตข้อมูลที่จะบันทึก
- ตาม UI-066 dialog สร้าง/แก้ไขแฟ้มย่อยปิดได้ทันทีเมื่อชื่อและสมาชิกโจทย์ยังเหมือนค่าเริ่มต้น แต่ถ้ามีร่างที่ยังไม่ยืนยัน การคลิกฉากหลัง กากบาท Escape หรือยกเลิกต้องเปิด `ConfirmDialog` ก่อนทิ้งข้อมูล · การกลับไปทำต่อต้องรักษาชื่อ checkbox และ focus ไว้ ส่วนการยืนยันออกจึงค่อยล้างร่าง โดยใช้ภาษาและลำดับปุ่มเดียวกับ guard ของ dialog เพิ่มโจทย์จากคลัง
- ตาม UI-067/UI-072 รายชื่อแฟ้มย่อยของโจทย์ต้องมีคำกำกับ “อยู่ในแฟ้มย่อย:” แยกออกจากวิชา หมวดหมู่ และแท็ก และแสดงชื่อทั้งหมดเป็นป้ายพื้นม่วงอ่อนกับข้อความสีหลักที่ wrap ได้โดยไม่ตัดเป็น `+N` หรือซ่อนบนมือถือ; เมื่อไม่มีสมาชิกให้แสดง “อยู่ในแฟ้มย่อย: -” แทนประโยคสถานะ · ใช้รูปแบบเดียวกันใน dialog จัดสมาชิก การ์ดโจทย์ และรายการสั้น; สถานะร่าง “จะเพิ่ม/จะเอาออก” เป็นอีกบรรทัดและห้ามแทนที่รายชื่อสมาชิกที่บันทึกอยู่

- **ปุ่มย้อนกลับหมายถึงหน้าที่ผู้ใช้เพิ่งมาจาก ไม่ใช่หน้าแม่ตามเส้นทาง URL** — หน้าเดียวเข้าถึงได้จากหลายที่ (เช่น หน้านำเข้าจาก Word เข้าได้ทั้งจากหน้าเลือกวิธีนำเข้าและจากปุ่มบนคลังโจทย์) หน้านั้นจึงตอบเองไม่ได้ว่าผู้ใช้มาจากไหน · ฝั่งที่ลิงก์เข้าไปต้องบอกด้วย `withBackHref(target, from)` แล้วปุ่มย้อนกลับอ่านคืนด้วย `resolveBackHref`/`backHrefFromSearchParams` (`lib/back-link.ts`)
  - พา view เดิมไปทั้ง URL รวม query ด้วย คลังโจทย์ที่กรองคำว่า "นิวตัน" อยู่หน้า 2 จึงกลับมาเหมือนตอนที่จากไป ไม่ใช่รายการเปล่าหน้า 1
  - `fallback` คือที่ที่น่าจะมาจากมากที่สุดเมื่อไม่มีอะไรถูกจำไว้ (เปิดจาก bookmark, พิมพ์ URL เอง, หรือลิงก์เก่า) ไม่จำเป็นต้องเป็นหน้าแม่ตามเส้นทาง
  - **ค่าที่จำไว้มาจากเบราว์เซอร์ จึงไม่เชื่อ** `resolveBackHref` คืนเฉพาะ path ภายในแอป ปฏิเสธ URL ที่มี scheme และ `//host` / `/\host` ที่เบราว์เซอร์อ่านเป็น protocol-relative — ด้วยเหตุผลเดียวกับที่ `safeQuestionsRedirect` มีอยู่ ปุ่มย้อนกลับที่เชื่อค่าใน URL คือ open redirect
  - หน้าที่เป็นปลายทางของเมนูด้านซ้ายไม่ต้องมีปุ่มย้อนกลับ (เช่น `/questions/new`, `/questions/import`) เพราะไม่ได้มีหน้าก่อนหน้าที่แน่นอน
- อย่าซ่อน authorization error ด้วย empty state
- Form ต้องมี label ที่อ่านได้ด้วย assistive technology

## ข้อมูลจริงกับต้นแบบ

- Mock/prototype ต้องมีป้ายชัดหรือซ่อนจาก production navigation
- ห้ามใช้เลขสุ่มเป็น analytics โดยไม่ระบุว่าเป็นข้อมูลตัวอย่าง
- ห้ามแสดง invoice, usage, plan หรือ cancellation สำเร็จหากไม่มี backend จริง
- ห้ามอ้าง PDPA, ISO, encryption, SLA, SSO, trial หรือราคาเป็นข้อเท็จจริงโดยไม่มีหลักฐานและการอนุมัติ

## Content principles

- ยืนยันการทำงานด้วยข้อความที่ตรงกับผลจริง
- อธิบายการสุ่มและการตรวจคะแนนให้ครูเข้าใจและตรวจสอบได้
- บอกชัดว่าส่วนใดตรวจอัตโนมัติและส่วนใดต้องให้ครูตรวจ
- หลีกเลี่ยงข้อความที่ทำให้ครูเชื่อว่าระบบตัดสินนักเรียนแทนครู
- ข้อมูลสุขภาพ ครอบครัว และความเครียดไม่ควรปรากฏใน dashboard รวมโดยไม่จำเป็น
