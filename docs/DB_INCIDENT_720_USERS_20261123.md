## สิ่งที่แก้

1. **จำกัดเวลารอ:** อ่าน Data API ไม่เกิน 20 วินาที และตรวจผู้ใช้กับ Auth ไม่เกิน 10 วินาที ดู `lib/supabase/request-timeout.ts`
2. **ไม่ลองอ่านซ้ำเมื่อหมดเวลา:** `postgrest-js` ลอง GET ซ้ำได้ 3 ครั้งเมื่อเครือข่ายล้ม timeout จึงส่งเป็น `AbortError` เพื่อไม่เพิ่มโหลดให้ฐานข้อมูลที่กำลังเต็ม
3. **ไม่แตะคำขอที่ยกเลิกไม่ปลอดภัย:** การเขียน, RPC, การหมุน refresh token และ Storage ยังใช้ขีดจำกัดเดิม เพราะฝั่งเซิร์ฟเวอร์อาจบันทึกสำเร็จไปแล้ว
4. **อ่านโปรไฟล์ไม่สำเร็จไม่เท่ากับไม่มีโปรไฟล์:** สร้างโปรไฟล์อัตโนมัติเฉพาะเมื่อฐานข้อมูลยืนยันว่าไม่มีแถวจริง
5. **Auth ล่มไม่เท่ากับยังไม่ล็อกอิน:** ผู้ใช้เห็นหน้าให้ลองใหม่แทนการถูกเด้งไป `/login` ครอบคลุมหน้าหลัก หน้าทำข้อสอบ การตรวจเครื่อง SEB คลังฝึก หน้าเชิญ และหน้าผู้ดูแล
6. **คอลัมน์ SEB ที่ Production ยังไม่มี:** การบันทึกสถานะคุมสอบและการแนบวิธีทำใช้ fallback เดียวกับจุดอื่น ข้อสอบที่บังคับ SEB ยังปฏิเสธการเข้าถึงเมื่อไม่มีคอลัมน์นี้

ไม่มี migration ไม่มีการเปลี่ยน RLS และไม่มีการแก้ข้อมูลใน Production

## ความเสี่ยงที่ 720 คน

- นักเรียนที่ไม่มีข้อมูลเลยเปิด `/dashboard` หนึ่งครั้งใช้ 7 คำขอไปยัง Supabase ผู้ใช้จริงจะใช้มากกว่านี้
- ถ้า 720 คนเปิดภายใน 1 นาที จะมีอย่างน้อยราว 84 คำขอต่อวินาที
- เหตุการณ์วันนี้เริ่มล้มในช่วงเฉลี่ยราว 36 คำขอต่อวินาที จึงคาดว่า **Nano ปัจจุบันไม่พอสำหรับ 720 คนที่เข้าพร้อมกัน** นี่เป็นการประเมิน ไม่ใช่ผลวัดจริง
- โค้ดชุดนี้ทำให้ระบบล้มอย่างปลอดภัยและฟื้นง่ายขึ้น แต่ไม่ได้เพิ่มกำลังของฐานข้อมูล

## สิ่งที่ยังไม่ได้ตรวจ

- ยังไม่ได้ทดสอบ 720 คนบนระบบจริง Staging เป็น Nano เท่ากับ Production จึงเหมาะกับการวัด แต่ต้องมีสิทธิ์ผ่าน Vercel Deployment Protection และบัญชีสังเคราะห์ 720 บัญชี ชุดทดสอบเดิมจำกัดไว้ 81 บัญชี
- ยังไม่ทราบคอขวดที่แท้จริงของเหตุการณ์ เพราะกราฟ CPU, Disk IO และ connection ย้อนหลังโหลดไม่ขึ้น
- ยังไม่ได้ปล่อยโค้ดนี้ขึ้น Staging หรือ Production
