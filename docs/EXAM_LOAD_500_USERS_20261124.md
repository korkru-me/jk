# ลดภาระระบบล็อกอินและจำลองสอบ 500 คน — 24 พฤศจิกายน 2026

ต่อจาก [DB_INCIDENT_720_USERS_20261123.md](DB_INCIDENT_720_USERS_20261123.md) เอกสารนี้แยกสิ่งที่วัดได้ในเครื่อง ออกจากข้อสรุปเกี่ยวกับ Production

## ปัญหาที่แก้

ระหว่างสอบ 23 พ.ย. เว็บเรียก `supabase.auth.getUser()` ทุกครั้งที่เปิดหน้า บันทึกคำตอบ และส่ง heartbeat คุมสอบทุก 15 วินาที แต่ละครั้งคือคำขอหนึ่งครั้งไปยัง Auth server ซึ่งต้องอ่าน Postgres อีกที log วันนั้นมี `/auth/v1/user` ตอบ 504 หลายร้อยครั้ง และ `/auth/v1/token` (การล็อกอิน) ล้มไปพร้อมกัน นักเรียนจึงค้างที่หน้า login

## สิ่งที่เปลี่ยน

- `lib/auth/session-user.ts` เพิ่ม `getSessionUser()` ที่ใช้ `auth.getClaims()` เพื่อตรวจลายเซ็น ES256 และวันหมดอายุของ access token ในเครื่อง ด้วยกุญแจสาธารณะของโปรเจกต์ โหลดกุญแจหนึ่งครั้งต่อ server instance ทุก 10 นาที และคำขอที่มาพร้อมกันใช้การดาวน์โหลดเดียวกัน
- `getAuthUser()` ของทุกหน้าใน `app/(app)` กับ server action ฝั่งนักเรียน/ครูส่วนใหญ่ใช้วิธีนี้
- ยังใช้ `getUser()` เหมือนเดิมในส่วนรหัสผ่าน อีเมล บัญชี Google องค์กร/สมาชิก รหัสออก SEB และหน้าผู้ดูแล/ผู้ดูแลระบบสูงสุด
- token หมดอายุหรือผิดรูปแบบยังถือว่าไม่ได้ล็อกอินเหมือนเดิม และ Auth ล่มยังแสดงหน้าให้ลองใหม่ ไม่เด้งไป login
- ข้อแลกเปลี่ยน: token ที่ถูกเพิกถอนจากการออกจากระบบยังใช้ได้ในเส้นทางเหล่านี้จนหมดอายุ (ไม่เกิน 1 ชั่วโมง) RLS และการตรวจสิทธิ์ในฐานข้อมูลไม่เปลี่ยน ไม่มี migration
- Production และ Staging ใช้กุญแจ ES256 ทั้งคู่ (ตรวจ `/.well-known/jwks.json` เมื่อ 24 พ.ย.)

## จำลองสอบ 500 คนในเครื่อง

วิธีทดสอบ: `next start` หนึ่ง process บน Mac เครื่องเดียว ต่อ Supabase จำลองบน `127.0.0.1` ที่ตอบช้า 20–80 ms ต่อคำขอ ใช้ token ES256 จริงที่เซ็นด้วยกุญแจที่สร้างขึ้นสำหรับการทดสอบ นักเรียนสังเคราะห์ 500 คนเปิด `/dashboard` และหน้าทำข้อสอบพร้อมกัน จากนั้นสอบ 2 นาที โดยส่ง heartbeat ทุก 15 วินาที และบันทึกคำตอบประมาณทุก 10 วินาที ผ่าน Server Action จริงของ build ไม่แตะ Production, Staging, Vercel หรือข้อมูลจริง

| | โค้ด Production ปัจจุบัน (`2bf2dc3`) | โค้ดใหม่ |
|---|---:|---:|
| เปิดหน้า (1,000 ครั้ง) | สำเร็จ 1,000 | สำเร็จ 1,000 |
| heartbeat | สำเร็จ 3,964 · p50 157 ms | สำเร็จ 3,978 · p50 106 ms |
| บันทึกคำตอบ | สำเร็จ 5,927 · p50 156 ms | สำเร็จ 5,922 · p50 105 ms |
| คำขอ `/auth/v1/user` | **10,891 (78/วินาที)** | **0** |
| ดาวน์โหลดกุญแจ JWKS | 0 | 1 |
| คำขอทั้งหมดไป Supabase | 36,673 (263/วินาที) | 25,801 (186/วินาที) |

เวลาในตารางใช้เทียบโค้ดเดิมกับโค้ดใหม่เท่านั้น ไม่ใช่เวลาที่ผู้ใช้จริงจะได้รับ เวลาเปิดหน้าขึ้นกับ Mac เครื่องเดียวที่รันทั้ง 500 คน จึงไม่ใช้เทียบ

## ตรวจบน Staging — 24 พฤศจิกายน 2026

PR #165 merge เข้า `staging` เป็น `5ad6e37` Vercel deploy สำเร็จ ตรวจที่ `https://staging.korkru.com` (เห็นป้าย STAGING) ด้วยบัญชีสังเคราะห์ครู 1 นักเรียน 1 ที่สร้างเพื่อรอบนี้

- ครู: สมัคร ยืนยันอีเมลผ่าน SQL editor ของ Staging (`dyuxkrzeveknqgtuzpbh`) เฉพาะสองอีเมลนี้ ล็อกอิน เปิดหน้าหลัก สร้างห้องเรียน โจทย์ถูก-ผิด 1 ข้อ และข้อสอบ 10 นาทีที่เปิดห้องคุมสอบสด แล้วเผยแพร่ได้ ออกจากระบบแล้ว `/login` แสดงฟอร์มตามปกติ
- นักเรียน: ล็อกอิน เข้าห้องด้วยรหัส เห็นข้อสอบ เข้าห้องสอบ สถานะ "เชื่อมต่อคุมสอบแล้ว" ตอบ 1/1 บันทึกอัตโนมัติ ส่ง และได้หน้าผล 1/1 ทุก Server Action ตอบ 200
- Log ของ API Gateway ฝั่ง Staging ตั้งแต่นักเรียนล็อกอิน (08:22:40 UTC) จนส่งข้อสอบ: `/auth/v1/user` **0** ครั้ง, `jwks.json` 2 ครั้ง, `/auth/v1/token` 1 ครั้ง (การล็อกอิน) ส่วนบันทึกคำตอบ (PATCH `submission_answers` 204) และ heartbeat (`record_exam_proctor_signal` 200) ปรากฏตามปกติ
- ช่วงครูสร้างงานยังมี `/auth/v1/user` จาก `getMyOrgId()` ใน `lib/actions/org.ts` ซึ่งตั้งใจคงไว้ในรอบนี้ เป็นงานครูปริมาณน้อย ไม่อยู่บนเส้นทางทำข้อสอบ
- ลบข้อมูลสังเคราะห์ครบใน transaction เดียว (ข้อสอบ submission โจทย์ ห้อง องค์กรส่วนตัว และบัญชี Auth) ตรวจซ้ำเหลือ 0 ทุกตาราง

## สิ่งที่ผลนี้บอกและไม่บอก

- บอก: โค้ดใหม่ไม่เรียก Auth server ระหว่างสอบเลย คำขอไป Supabase ลดลงราว 30% และทุก heartbeat/การบันทึกเร็วขึ้นหนึ่ง round trip
- ไม่บอก: Production รับ 500 คนได้หรือไม่ ส่วนที่เหลือราว 186 คำขอ/วินาทีเป็นการอ่าน/เขียนฐานข้อมูลจริง (heartbeat อ่าน 1 + RPC 1, บันทึกคำตอบ อ่าน 1 + เขียน 1, เปิดหน้าราว 10) เหตุการณ์ 23 พ.ย. เริ่มล้มที่เฉลี่ยราว 36 คำขอ/วินาทีบน Nano จึงคาดว่า **500 คนพร้อมกันยังต้องอัปเกรด Compute** นี่เป็นการประเมิน ไม่ใช่ผลวัด
- การพิสูจน์กำลังจริงต้องทดสอบไล่ระดับบน Staging (Nano เท่ากับ Production) ด้วยบัญชีสังเคราะห์

## งานต่อที่ลดภาระได้อีก

- รวมการอ่าน submission ก่อน heartbeat เข้าไปใน RPC `record_exam_proctor_signal` (ลด 1 คำขอทุก 15 วินาทีต่อคน) ต้องคงการตรวจ SEB เดิมและต้องมี migration
- ทดสอบไล่ระดับบน Staging 100 / 250 / 500 คน แล้วหยุดทันทีเมื่อ error หรือเวลาตอบเกินเกณฑ์
