# Feature status

ตรวจจาก repository: 3 กันยายน 2026

## วิธีอ่านสถานะ

- **มีโค้ดรองรับ** — พบ route, UI, action และ/หรือ migration สำหรับเส้นทางจริง แต่ยังไม่เท่ากับ production-ready
- **บางส่วน** — มีการทำงานจริง แต่ยังมีช่องว่างหรือส่วนจำลองที่กระทบการใช้งานครบเส้นทาง
- **ต้นแบบ/ข้อมูลจำลอง** — UI มีไว้สาธิตหรือใช้ค่าคงที่ ไม่ใช่ข้อมูลธุรกิจจริง
- **วางแผน** — อยู่ในทิศทางผลิตภัณฑ์แต่ยังไม่ใช่งานระยะปัจจุบัน

> โจทย์ประเภท "ส่งไฟล์งาน" (`file_upload`) เคยใช้งานบน production ไม่ได้จนถึง 23 สิงหาคม 2026 เพราะ `20260726120000_file_upload_question_type.sql` ไม่เคยถูก apply — ทั้งที่โค้ดฝั่งแอปรองรับครบมาตั้งแต่กรกฎาคม ตอนนี้รันแล้ว: enum `question_type` มีค่า `'file_upload'` และ bucket `submission-files` มีอยู่จริง (public, จำกัด 10 MB, รับ png/jpeg/webp/pdf) ยังไม่ได้ทดสอบเส้นทางอัปโหลดจริงจากฝั่งนักเรียน

มี automated test (`npm test`) ครอบคลุมเฉพาะโมดูลที่เป็น pure logic — evaluator, การให้คะแนน และตัวช่วยข้อความ ยังไม่มีอะไรทดสอบ Supabase, server action หรือ browser การยืนยันฐานข้อมูลที่ deploy จริงจะระบุแยกไว้เฉพาะฟีเจอร์ที่ตรวจแล้ว และทุกสถานะยังต้องผ่าน end-to-end กับ authorization testing ก่อนเปลี่ยนเป็น “พร้อมใช้จริง”

## MVP core

### Authentication — บางส่วน

- มี email/password signup/login สำหรับ `teacher` และ `student`; หน้าสมัครถามเฉพาะประเภทบัญชี ชื่อที่ใช้แสดง อีเมล และรหัสผ่าน ไม่ถามโรงเรียนหรือกลุ่มสาระ กลุ่มสาระเดิมใน `users.subject_group`/`subject_group_other` ยังคงไว้กับข้อมูลเก่าแต่ไม่เก็บเพิ่มตอนสมัคร เพราะอนุมานความสนใจจริงจากวิชาหรือโจทย์ที่ครูสร้างได้ภายหลัง
- Google OAuth รายใหม่ต้องผ่าน `/complete-profile` เพื่อยืนยันชื่อและประเภทบัญชีครั้งเดียว จึงไม่ถูกกำหนดเป็นครูหรือนักเรียนจากค่า default ของ trigger; protected layout กันบัญชีที่ยังไม่จบขั้นตอนนี้ออกจากหน้าหลัก ส่วน admin เดิมไม่ถูกบังคับเปลี่ยน role
- Magic link ใช้ได้เฉพาะบัญชีที่มีอยู่ (`shouldCreateUser: false`) และตอบข้อความแบบเดียวกันไม่ว่าอีเมลมีบัญชีหรือไม่ เพื่อไม่ให้หน้า login กลายเป็นทางสมัครที่ข้ามการเลือกบทบาทหรือเปิดเผยรายชื่อบัญชี
- เส้นทางลืมรหัสผ่านครบแล้ว: ส่ง recovery link ผ่าน `/auth/callback`, แลก code เป็น session, เปิด `/reset-password`, ตรวจความแข็งแรง/การยืนยันซ้ำฝั่ง client และ server แล้ว global sign-out หลังเปลี่ยนสำเร็จ
- migration `20260901091339_restore_auth_user_provisioning.sql` คืน invariant ที่บัญชีใหม่ทุกคนต้องมี personal organization หลัง `20260823081036` เคยเขียนทับ `handle_new_user()` จนส่วนสร้าง organization หาย และ backfill เฉพาะบัญชีที่ตกหล่นแบบ idempotent
- apply migration นี้กับฐาน Production แล้วเมื่อ 1 กันยายน 2026; migration ledger ฝั่ง local/remote ตรงกันและ `supabase db lint --linked --level error` ไม่พบ error
- มี session refresh และ protected layouts
- ยังไม่ได้ยืนยันการส่งอีเมลจริงกับ production SMTP หรือทดสอบ Google/recovery end-to-end ใน browser ด้วยบัญชีทดสอบ
- authority ระหว่าง system admin, organization admin และ super admin ยังต้องสรุป

### คลังโจทย์ — มีโค้ดรองรับ

- มี create/edit/list/preview/delete, tags, categories, visibility และ sharing
- **หน้า "ดูตัวอย่าง" ของโจทย์มีทางเข้าหน้าตรวจของครูแล้ว** (`components/questions/teacher-grading-preview.tsx`) — ปุ่ม "ดูหน้าที่ครูตรวจ" สลับตัวอย่างทั้งหน้าไปเป็นการ์ดรายข้อแบบเดียวกับ `/submissions/[id]` (วงกลมสถานะ ป้ายคะแนน คำตอบเทียบเฉลย ช่องรูปวิธีทำ) โดยเอาคำตอบที่ครูเพิ่งลองตอบมาแสดง · **ต้องลองตอบก่อน** ไม่งั้นขึ้น toast ให้ตอบก่อน เพราะหน้าตรวจที่ไม่มีคำตอบไม่ได้บอกอะไรเลย · **ป้ายคะแนนกดแก้ได้จริงในหน้านี้** (`EditableScore` ท่าเดียวกับ `ScoreEditor` ของหน้าตรวจจริง รับทศนิยม ตรวจช่วง 0–คะแนนเต็ม ข้อความ error เดียวกัน) เพราะการให้คะแนนใหม่คือสิ่งเดียวที่ครู "ทำ" ที่หน้าตรวจ ป้ายที่กดไม่ได้จึงไม่ได้สอนอะไร · เก็บค่าไว้ในหน่วยความจำของหน้าเท่านั้น ไม่มี submission ให้บันทึกลง และข้อความท้ายการ์ดบอกตรง ๆ ว่าของจริงอยู่ที่หน้าผลการส่งของนักเรียน
  - **Enter/Escape ในช่องคะแนนถูก `stopPropagation`** เพราะช่องนี้อยู่ใน Dialog — Escape ที่ลอยไปถึง Dialog แปลว่า "ปิดตัวอย่างทั้งหน้า" คำตอบกับรูปที่ครูเพิ่งลองตอบจะหายไปด้วย ทั้งที่ครูตั้งใจแค่ยกเลิกการพิมพ์คะแนน (เจอตอนทดสอบจริง) · `ScoreEditor` ตัวจริงไม่มีปัญหานี้เพราะไม่ได้อยู่ใน Dialog
  - **ขึ้นเฉพาะโจทย์ที่ครูกลับมายุ่งด้วยได้จริง**: เติมคำตอบตัวเลข (ระบบตรวจครบแล้ว แต่ครูเปิดดูรูปวิธีทำและแก้คะแนนได้) · อัตนัย (ไม่ตรวจเลย รอครูเสมอ) · ส่งไฟล์งาน (ให้คะแนนเต็มอัตโนมัติเมื่อมีไฟล์ ครูเปิดไฟล์แล้วปรับเอง) · เติมคำในช่องว่าง **เฉพาะเมื่อมีช่องชนิด `text`** · ถูก-ผิดที่ `explanation_mode !== 'none'` (เหตุผลไม่มีเฉลยให้เทียบ) · โจทย์ผสมที่มีข้อย่อยเติมคำชนิด `text` — เงื่อนไขเดียวกับที่ `gradeAnswer` ปล่อย `is_correct` เป็น null หรือให้คะแนนไปก่อนแล้วครูค่อยปรับ ชนิดที่ตรวจจบอัตโนมัติ (ปรนัย จับคู่ เรียงลำดับ เติมคำที่เป็นคำตอบตายตัวล้วน) ไม่มีปุ่มนี้
  - **ตัวอย่างของเติมคำตอบตัวเลขมีช่องแนบรูปวิธีทำแล้ว และแนบไฟล์จริงจากเครื่องได้** พร้อมคำอธิบายว่ามันคืออะไรและสวิตช์อยู่ที่ไหน — ครูหาสวิตช์นี้ในหน้าสร้างโจทย์ไม่เจอ เพราะมันอยู่ที่ขั้นตั้งค่าของหน้าสร้างงาน (ดูหัวข้องานและข้อสอบ) · ใช้ `WorkImageUpload` กับ `FileSubmissionUpload` **ตัวเดียวกับที่นักเรียนใช้** ครูจึงเห็นของจริง ไม่ใช่ของที่วาดให้เหมือน และรูป/ไฟล์ที่แนบไปโผล่ในหน้าตรวจจำลองเหมือนตอนตรวจงานจริง
  - **แต่ไม่มีอะไรขึ้น storage — `localOnly`** ตัวอัปโหลดทั้งสองรับ prop นี้แล้ว เปิดเมื่อไรจะถือไฟล์ไว้เป็น `URL.createObjectURL` ของแท็บนั้นแทนการอัป และคืน object URL ตอนกดเอาออก/ปิดตัวอย่าง/กดสุ่มโจทย์ใหม่ · เหตุผลที่ไม่เลือกทาง "อัปจริงแล้วค่อยตามลบ": ตัวอย่างไม่มี submission ให้ผูกไฟล์ด้วย ไฟล์จึงเป็นกำพร้าตั้งแต่วินาทีแรก และการตามลบไม่มีวันครบ — ปิดแท็บ เน็ตหลุด หรือเบราว์เซอร์ถูกฆ่าระหว่างนั้น ไฟล์ก็ค้าง ต้องรอให้ครูไปกดกวาดที่ ตั้งค่า → พื้นที่จัดเก็บไฟล์ ซึ่งเว้นไฟล์อายุไม่ถึง 7 วันไว้เสมอ
  - **`/assignments/[id]/preview` เคยอัปไฟล์จริงทิ้งไว้ทุกครั้งที่ครูลองทำข้อสอบตัวเอง — แก้แล้วด้วย prop เดียวกัน** หน้านั้นใช้ `ExamClient` ตัวจริง `previewMode` กันแค่การเขียน `submission_answers` (`if (previewMode) return` ก่อน `saveWorkImage`) แต่ไฟล์ขึ้น `work-images`/`submission-files` ไปแล้วตั้งแต่ก่อนหน้านั้น และ preview ไม่สร้าง submission จึงไม่มีแถวไหนอ้างถึงตลอดกาล · ตอนนี้ `MultiPartAnswerInput` กับ `FileUploadAnswerInput` ส่ง `localOnly={previewMode}` ต่อลงไป เส้นทางของนักเรียนไม่เปลี่ยน (`localOnly` เป็น undefined = โค้ดเดิมทุกบรรทัด)
  - **ตอบเป็นตัวอักษรแล้วตัวอย่างเงียบ — แก้แล้ว** `evaluateStudentAnswer` คืน `null` เมื่อ parse ไม่ได้ และ `checkWritten` เดิมตีความว่า "ตัดสินไม่ได้" จึงไม่ขึ้นทั้งกากบาทและเฉลย เหลือแค่บรรทัดสรุป "❌ ผิด" ลอย ๆ ทั้งที่ `gradeAnswer` ของจริงแปลงเป็น `NaN` แล้วตัดสินว่าผิด · ตอนนี้ขึ้น "✗ คำตอบไม่ใช่ตัวเลข · เฉลย: …" และเก็บ `null` ไว้เฉพาะกรณีที่สูตรของครูเองคำนวณไม่ได้ ซึ่งแสดงเป็น "⚠ ตรวจไม่ได้"
  - **ตัวอย่างใช้ค่าคลาดเคลื่อนจริงแล้ว** เดิมมีสูตรของตัวเองที่ตรึงไว้ที่ ±1% คำว่า "ถูก" ในตัวอย่างจึงไม่ได้แปลว่าจะถูกตอนตรวจจริง · ตอนนี้เรียก `gradeValue` ตัวเดียวกับ `gradeAnswer` (export เพิ่มจาก `lib/assignment-attempt.ts`) และรับ tolerance ตามลำดับเดียวกัน: ของข้อย่อย → ของทั้งโจทย์ → 0.1
  - **ข้อย่อยเติมคำของโจทย์ผสมที่ไม่มี `[คำตอบ]` แล้วไม่มีช่องกรอก — แก้แล้ว** เดิมทั้งหน้าตัวอย่างและหน้าทำข้อสอบจริงคืน `<RichText>` เปล่า ๆ เมื่อ `splitAnswerBlankHtml` เป็น null นักเรียนจึงตอบข้อย่อยนั้นไม่ได้ ทั้งที่ `naturalMaxScore('composite', …)` ยังนับข้อย่อยนั้นเป็นคะแนนเต็ม — เสียคะแนนให้ช่องที่ครูไม่เคยให้มา · ตอนนี้ทั้งสองที่ (`components/exam/exam-client.tsx`, `components/questions/question-preview-content.tsx`) เรนเดอร์ช่องกรอก/ดรอปดาวน์ **ไว้บรรทัดถัดจากข้อความ** แทนการแทรกในบรรทัด ส่วนข้อย่อยที่มี `[คำตอบ]` ยังแทรกในบรรทัดเหมือนเดิม · `compositeAnswerable` จึงเลิกเช็ค marker แล้ว เพราะข้อย่อยเติมคำที่มี `blanks[0]` ตอบได้ทุกกรณี
    - **ไม่ได้แตะการให้คะแนน** — `COMP:` เก็บเฉลยจาก `blanks[0]` ไม่ได้อ่านข้อความข้อย่อยเลย marker จึงไม่เคยมีผลต่อคะแนน การแก้นี้เพิ่มเฉพาะตัวรับคำตอบที่หายไป · ตรวจฐานข้อมูลก่อนแก้: โจทย์ผสมที่บันทึกไว้มี 10 ข้อ ทุกข้อเป็น "ถูก-ผิดแบบชุด" (ข้อย่อย `true_false` ล้วน) **ยังไม่มีข้อย่อยเติมคำในฐานข้อมูลเลยสักข้อ** ผลคะแนนเก่าจึงไม่มีทางเปลี่ยน
    - **หน้าสร้างโจทย์กันไว้อยู่แล้ว** — `composite-form.tsx` บังคับ `[คำตอบ]` ให้ครบ 1 จุดตั้งแต่ commit แรกของโจทย์ผสม ที่ยังเข้ามาได้คือทางที่ไม่ผ่านฟอร์ม: การนำเข้าไฟล์ส่ง `extra_data` ผ่านตรง ๆ (`lib/question-portable.ts`) · จงใจไม่เพิ่ม validation ฝั่ง server เพราะ fallback ทำให้โจทย์รูปนั้นใช้งานได้แล้ว การปฏิเสธจะกลายเป็นการบล็อกไฟล์ที่นำเข้าได้อยู่

- **เลือกลำดับการเรียงได้ทั้งคลังของฉันและโจทย์ที่แชร์ในทีม** — เมนูข้างช่องค้นหาเรียงได้ตาม **วันที่สร้าง · วันที่แก้ไขล่าสุด · ชื่อโจทย์ · วิชา · หมวดหมู่ · ระดับความยาก · ประเภทโจทย์ · จำนวนแท็ก** และเฉพาะคลังของฉันอีก 4 แบบจากสถิติรายข้อ (**ใช้ในข้อสอบบ่อย · ความยากจริงจากคะแนน · อำนาจจำแนก · ใช้ครั้งล่าสุด**) และปุ่มข้างเมนูสลับหัวท้ายของแต่ละแบบ (ป้ายเปลี่ยนตามเรื่องที่เรียง — "ใหม่ → เก่า" กับ "ก → ฮ") กติกาอยู่ที่ `lib/question-sort.ts` (มีเทสต์) และทุก query ที่เรียงโจทย์เรียกผ่าน `applyQuestionSort` ตัวเดียว เพราะ query ที่นับกับ query ที่อ่านแถวต้องเรียงเหมือนกัน ไม่งั้นการแบ่งหน้าจะซ้ำข้อและตกข้อ
  - ลำดับอยู่ใน URL (`?sort=` / `?dir=` และ `?tsort=` / `?tdir=` ของรายการทีม) เหมือนคำค้นและตัวกรอง จึงส่งเป็นลิงก์และรอดจากการ refresh ได้ ค่าที่ตรงกับค่าเริ่มต้น (ใหม่สุดก่อน) ไม่ถูกเขียนลง URL ลิงก์เก่าทุกอันจึงยังเปิดได้รายการเดิม · เปลี่ยนลำดับแล้วกลับไปหน้า 1 ของรายการนั้นเท่านั้น แท็บ "ทั้งหมด" แสดงสองรายการพร้อมกันและแบ่งหน้าแยกกัน · ทุก query ตัดสินข้อที่เท่ากันด้วย `id` ทิศเดียวกับคีย์ที่เรียง เพราะไม่มีคอลัมน์ไหนที่เรียงแล้วไม่ซ้ำ
  - เรียงในโหมดค้นหาได้ด้วย โดยเรียงภายในแต่ละกลุ่ม (พบจากแท็ก → ชื่อโจทย์ → เนื้อหาโจทย์) ลำดับของกลุ่มยังคงเดิม เพราะกลุ่มคือลำดับความตรงของคำค้นอยู่แล้ว
  - **รายการทีมมีสองแบบเพิ่ม: ชื่อผู้สร้าง และทีมเจ้าของโจทย์** (แบบหลังโผล่เฉพาะครูที่อยู่หลายทีม) เรียงด้วย `order=users(full_name)` / `order=organizations(name)` ซึ่งเป็นการเรียงแถวแม่ตามตารางที่ join มาแบบ to-one — ทดสอบกับฐานข้อมูลจริงแล้วว่า PostgREST เรียงให้จริง ไม่ใช่รับคำสั่งแล้วเมิน สองแบบนี้ใช้กับคลังของฉันไม่ได้ (query นั้นไม่ได้ join) `readQuestionSort` จึงปฏิเสธคีย์เหล่านี้เมื่ออ่านจากพารามิเตอร์ของคลังของฉัน
  - **"วิชา" กับ "หมวดหมู่" คนละอย่างกัน และเรียงได้ทั้งคู่** — วิชาคือคอลัมน์ `subject` บนแถว (ฟิสิกส์ · โลก ดาราศาสตร์ และอวกาศ) ส่วนหมวดหมู่คือป้ายสีม่วงบนการ์ด `question_categories(name)` ซึ่งเป็นหัวข้อย่อยภายในวิชา เรียงแบบหลังใช้กลไกเดียวกับ "ชื่อผู้สร้าง" คือเรียงแถวแม่ตามตารางที่ join มา และใช้ได้ทั้งสองรายการเพราะทั้งคู่ select `question_categories` อยู่แล้ว **หมายเหตุ: การ์ดยังไม่ได้แสดง `subject`** เรียงตามวิชาจึงจัดกลุ่มถูกแต่ผู้ใช้ไม่เห็นชื่อกลุ่ม
  - **"จำนวนแท็ก"** เรียงด้วยคอลัมน์ generated `questions.tag_count` (`coalesce(array_length(tags,1),0)` แบบ STORED) เพราะ PostgREST เรียงตามคอลัมน์ ไม่ใช่ตาม expression — ฐานข้อมูลดูแลค่าให้เอง ไม่มี state ให้หลุดจากกันเหมือน counter ที่ใช้ trigger ทิศ "ยังไม่มีแท็กก่อน" คือรายการงานสำหรับไล่ติดแท็ก (คลังจริงตอนนี้ 41 จาก 888 ข้อเท่านั้นที่มีแท็ก) · การเพิ่มคอลัมน์นี้ต้องแก้ `questions_touch_updated_at` ให้ตัด `tag_count` ออกจากการเทียบด้วย เพราะ Postgres เติมค่า generated column หลัง BEFORE trigger ทำงาน ถ้าไม่ตัด การเขียน fingerprint จะกลายเป็น "แก้ไข" ทุกครั้งและประทับ `updated_at` ทั้งคลัง
  - **ยังไม่มี "เรียงตามระดับชั้น"** — `questions.grade_level` เป็น NULL ทั้ง 888 แถวและไม่มีฟอร์มไหนเขียนค่าลงไป (มีแต่ทางนำเข้าไฟล์) เมนูที่เรียง NULL เท่ากันหมดไม่ได้ทำอะไรเลย จึงยังไม่ใส่จนกว่าจะมีข้อมูลจริง
  - **4 แบบที่มาจากสถิติรายข้อจัดอันดับในหน่วยความจำ ไม่ใช่ในฐานข้อมูล** — p อำนาจจำแนก และ "ใช้ในกี่ชุดสอบ" ไม่ใช่คอลัมน์ แต่คำนวณจากคำตอบที่นักเรียนส่งจริง และกติกาการคำนวณอยู่ที่ `computeQuestionStats` การเขียนสูตรเดิมซ้ำเป็น SQL เพื่อให้ `order=p_value` ใช้ได้ เท่ากับมีสองที่ที่คำนวณ item analysis และวันที่มันไม่ตรงกัน รายการจะถูกเรียงด้วยตัวหนึ่งแต่ติดป้ายด้วยอีกตัวหนึ่ง จึงใช้วิธี: อ่าน **id อย่างเดียว** ของทุกข้อที่ตรงตัวกรอง (`buildQuery(group, 'ids')`) จัดอันดับด้วย `rankQuestionIds` แล้วดึงการ์ดเฉพาะ 24 id ที่ตกอยู่ในหน้านั้น — เหตุผลที่คลังต้องแบ่งหน้าในฐานข้อมูลคือน้ำหนักของแถว ไม่ใช่จำนวนของมัน · ข้อที่ยังไม่มีใครตอบถือว่า "ยังไม่ได้วัด" ไม่ใช่ศูนย์ จึงอยู่ท้ายรายการทั้งสองทิศ และเรียงกันเองแบบใหม่สุดก่อนตามเดิม · อำนาจจำแนกที่คำนวณไม่ได้ (ตอบน้อยเกินไป หรือคะแนนไม่มีความแปรปรวน) ก็นับเป็น "ยังไม่ได้วัด" เช่นกัน
  - สี่แบบนี้ไม่มีในรายการทีม เพราะสถิติที่ครูคนหนึ่งเห็นคือผลของนักเรียนตัวเอง การเรียงคลังของเพื่อนด้วย "ความยากจริง" จะเป็นการเรียงด้วยตัวเลขที่พูดถึงห้องเรียนของเรา ไม่ใช่โจทย์ของเขา
  - `fetchQuestionStats` รับ `'all'` เพิ่ม สำหรับตอนจัดอันดับ (RLS จำกัดให้เหลือเฉพาะงานที่ครูคนนั้นสร้างอยู่แล้ว การไล่ระบุ id ทีละ 200 จึงเป็นการส่ง URL ยาว 5 รอบไปเอาแถวชุดเดิม) และตอนนี้อ่านผ่าน `fetchAllRows` ทั้งสองทาง — เดิมไม่ได้แบ่งหน้า ห้องเรียนชุดใหญ่ที่คำตอบเกิน 1,000 แถวต่อ 1 slice จะถูก PostgREST ตัดทิ้งเงียบ ๆ แล้วคำนวณ p จากหลักฐานแค่บางส่วน
  - **ยังไม่มี "เรียงตามจำนวนข้อย่อย" และ "โจทย์ซ้ำ"** — จำนวนข้อย่อยของโจทย์หลายขั้นตอนนับจากแถวลูกในกลุ่ม และกติกาการนับอยู่ที่ `lib/question-parts.ts` ที่มีเทสต์ การป้อนให้มันต้องดึง jsonb ทั้งคลัง ซึ่งเป็นสิ่งที่ `fetchSubQuestionCounts` ตั้งใจเลี่ยง ส่วนโจทย์ซ้ำ คลังจริงตอนนี้มี 0 กลุ่ม เรียงแล้วเสมอกันหมด
  - ทางเดียวที่เรียงในฐานข้อมูลไม่ได้คือ fallback ของรายการทีมตอนที่รายการแชร์ยาวเกินกว่าจะแบ่งหน้าใน URL เดียว — มันรวมผลสอง query ผ่าน Map ซึ่งทิ้งลำดับที่ฐานข้อมูลส่งมา จึงเรียงในหน่วยความจำด้วย `compareQuestions` แทน ตัวนี้เป็นฝาแฝดของ `applyQuestionSort` (คีย์เดียวกัน · ค่าว่างอยู่ล่างสุดทั้งสองทิศ · ตัดสินเสมอด้วย `id`) และเทียบข้อความไทยด้วย `localeCompare(…, 'th')` ซึ่งให้ลำดับตรงกับ collation ของฐานข้อมูล
- คลังแฟ้มโจทย์ใช้ session/query ชุดเดียวของหน้าและตรวจจำนวนโจทย์ที่ยังมีอยู่ของทุกชุดใน query เดียว
- **ท้ายหน้าคลังแฟ้มโจทย์ ต่อจากแฟ้มทุกใบ มีตัวเรียกดูโจทย์ทั้งคลัง** เปิดมาที่ "โจทย์ที่ยังไม่อยู่ในแฟ้มใด" ซึ่งเป็นงานค้างของหน้านี้ สลับได้ด้วยชิปสองอันกับเมนูแฟ้ม: **ยังไม่อยู่ในแฟ้มใด · โจทย์ทั้งหมด · ในแฟ้ม <ชื่อแฟ้ม>** (เมนู ไม่ใช่ชิปเรียง เพราะชื่อแฟ้มยาวและจำนวนแฟ้มไม่มีเพดาน) · "ยังไม่อยู่ในแฟ้มใด" นับทั้งแฟ้มของตัวเองและแฟ้มที่ทีมแชร์ (ข้อที่เพื่อนใส่แฟ้มไว้แล้วก็มีบ้านแล้ว) ส่วนเมนูแฟ้มมีเฉพาะแฟ้มของตัวเอง
  - **ค้นหาและเรียงลำดับด้วยกติกาเดียวกับหน้าโจทย์รายข้อ** — ช่องค้นหาเดียวจับ ชื่อ/เนื้อหา/แท็ก (`lib/question-search.ts`) และแยกผลเป็นกลุ่ม **พบจากแท็ก → พบจากชื่อโจทย์ → พบจากเนื้อหาโจทย์** พร้อมตัวเลือกดูเฉพาะกลุ่ม · เมนูเรียงลำดับมี 8 แบบที่ฐานข้อมูลเรียงได้ (`LIBRARY_QUESTION_SORT_KEYS`) **ไม่มี 4 แบบที่มาจากสถิติรายข้อ** เพราะต้องดึงสถิติทั้งคลังมาคำนวณ ซึ่งหน้านี้ไม่มีเหตุผลอื่นให้โหลด · สถานะทั้งหมดอยู่ใน URL (`qscope` `uq` `umatch` `usort`/`udir` `unfiled`) ลิงก์กลับมาที่เดิมได้ · ช่องค้นหาแฟ้มด้านบนของหน้ายังกรองเฉพาะชื่อแฟ้มเหมือนเดิม เป็นคนละช่องกัน
  - **วิธีหาคำตอบ** สมาชิกแฟ้มอยู่บนแถวของแฟ้ม ไม่ใช่บนตัวโจทย์ ค้นหากับเรียงลำดับเป็นคอลัมน์จึงอยู่ใน query ได้ แต่ "อยู่ในแฟ้มไหน" อยู่ไม่ได้ — และการไล่ระบุ id เป็นพันใน URL คือ 400 จาก PostgREST หน้าจึงขอ **id อย่างเดียว** ของทุกข้อที่ตรงคำค้นในลำดับที่เลือกไว้แล้ว (`fetchAllRows`) กรองสมาชิกภาพในหน่วยความจำ (กรองรายการไม่เคยสลับลำดับ) แล้วค่อยดึงการ์ดจริงเฉพาะ 24 id ของหน้านั้น — แพตเทิร์นเดียวกับที่หน้าคลังโจทย์ใช้ตอนเรียงด้วยสถิติ · ตอนค้นหาจะทำแบบนี้กลุ่มละครั้ง (แท็ก/ชื่อ/เนื้อหา) แล้วตัดหนึ่งหน้าต่อเนื่องข้ามกลุ่มด้วย `questionSearchGroupSlices`
  - **การ์ดเป็นการ์ดแบบเดียวกับหน้าโจทย์รายข้อ แต่เป็นฉบับ "ไว้ดู"** (`library-question-card.tsx`) — ป้ายครบชุด (หลายขั้นตอน · ความยาก · ชนิดโจทย์ · จำนวนข้อย่อย · วิชา · หมวดหมู่ · แฟ้มที่ข้อนั้นอยู่) ตัวอย่างเนื้อโจทย์ ปุ่มดูตัวอย่าง (modal ตัวเดียวกับหน้าคลัง) และ **แท็กที่เพิ่ม/ลบได้** ส่วนสถิติรายข้อ แก้ไข ลบ ทำสำเนา แชร์ รายงานปัญหา และสวิตช์บังคับแนบรูปวิธีทำ ถูกตัดออกทั้งหมด — หน้านี้ครูกำลังตัดสินใจว่าโจทย์ควรอยู่แฟ้มไหน ปุ่มที่เหลือคือสิ่งที่ทำให้หลุดจากงานนั้น (หรือทำโจทย์หาย) · ป้ายชื่อแฟ้มขึ้นเฉพาะตอนดู "ทั้งหมด" กับ "ในแฟ้ม X" เพราะในรายการที่ยังไม่มีแฟ้ม คำตอบเป็น "ไม่มี" เสมอ · ป้าย "ซ้ำกับอีก N ข้อ" ไม่มีที่นี่ ต้องไล่เทียบลายนิ้วมือเนื้อหาทั้งคลังเพิ่มอีกรอบ
  - **ติ๊กเลือกหลายข้อ × เพิ่มเข้าได้หลายแฟ้มพร้อมกัน** — ติ๊กที่การ์ด (หรือ "เลือกทั้งหน้า") แล้วแถบสรุปลอยขึ้นมาบอกจำนวนที่เลือกไว้ ข้ามหน้าได้ กดแล้วเปิด dialog ที่ **ติ๊กแฟ้มได้มากกว่าหนึ่งแฟ้ม** — จำเป็นเพราะโจทย์หลุดจากรายการ "ยังไม่อยู่ในแฟ้มใด" ทันทีที่เข้าแฟ้มแรก ถ้าไม่เลือกให้ครบตอนนั้นต้องไปตามใส่ทีหลังที่หน้าแก้ไขแฟ้ม · แฟ้มที่ถือโจทย์ที่เลือกไว้ครบทุกข้อแล้วจะบอกว่า "อยู่ในแฟ้มนี้แล้ว" · ยังไม่ให้เลือกลงแฟ้มย่อยจากตรงนี้ ไปจัดต่อที่หน้าแก้ไขแฟ้ม
  - **ตอนดู "ในแฟ้ม X" เอาโจทย์ออกจากแฟ้มนั้นได้** ทั้งรายข้อและหลายข้อ ถามยืนยันด้วย `ConfirmDialog` ที่ย้ำว่าโจทย์ยังอยู่ในคลังและงานที่มอบหมายไปแล้วไม่กระทบ (`removeQuestionsFromQuestionSet` ใช้ `removeQuestionsFromSet` ตัวเดิมใน `lib/question-set-sections.ts` โจทย์จึงหลุดจากแฟ้มย่อยตามไปด้วย)
  - เพิ่ม/เอาออกแล้วการ์ดหายจากรายการทันที (ซ่อนฝั่ง client) แล้ว `router.refresh()` ให้ตัวเลขกับหน้าถัดไปตรง — ยกเว้นตอนดู "โจทย์ทั้งหมด" ที่การ์ดยังอยู่ เพราะมันยังอยู่ในรายการนั้นจริง
  - `addQuestionsToSets(setIds, questionIds)` **ต่อ id เข้าท้าย `question_ids` เท่านั้น** ไม่แตะชื่อ คำอธิบาย การมองเห็น หรือการแชร์ (ต่างจาก `updateQuestionSet` ที่เขียนทับทั้งแฟ้ม ซึ่งแปลว่า client ต้องส่งสถานะทั้งก้อนกลับมา และอะไรที่ค้างอยู่จะถูกเขียนทับ) · ข้อที่แฟ้มมีอยู่แล้วถูกข้าม ไม่ใช่ใส่ซ้ำ · `sections` ถูก normalize ใหม่ให้แฟ้มย่อยยังถูกต้อง · ทั้งสอง action อ่านแฟ้มด้วย `.eq('created_by', user.id)` ทับ RLS อีกชั้น แฟ้มที่ไม่ใช่ของคนเรียกจึงตอบว่าไม่พบ แทนที่จะเงียบ
  - ชิ้นส่วนที่สองหน้าใช้ร่วมกันถูกย้ายออกมาแล้ว: `components/ui/pagination.tsx` · `components/questions/question-sort-control.tsx` · `components/questions/question-search-groups.tsx` · `components/questions/question-set-badges.tsx` · `lib/question-sub-counts.ts` — เพื่อให้ "พบจากแท็ก" กับลำดับของคีย์เดียวกันแปลว่าเรื่องเดียวกันทั้งสองหน้า
- รายการเลือกโจทย์ (ทั้งหน้าสร้างแฟ้มโจทย์และหน้าสร้างงาน) แสดงตัวอย่างเนื้อโจทย์ผ่าน `questionExcerpt` แล้ว โจทย์ที่นำเข้ามาพร้อม HTML จึงไม่โชว์แท็กดิบ และช่องค้นหาก็จับคู่กับข้อความที่ครูเห็นจริง ไม่ใช่ markup
- **กติกาการค้นหาโจทย์เป็นชุดเดียวกันทั้งเว็บ** อยู่ที่ `lib/question-search.ts` (มีเทสต์): ช่องค้นหาช่องเดียวจับคู่กับ **ชื่อโจทย์ · เนื้อโจทย์ (ตัด markup ด้วย `questionExcerpt`) · แท็ก** และแยกคำที่พิมพ์ด้วยช่องว่างแล้วต้องเจอครบทุกคำ ไม่สนลำดับ — พิมพ์ "พลัง" เจอทั้งข้อที่ชื่อ/เนื้อหามีคำนั้นและข้อที่ติดแท็ก "พลังงาน" เดิมต้องพิมพ์ตรงเป๊ะเป็นสายเดียวและไม่ค้นแท็กเลย
  - หน้าต่างเลือกโจทย์กรองในเบราว์เซอร์ด้วย `filterQuestions` ส่วนหน้าคลังโจทย์กรองในฐานข้อมูล (คลังใหญ่เกินกว่าจะส่งมาทั้งก้อน) ด้วย `questionSearchOrClauses` ซึ่งแปลงกติกาเดียวกันเป็น `or(...)` คำละชุดแล้ว AND กัน
  - แท็กแมตช์ได้เฉพาะทั้งค่า (`tags.ov`) ฝั่ง server จึงต้องรู้ว่ามีแท็กอะไรอยู่ก่อน — `fetchTags` ดึงรายชื่อแท็กของ scope นั้น (ของฉัน / ของทีม) มาขยายคำที่พิมพ์เป็นรายการแท็กก่อนยิง query
  - หน้าคลังจัดผลค้นหาเป็นกลุ่มแบบไม่ซ้ำตามลำดับ **พบจากแท็ก → พบจากชื่อโจทย์ → พบจากเนื้อหาโจทย์** และมีตัวเลือกแสดงทั้งหมดหรือเฉพาะกลุ่มใดกลุ่มหนึ่ง ทั้งคลังของฉันและโจทย์ที่แชร์ในทีม; คลังที่แบ่งหน้าจะนับแต่ละกลุ่มในฐานข้อมูลแล้วตัดหนึ่งหน้าต่อเนื่องข้ามกลุ่ม จึงยังส่งกลับไม่เกิน 24 ข้อต่อรายการแทนการโหลดผลทั้งหมดมาแบ่งใน browser
  - ระดับความยาก (และรูปแบบโจทย์ในหน้าคลัง) ยังเป็นตัวกรองแยก AND ทับคำค้นเหมือนเดิม
  - **แก้ไขโจทย์แล้วกลับมาที่มุมมองเดิม** — คำค้น ตัวกรอง แท็บ และเลขหน้าของหน้าคลังถูกพ่วงไปกับลิงก์แก้ไขเป็นพารามิเตอร์เดียว (`?from=`) แล้วคืนค่าเมื่อกดบันทึกหรือยกเลิก ทั้งโจทย์เดี่ยวทุกชนิดและโจทย์กลุ่มหลายขั้นตอน กติกาอยู่ที่ `lib/question-return.ts` (มีเทสต์) ลิงก์เก่าแบบ `?tab=team` ยังใช้ได้ และ `redirect_to` ที่ส่งมาจากเบราว์เซอร์ถูกจำกัดให้เป็น `/questions` เท่านั้น
  - แถบเลื่อนหน้ามีทั้งเหนือและใต้รายการโจทย์ (ทั้งคลังของฉันและโจทย์ในทีม) ตัวบนไม่เลื่อนจอ ตัวล่างเลื่อนขึ้นบนให้เหมือนเดิม ปุ่มเลขหน้าแสดงหน้าข้างเคียงข้างละ 2 (เดิมข้างละ 1 จึงกดข้ามไปหน้าถัดจากนั้นไม่ได้) และมีตัวเลือก "ไปหน้า N จาก M" ให้กระโดดไปหน้าไหนก็ได้ในคลิกเดียวเมื่อมีเกิน 3 หน้า แถบตัดบรรทัดเองบนจอแคบ
- หน้าต่างเลือกโจทย์เหลือช่องค้นหาช่องเดียว (ช่องกรองแท็กแยกถูกถอดออก) ใต้ช่องจะเสนอ "แท็กที่ตรง" กับคำที่กำลังพิมพ์เป็นปุ่มให้กดเติมให้เต็มคำ และเมื่อไม่พบโจทย์จะบอกว่ากำลังกรองด้วยอะไรพร้อมปุ่ม "ล้างตัวกรองทั้งหมด"
- หน้าสร้าง/แก้ไขแฟ้มโจทย์ กับหน้าสร้างงาน ดึงคลังผ่าน `fetchBankQuestions` (`lib/question-bank.ts`) ตัวเดียวกัน ซึ่ง **ดึง `tags` มาด้วย** และไล่ดึงทีละหน้าจนครบ — เดิม query ของหน้าแฟ้มโจทย์ไม่ได้เลือกคอลัมน์ `tags` ตัวกรองแท็กจึงไม่เจออะไรเลยทุกครั้ง และทุกหน้าดึงรอบเดียวจึงติดเพดาน 1,000 แถวของ PostgREST คลังที่เกินพันข้อจะหาข้อท้ายๆ ไม่เจอ
- แฟ้มโจทย์ไม่มีแท็กแล้ว — ทั้งฟอร์มสร้าง/แก้ไข ตัวกรอง และชิปบนการ์ดถูกถอดออก ค้นหาแฟ้มโจทย์ด้วยชื่อชุดอย่างเดียว (คอลัมน์ `tags` ยังอยู่ในฐานข้อมูลและค่าของชุดเดิมไม่ถูกลบ `updateQuestionSet` จะไม่แตะคอลัมน์นี้ถ้าผู้เรียกไม่ได้ส่งมา)
- **หัวหน้าแฟ้มคือชื่อแฟ้มเอง** — "แฟ้มโจทย์ <ชื่อ>" เรนเดอร์จากฟอร์ม (ไม่ใช่จาก page) จึงเปลี่ยนตามทันทีที่พิมพ์ชื่อใหม่ ก่อนกดบันทึกด้วยซ้ำ · หน้าสร้างแฟ้มยังเป็น "สร้างแฟ้มโจทย์" เพราะยังไม่มีชื่อให้ต่อท้าย
- **การ์ด "ข้อมูลแฟ้มโจทย์" เปิดมาเป็นแบบอ่านอย่างเดียว มีปุ่ม แก้ไข** — ครูเข้าหน้านี้มาทำงานกับโจทย์ข้างใน ไม่ได้มาเปลี่ยนชื่อแฟ้ม การมีช่องกรอกสามช่องเปิดรออยู่บนสุดคือสามอย่างที่เผลอกดแล้วเปลี่ยนได้โดยไม่มีใครเห็น · กด "แก้ไข" จึงจะกรอกได้ กด "เสร็จสิ้น" เพื่อพับกลับ (ค่าที่แก้ยังเป็นร่างอยู่ ยังไม่บันทึกจนกดบันทึกการแก้ไขเหมือนเดิม) · หน้าสร้างแฟ้มเปิดเป็นโหมดกรอกเลย เพราะยังไม่มีอะไรให้แสดง
- **การ์ดแฟ้มย่อยเป็นแถวเดียวจบ** — ไอคอน + ชื่อ + จำนวนข้อ + เมนู ⋮ ไม่แสดงตัวอย่างโจทย์ข้างในแล้ว และเรียงได้ถึง 4 คอลัมน์ · ของเดิมสูง 168px ต่อใบพร้อมตัวอย่างโจทย์สองบรรทัด ซึ่งอ่านดีตอนมีสามแฟ้มย่อย แต่ครูที่แบ่งไว้ยี่สิบแฟ้มย่อยจะได้หน้าที่ต้องเลื่อนยาวก่อนจะถึงรายการโจทย์ · "เปิดแฟ้มย่อย" ย้ายเข้าไปในเมนู ⋮ (กดทั้งใบก็เปิดได้เหมือนเดิม)
- แฟ้มโจทย์จัด "แฟ้มย่อย" ได้ชั้นเดียว (`question_sets.sections` — คำเดิมในโค้ดคือ section) หน้าสร้าง/แก้ไขแฟ้มเรียงลงมาสามชั้น: ข้อมูลแฟ้ม → แฟ้มย่อยเป็นการ์ดแบบเดียวกับคลังแฟ้มโจทย์ → รายการโจทย์ ทั้งหน้าสร้างและหน้าแก้ไขใช้ฟอร์มเดียวกัน จึงสร้างแฟ้มย่อยได้ตั้งแต่ตอนสร้างแฟ้ม (ไม่บังคับ)
- หน้าแฟ้มโจทย์แยกหน้าที่ของสองระดับให้ขาดกัน: **การ์ดแฟ้มย่อย** จัดว่าโจทย์ข้อไหนอยู่ในแฟ้มย่อยใด ส่วน **รายการด้านล่าง** เป็นโจทย์ทั้งหมดในแฟ้ม (`components/questions/set-structure-panel.tsx`) เดิมทั้งสองอย่างปนกันในรายการเดียว — กดการ์ดแล้วรายการด้านล่างเปลี่ยนความหมายเงียบๆ ครูจึงแยกไม่ออกว่ากำลังแก้ระดับไหน
- **"โจทย์ในแฟ้มนี้" ใช้การ์ดใบเดียวกับหน้าคลังโจทย์ แก้ไขโจทย์ได้ครบจากในแฟ้ม** (`components/questions/set-question-list.tsx` + `components/questions/question-card.tsx` ซึ่งย้ายออกจาก `app/(app)/questions/_components/` มาเป็นของกลาง พร้อม `question-tags-editor` `sub-question-count-badge` `preview-modal`) เหตุผลคือคลังพันข้อหาโจทย์ยาก แต่แฟ้มเป็นตัวจำกัดขอบเขตที่ครูเปิดอยู่แล้ว การ์ดจึงมีครบทั้งดูตัวอย่าง แชร์ รายงานปัญหา ทำสำเนา แก้ไข แก้แท็กในที่ และแถบสถิติ p/r (สวิตช์บังคับแนบรูปวิธีทำถูกถอดออกแล้ว — ย้ายไปถามตอนสร้างงาน)
  - **สองมุมมอง** — "การ์ด" (ค่าเริ่มต้น) ไว้อ่านและแก้โจทย์ · "รายการสั้น" คือแถวบรรทัดเดียวแบบเดิม ไว้จัดลำดับเลขข้อ เพราะลำดับนี้คือเลขข้อที่นักเรียนเห็น และการเลื่อนข้อ 80 ขึ้นไปข้อ 3 ผ่านการ์ดทีละใบใช้ไม่ได้จริง · มีช่องค้นหาเฉพาะในแฟ้ม และมุมมองการ์ดแบ่งหน้าละ 24 ข้อเท่าหน้าคลังโจทย์ แฟ้ม 500 ข้อจึง mount การ์ดแค่ 24 ใบ
  - **`ลบโจทย์ถาวรจากคลัง` อยู่ในเมนู ⋯ ไม่วางติดกับ `เอาออกจากแฟ้ม`** — สองปุ่มนี้ทำคนละเรื่อง (ลบออกจากคลังทั้งหมด กับ เอาออกจากแฟ้มนี้เฉยๆ) ไอคอนคล้ายกันห่างกันไม่กี่พิกเซลคือทางที่โจทย์หายโดยไม่ตั้งใจ · ข้อความยืนยันในบริบทแฟ้มบอกทางเลือกที่ครูน่าจะตั้งใจจริงด้วย
  - **กด `แก้ไข` จะบันทึกแฟ้มให้ก่อนอัตโนมัติ แล้วค่อยไปหน้าแก้ไขโจทย์ เสร็จแล้วเด้งกลับมาที่แฟ้มเดิม** — หน้านี้เป็นร่างทั้งหน้า (ลำดับ แฟ้มย่อย โจทย์ที่เพิ่งเพิ่ม ยังไม่มีผลจนกดบันทึก) การเด้งออกไปเฉยๆ คือทิ้งร่างทั้งก้อน · บันทึกไม่สำเร็จก็ไม่ไปไหน · `saveQuestionSet` คือ `updateQuestionSet` ที่ไม่ redirect — ตัวเดิมปิดท้ายด้วย `redirect('/questions/sets')` จึงไม่เคยคืนค่าให้ผู้เรียก · ทางกลับเดินผ่าน `?from=set=<id>` ซึ่ง `questionsReturnTo`/`safeQuestionsRedirect` ประกอบ path ขึ้นใหม่จาก id ที่ต้องเป็น uuid เท่านั้น ไม่ไว้ใจ path ที่ส่งมา (มีเทสต์ใน `lib/question-return.test.ts`)
  - **ค่าใช้จ่ายผูกกับสิ่งที่เห็นบนจอ ไม่ใช่ขนาดแฟ้มหรือขนาดคลัง** — ไม่แตะ `fetchBankQuestions` (อีก 3 หน้าใช้ร่วม จะพลอยช้าไปด้วย) ส่วนที่การ์ดต้องใช้เพิ่ม (วิชา หมวดหมู่ กลุ่มหลายขั้นตอน สถิติ ป้ายซ้ำ จำนวนข้อย่อย แฟ้มอื่นที่ถือข้อนี้) มาจาก `getQuestionCardData` ที่ขอทีละหน้าจอ — 24 id แรกดึงมาพร้อมหน้า ที่เหลือดึงตอนเปิดไปหน้านั้น · มุมมองรายการสั้นไม่ยิง query เลย · การอ่านที่ใช้ร่วมกับหน้าคลังโจทย์ (`fetchQuestionStats` `fetchDuplicateCounts` `fetchSetMemberships`) ย้ายมาอยู่ที่ `lib/question-card-data.ts` ที่เดียว · ระหว่างที่คำตอบยังไม่มา แถบสถิติจะไม่ขึ้นเลย แทนที่จะขึ้นว่า "ยังไม่มีสถิติ" ซึ่งเป็นคำกล่าวถึงตัวโจทย์ ไม่ใช่ถึงหน้า
  - หน้า *สร้าง* แฟ้ม (ยังไม่มี id) การ์ดจะไม่มีปุ่มแก้ไขและลบถาวร เพราะยังไม่มีแฟ้มให้บันทึกร่างลงไปหรือให้กลับมา — มีบรรทัดบอกว่าให้บันทึกแฟ้มก่อน
- กดการ์ดแฟ้มย่อยได้ทั้งใบ (หรือปุ่ม "เปิดแฟ้มย่อย") เปิด dialog ที่มีชื่อแฟ้มย่อยให้แก้ และรายการติ๊กเลือกสมาชิก — **เลือกได้เฉพาะโจทย์ที่อยู่ในแฟ้มนี้แล้ว ไม่มีทางเข้าถึงคลังโจทย์จากตรงนี้** ติ๊กคือเพิ่มเข้าแฟ้มย่อยนี้ (ไม่ดึงออกจากแฟ้มย่อยอื่น) ติ๊กออกคือเอาออกจากแฟ้มย่อยนี้ ไม่ใช่ออกจากแฟ้ม
- **แต่ละแถวใน dialog แฟ้มย่อยมีป้ายระดับ/ชนิด กับปุ่ม ดูตัวอย่าง และ แก้ไข** — ไม่ใช้การ์ดเต็มเพราะ dialog กว้างแค่ ~672px และงานหลักตรงนี้คือติ๊กเข้า/ออกให้เร็ว · `ดูตัวอย่าง` เปิดทับ dialog ไม่พาไปไหน จึงกดได้เสมอ ส่วน `แก้ไข` ปิดไว้จนกว่าจะกดยืนยันการเปลี่ยนแปลง เพราะการติ๊กในนี้ก็เป็นร่างเหมือนกัน และการแอบบันทึกให้จะสร้างแฟ้มย่อยไร้ชื่อขึ้นมาทั้งที่ครูแค่เปิดดู · ปุ่มแก้ไขถาม `getQuestionCardData` ของ id เดียวตอนกด เพื่อรู้ว่าเป็นโจทย์หลายขั้นตอนหรือไม่ (คนละเส้นทางแก้ไข) แล้วค่อยบันทึกแฟ้มและไป
- สร้างแฟ้มย่อยใหม่จะเปิด dialog นั้นทันทีพร้อมโฟกัสช่องชื่อ · เมนู ⋮ บนการ์ดเหลือแค่ย้ายลำดับกับลบ · ลบแฟ้มย่อยแล้วโจทย์ไม่หาย แต่กลับไปอยู่ในแฟ้มหลัก · เอาโจทย์ออกจากแฟ้มก็หลุดจากแฟ้มย่อยตามไปด้วย
- หน้าต่าง "เพิ่มโจทย์จากคลัง" เพิ่มเข้าแฟ้มอย่างเดียว ไม่มีตัวเลือกปลายทางเป็นแฟ้มย่อยแล้ว
- **การเพิ่ม/เอาออกทุกจุดต้องยืนยันก่อน** — หน้าต่างเลือกโจทย์ทั้งสองแบบ (คลังโจทย์ และแฟ้มย่อย) เก็บสิ่งที่ติ๊กไว้เป็นร่าง ทำเครื่องหมายรายแถวว่า "+ จะเพิ่ม" (เขียว) หรือ "− จะเอาออก" (แดง) สรุปจำนวนที่ท้ายหน้าต่าง แล้วเปลี่ยนจริงเมื่อกดปุ่มยืนยันเท่านั้น กดยกเลิกคือทิ้งร่างทั้งหมด `QuestionPicker` รับ `baselineIds` เพื่อทำเครื่องหมายและตรึงข้อที่ถูกติ๊กออกไว้ที่เดิม ไม่ให้ตกกลับไปในคลังพันข้อจนหาไม่เจอ
- การเอาโจทย์ออกจากแฟ้ม (รายข้อและหลายข้อ) กับการลบแฟ้มย่อย ถามยืนยันด้วย `ConfirmDialog` (`components/ui/confirm-dialog.tsx`) ที่บอกชื่อโจทย์ที่กำลังจะหายและย้ำว่าโจทย์ยังอยู่ในคลัง แทน `window.confirm` เดิม
- สร้างแฟ้มย่อยเกิดขึ้นตอนกดยืนยันเท่านั้น กดยกเลิกแล้วไม่มีแฟ้มย่อยเปล่าค้างไว้
- การลบทั้งแฟ้มโจทย์ (ทั้งจากการ์ดในคลังและปุ่มท้ายหน้าแก้ไข) ใช้ `ConfirmDialog` เหมือนกัน และบอกให้ชัดว่าลบถาวรกู้ไม่ได้ แต่โจทย์ข้างในยังอยู่ในคลังและงานที่มอบหมายไปแล้วไม่กระทบ (`deleteQuestionSet` ลบเฉพาะแถว `question_sets`)
- การเลือกโจทย์จากคลังย้ายไปอยู่ใน dialog แล้ว (เดิมเป็นคอลัมน์ซ้าย) `QuestionPicker` รับ `surface="plain"` / `showHeader={false}` สำหรับกรณีนี้
- โจทย์ข้อเดียวอยู่ได้หลายแฟ้มย่อย (`setQuestionInSection`) รายการโจทย์แสดงป้ายชื่อแฟ้มย่อยได้หลายป้ายต่อข้อ · มอบหมายหลายแฟ้มย่อยพร้อมกันจะรวบข้อที่ซ้ำเหลือครั้งเดียว (`questionIdsForSections` รับลำดับของแฟ้มมา dedupe)
- `question_ids` เป็นแหล่งความจริงของทั้งสมาชิกและลำดับ **ไม่ได้สร้างใหม่จากลำดับแฟ้มย่อยแล้ว** — ข้อที่อยู่สองแฟ้มย่อยไม่มีตำแหน่งเดียวให้ไปอยู่ ครูจัดลำดับเองที่รายการโจทย์ (`moveQuestionInSet`) ส่วนหน้าที่แสดงป้ายได้ป้ายเดียวต่อข้อ (ใบพิมพ์ ตารางนำทาง หน้าตรวจ) ใช้ `sectionByQuestionId` ซึ่งคืนแฟ้มย่อยแรก แฟ้มที่ไม่มีแฟ้มย่อยทำงานเหมือนเดิมทุกอย่าง
- การ์ดในคลังแฟ้มโจทย์บอกจำนวนแฟ้มย่อยและชื่อ 3 แฟ้มย่อยแรก ปุ่ม "มอบหมาย" มีเมนูเลือกมอบหมายเฉพาะแฟ้มย่อยเดียว (`?set=<id>&sections=<id>`) ซึ่งจะตั้งชื่องานเป็น "ชื่อแฟ้ม — ชื่อแฟ้มย่อย" ให้
- กดที่ตัวการ์ดได้ทั้งใบ — แฟ้มของตัวเองไปหน้าแก้ไข แฟ้มที่ทีมแชร์มาไปหน้ามอบหมาย (หน้าแก้ไขเปิดได้เฉพาะคนสร้าง) ทำด้วยลิงก์โปร่งใสวางทับการ์ด ไม่ใช่ `<a>` ครอบเนื้อหา แถวปุ่มล่างจึงยังกดแยกได้ ปุ่มแก้ไขถูกถอดออก ส่วนดาวน์โหลดกับลบย้ายลงมาอยู่แถวเดียวกับ "มอบหมาย"
- **แก้ไขชุดโจทย์ของงานที่มอบหมายได้ ตราบใดที่ยังไม่มีใครเริ่มทำ** — การ์ด "โจทย์และคะแนน" ในหน้าแก้ไขงาน เพิ่มโจทย์จากคลัง (ผ่าน `QuestionPicker` แบบเดียวกับหน้าแฟ้มโจทย์ ยืนยันก่อนจึงเปลี่ยน) เอาข้อออก และสลับลำดับได้ เรียงลำดับด้วยปุ่มลูกศรทีละขั้น หรือพิมพ์เลขข้อปลายทางลงในช่องซ้ายมือแล้วกด Enter (`moveQuestionToIndex` ใน `lib/question-set-sections.ts` มีเทสต์)
  - **ล็อกทันทีที่มี submission แถวแรก** เพราะทุกครั้งที่นักเรียนกดเริ่ม ระบบ freeze ชุดโจทย์ลง `submission_answers` พร้อมคำนวณ `max_score` เก็บไว้ ถ้าแก้ทีหลังคนที่ทำก่อน/หลังจะได้ข้อสอบคนละชุดและคะแนนเต็มไม่เท่ากัน — UI ซ่อนปุ่มพร้อมอธิบายเหตุผล และ `updateAssignment` ปฏิเสธซ้ำอีกชั้น (client ส่ง `question_ids` มาเฉพาะตอนที่แก้ได้จริง จึงไม่ทริกข้อผิดพลาดตอนบันทึกฟิลด์อื่น)
  - ตอนบันทึก `question_ids` กับ `sections` ถูกเขียนคู่กันผ่าน `normalizeSetSections` เสมอ แฟ้มย่อยจึงไม่ค้างชี้ไปยังข้อที่ถูกเอาออก, `question_points` ถูกกรองด้วยชุดใหม่, `random_question_count` ตรวจกับจำนวนข้อชุดใหม่ (ลบจนเหลือน้อยกว่าจำนวนสุ่มไม่ได้) และปฏิเสธชุดว่าง
  - id ที่ส่งมาถูกตรวจกับ RLS อีกชั้น (`in(...)` แล้วเทียบจำนวน) โจทย์ที่ครูคนนี้ไม่มีสิทธิ์จึงเพิ่มเข้าชุดไม่ได้
- **คะแนนเริ่มต้นรายข้อคิดตามจำนวนข้อย่อย** (ข้อย่อย 1 ข้อ = 1 คะแนน) ทั้งหน้าสร้างและหน้าแก้ไขงาน — เดิมตั้งให้ทุกข้อเท่ากับ 1 แล้วส่งเป็น override ทุกข้อ เติมคำ 6 ช่องจึงกลายเป็น 1 คะแนนโดยที่ครูไม่ได้สั่ง ค่าเริ่มต้นมาจาก `defaultQuestionPoints` (`lib/question-bank.ts`) ซึ่งเรียก `naturalMaxScore` ตัวเดียวกับที่ระบบใช้ตอนตรึง `submission_answers.max_score` คะแนนเริ่มต้นจึงเท่ากับคะแนนโครงสร้างพอดีและการตรวจไม่ถูก rescale · ถ้าครูถ่วงน้ำหนักไว้เอง (คะแนนต่อข้อความของถูก-ผิด หรือคะแนนรายส่วนของโจทย์ผสม) ค่าเริ่มต้นจะตามน้ำหนักนั้น ไม่ใช่จำนวนข้อย่อยดิบ
  - งานที่มอบหมายไปแล้วไม่เปลี่ยน — ค่าที่เคยบันทึกใน `question_points` ยังชนะค่าเริ่มต้นเสมอ
  - `fetchBankQuestions` ดึงคอลัมน์ที่ใช้นับมาคำนวณฝั่ง server แล้วส่งเฉพาะตัวเลข (`sub_question_count`, `default_points`) ให้ browser ไม่ได้ส่ง jsonb ของทั้งคลังไปด้วย
- **ขั้น "คะแนน" ของหน้าสร้างงานสลับลำดับข้อ เอาข้อออก และดูตัวอย่างรายข้อได้** — แถวเดียวกับที่ตั้งคะแนน มีปุ่มลูกศรย้ายทีละขั้น ช่องเลขข้อที่พิมพ์ปลายทางแล้วกด Enter (`OrderNumberInput` ตัวเดียวกับหน้าแก้ไขงาน) ปุ่มกากบาทท้ายแถวเอาข้อนั้นออก (เจอข้อซ้ำแล้วไม่ต้องย้อนกลับไปขั้นเลือกโจทย์) และปุ่มรูปตาเปิด "มุมมองนักเรียน" ของข้อนั้นพร้อมเดินหน้า/ถอยหลังทั้งชุด (`QuestionPreviewDialog` ใช้ร่วมกับตัวช่วยสร้างโครงการวิจัย โหลดโจทย์เต็มผ่าน `getQuestionClientDetail` เพราะรายการในคลังส่งมาแค่ข้อมูลย่อ)
  - ปุ่มเอาออกมีผลเท่ากับติ๊กออกที่ขั้นเลือกโจทย์ (ตัดจาก `selectedIds` เฉยๆ ไม่แตะ `sections` ข้อนั้นจึงกลับเข้าแฟ้มย่อยเดิมได้ถ้าติ๊กกลับ) และปิดตายเมื่อเหลือข้อสุดท้าย เพราะ server ปฏิเสธงานที่ไม่มีโจทย์ และงานที่สร้างจากแฟ้มจะถูกเติมโจทย์ทั้งแฟ้มกลับมาเงียบๆ แทน · หัวการ์ดบอกจำนวนข้อคู่กับคะแนนรวมแล้ว (`N ข้อ · รวม X คะแนน`) จำนวนที่เหลือจึงเห็นทันทีตอนกดออก
  - ลำดับที่จัดไว้คือ `question_ids` ของงานโดยตรง (ถ้าเปิด "สลับลำดับข้อ" ในขั้นตั้งค่า นักเรียนยังได้ลำดับสุ่มทับอีกชั้น) การสลับลำดับตอนสร้างใช้ `moveQuestionOrder`/`moveQuestionOrderToIndex` ซึ่งไม่แตะ `sections` — แฟ้มย่อยของข้อที่ยังไม่ได้ติ๊กจึงไม่หายไประหว่างทาง และถูกกรองด้วย `filterSectionsToQuestions` ตอนบันทึกเหมือนเดิม (มีเทสต์ใน `lib/question-set-sections.test.ts`)
- **"เพิ่มจากแฟ้มโจทย์ที่มีอยู่" อยู่ในการ์ดเลือกโจทย์ พับเก็บไว้จนกว่าจะกด** (`QuestionSetImport`, เสียบผ่าน prop `toolbar` ของ `QuestionPicker` ซึ่งวางไว้ระหว่างหัวข้อกับช่องค้นหา) — เดิมเป็นการ์ดแยกเหนือรายการโจทย์ ครูที่เลื่อนลงไปกลางคลังพันข้อจึงต้องเลื่อนกลับขึ้นไปสุดถึงจะเจอ
  - แต่ละแถวบอกว่าแฟ้มนั้นให้อะไรได้บ้าง: `N ข้อ` · `เพิ่มไปแล้ว K ข้อ` / `เพิ่มครบแล้ว` (กดไม่ได้แล้ว) · `ข้าม M ข้อที่ถูกลบไปแล้ว` — แฟ้มที่ไม่เหลือโจทย์ให้เพิ่มเลยถูกปิดปุ่มและจมไปท้ายรายการ ไม่ซ่อน เพราะครูที่รู้ว่ามีแฟ้มนี้อยู่ต้องหาเจอและอ่านเหตุผลได้
  - เกิน 6 แฟ้มจะมีช่องค้นหาชื่อ/คำอธิบายของตัวเอง พร้อมบรรทัด "พบ X แฟ้ม จากทั้งหมด Y แฟ้ม" และรายการสูงไม่เกิน `max-h-64` แล้วเลื่อนในตัวเอง
  - toast บอกจำนวนที่เพิ่มเข้ามาจริง ไม่ใช่ขนาดแฟ้ม — กดแฟ้มเดิมซ้ำเคยขึ้นว่าเพิ่มครบ 22 ข้ออีกรอบทั้งที่ไม่ได้เพิ่มอะไรเลย
- **ตัวเลือกห้องเรียนในหน้าสร้างงานเป็นรายการสูงคงที่ เลื่อนในตัวเอง** (`ClassroomPicker`) — เดิมพิมพ์ทุกห้องเต็มความสูง ครูที่มียี่สิบห้องต้องเลื่อนผ่านหน้าจอกว่าครึ่งกว่าจะถึงช่องอื่นในฟอร์ม
  - แถวเตี้ยลง (ไอคอน 7×7, `p-2.5`) และคำใต้ชื่อเหลือแค่ `ระดับ · ภาคเรียน · คำอธิบายที่ครูพิมพ์เอง` — เดิมพิมพ์ `description` ดิบจึงขึ้น `หน้าปก: blue · … · การเข้าร่วม: …` ให้ครูอ่าน ซึ่งเป็นข้อยกเว้นเดียวที่เหลือของกติกา `displayDescription()`
  - ไอคอนใช้สีหน้าปกที่ครูตั้งไว้ (`coverOf`) ห้องเรียนจึงจำได้ด้วยสีเหมือนหน้าคลังห้องเรียน
  - เกิน 6 ห้องมีช่องค้นหา (ชื่อ ระดับ ภาคเรียน แท็ก คำอธิบาย) พร้อมบรรทัด "พบ X ห้อง จากทั้งหมด Y ห้อง" · รายการสูงไม่เกิน `max-h-64`
  - **ห้องที่ติ๊กไว้ปักอยู่บนสุดเสมอ และไม่หายแม้คำค้นจะไม่ตรง** (ต่างจาก `QuestionPicker` ที่ปักเฉพาะในผลค้นหา) — ช่องนี้ตัดสินว่าใครได้ทำงานชิ้นนี้ สิ่งที่เลือกไว้จึงต้องมองเห็นและติ๊กออกได้ตลอด · มีหัวข้อ "ห้องเรียนอื่น" คั่นเมื่อมีทั้งสองกลุ่ม
- ปุ่ม ประเภทงาน (แบบฝึกหัด/ข้อสอบ) และ โหมดการสอบ (ออนไลน์/พิมพ์ใบงาน) เป็นแถวเตี้ยแบบไอคอนอยู่ซ้าย ทรงเดียวกับรายการห้องเรียนเหนือมัน (เดิมเป็นบล็อกอีโมจิซ้อนข้อความ สูงเกือบเท่าตัว) และบนจอมือถือเรียงลงมาทีละอันเพื่อไม่ให้คำอธิบายตัดบรรทัด
- หน้าต่างเลือกโจทย์ติดป้าย "ข้อ 1, ข้อ 2…" บนแถวที่ติ๊กแล้ว (เดิมมีเลขเฉพาะในชิปสรุปด้านล่าง) ครูจึงเห็นตั้งแต่ตอนเลือกว่าโจทย์ไหนจะเป็นข้อที่เท่าไหร่
- งานที่มอบหมายเก็บ snapshot ของแฟ้มย่อยไว้เอง (`assignments.sections`, `show_sections`) แก้แฟ้มทีหลังไม่กระทบงานเดิม ชื่อแฟ้มย่อยแสดงในหน้าทำข้อสอบ (ป้ายกำกับข้อ + จัดกลุ่มตารางนำทาง), ใบงานพิมพ์, หน้าส่งออก PDF และแท็บโจทย์ฝั่งครู โดยเลขข้อยังไล่ต่อเนื่อง 1..n ไม่รีเซ็ตต่อแฟ้มย่อย และปิด/เปิดการแสดงชื่อแฟ้มย่อยได้จากหน้าแก้ไขงาน
- ตอนสร้างงานจากแฟ้ม โจทย์ที่ครูติ๊กออกจะถูกตัดออกจริงแล้ว (เดิม server ใช้ `question_ids` ทั้งแฟ้มทับสิ่งที่ครูเลือก) แต่ยังรับเฉพาะ id ที่อยู่ในแฟ้มนั้นเหมือนเดิม
- ใบงานพิมพ์และหน้าส่งออกเรียงโจทย์ตามลำดับของงานแล้ว (เดิมใช้ลำดับที่ฐานข้อมูลส่งกลับมาจาก `.in()`)

- ฟอร์ม written/random numeric ไม่มีช่อง "หน่วยของคำตอบ" แล้ว ครูพิมพ์หน่วยลงในรูปแบบช่องคำตอบแทน (เช่น "ตอบ [คำตอบ] J") คอลัมน์ `answer_unit`/`answer_parts[].unit` ยังอยู่และถูกส่งต่อตอนบันทึก โจทย์เก่าที่เคยกรอกหน่วยไว้จึงยังแสดงหน่วยข้างช่องคำตอบเหมือนเดิม แต่แก้ไขหน่วยนั้นจากฟอร์มไม่ได้แล้ว
- มี question sets, team sharing และ duplicate/remix-related UI
- ช่องแท็กเสนอแท็กจากโจทย์ที่บันทึกไว้ (`getAllTags`) รวมกับแท็กที่เพิ่งพิมพ์ในเบราว์เซอร์เดียวกัน (localStorage `korkru:tag-history` เก็บ 200 รายการล่าสุด) จับคู่แบบไม่สนช่องว่างซ้ำ/ตัวพิมพ์ และยอมให้พิมพ์ผิดได้เล็กน้อย เลือกด้วยลูกศร+Enter ได้ และลบแท็กที่เคยพิมพ์ออกจากรายการได้ — ประวัติฝั่งเบราว์เซอร์นี้ไม่ซิงก์ข้ามเครื่องและไม่ผูกกับบัญชีผู้ใช้
- ตัวกรอง "แท็ก" ในแถบตัวกรองใช้แท็กจริงจากคลังของครูคนนั้น (เรียงตามที่ใช้บ่อย แสดง 12 อันแรกแล้วกดดูทั้งหมดได้) ไม่ใช่รายการตัวอย่างที่ hardcode ไว้แล้ว
- หน้านำเข้าไฟล์โจทย์อ่านคลังเดิมแบบแบ่งหน้าด้วย `fetchAllRows` แล้วทั้งการตรวจซ้ำ (`checkImportDuplicates`) และการตั้งชื่อเลี่ยงชนกันตอนเลือก "เปลี่ยนชื่อ" (`importQuestionsFromFile`) — เดิมทั้งสองที่ยิง query เดียวไม่แบ่งหน้า จึงติดเพดาน 1,000 แถวของ PostgREST คลังที่เกินพันข้อจะเทียบได้ไม่ครบ โจทย์ที่นำเข้าซ้ำแต่ตรงกับข้อในส่วนที่หายไปจะรายงานว่า "ไม่ซ้ำ" และ "(2)" ที่ตั้งให้ก็อาจไปชนชื่อที่มีอยู่แล้ว
- **การ์ดในคลังโจทย์เตือนเมื่อเนื้อหาซ้ำ** — ป้าย "ซ้ำกับอีก N ข้อ" ขึ้นเมื่อโจทย์อื่นในคลังของครูคนเดียวกันมีเนื้อหาตรงกันทุกอย่าง กติกาอยู่ที่ `lib/question-content-match.ts` (มีเทสต์) เทียบ **เนื้อโจทย์ (ตัด markup/ช่องว่าง/ตัวพิมพ์) · ชนิดโจทย์ · รูป · ตัวเลือก · สูตร/หน่วย/ความคลาดเคลื่อน/ส่วนคำตอบ · ตัวแปร · logic rules · extra_data** และ **ไม่นับ** ชื่อโจทย์ แท็ก ระดับความยาก หมวด การมองเห็น/แชร์ เฉลย และสวิตช์บังคับแนบรูปวิธีทำ — id สุ่มใน jsonb (ตัวเลือก/ข้อเรียงลำดับ) ถูกตัดทิ้งก่อนเทียบ ไม่งั้นสำเนาจะไม่มีวันตรงกัน
  - หน้าคลังไม่สแกนทั้งคลังแล้ว: fingerprint เก็บอยู่บนแถว (`questions.content_fingerprint` เขียนตอนบันทึกโจทย์) หน้าคลังจึงถามแค่ว่าโจทย์ของครูคนนั้นมีกี่ข้อที่ถือ fingerprint ที่อยู่บนจอ ยิงทีละ 100 ค่า — งานผูกกับจำนวนที่แสดง ไม่ใช่ขนาดคลัง แถวที่ยังไม่ backfill (`content_fingerprint` เป็น NULL) ถูกข้าม ป้ายจึงหายไปเฉย ๆ ไม่ใช่นับผิด
  - ตรวจเฉพาะคลังของครูคนนั้น ไม่ข้ามไปโจทย์ที่เพื่อนในทีมแชร์มา และโจทย์กลุ่มเทียบที่ข้อแม่ (ตัวที่แสดงในรายการ)
- การ์ดในคลังโจทย์แก้แท็กได้ในที่ (`updateQuestionTags` เขียนเฉพาะโจทย์ที่ผู้ใช้สร้างเอง) เอาเมาส์ชี้ที่แท็กจะมีปุ่มลบมุมขวาบนและถามยืนยันก่อนลบ ส่วนปุ่ม "+ แท็ก" เพิ่มแท็กได้โดยไม่ต้องเข้าหน้าแก้ไข รายการที่เสนอมาจากแท็กทั้งคลังของครูคนนั้น รวมกับแท็กของโจทย์ทีมที่อยู่ในหน้าและประวัติที่พิมพ์ในเบราว์เซอร์
- สถิติรายข้อ (ค่าความยาก p, อำนาจจำแนก r, จำนวนครั้งที่ตอบ, ใช้ในกี่ชุดสอบ) คำนวณจาก `submission_answers` จริงแล้ว โจทย์ที่ยังไม่มีใครตอบจะแสดงว่ายังไม่มีสถิติ ไม่ใช่เลขสุ่ม
- แท็บประวัติการแก้ไขแสดงเฉพาะ `created_at`/`updated_at` จริง ยังไม่มีตารางเก็บรายละเอียดการแก้ไขรายครั้ง
- เมนูแชร์บนการ์ดโจทย์แชร์เข้าทีมจริงผ่าน `question_shares` (RLS อนุญาตเฉพาะเจ้าของโจทย์และทีมที่ตนสังกัด) ไม่ใช่รายชื่อครูตัวอย่าง
- นำเข้า/ส่งออกไฟล์ `.korkru.json` ใช้งานได้ รวมถึงโจทย์ composite แล้ว หมวดหมู่ถูก resolve จากชื่อ (รองรับ path "หมวดหลัก / หมวดย่อย") และอ่านตารางหมวดครั้งเดียวต่อการนำเข้า
- **ทางเข้าการนำเข้ามีสองชั้น** — เมนูซ้าย "นำเข้าโจทย์" (`/questions/import`) เป็นหน้าเลือกว่าจะนำเข้าจากไฟล์ Word หรือไฟล์ `.korkru.json` สำหรับคนที่ยังไม่รู้ว่ามีอะไรบ้าง ส่วนปุ่มสองปุ่มบนหน้าคลังโจทย์และหน้าคลังแฟ้มโจทย์ยังอยู่ที่เดิมสำหรับคนที่รู้แล้ว ทั้งสองทางใช้โค้ดตัวเดียวกัน — การ์ดในหน้าเลือกเรียก `ImportQuestionsButton` ผ่าน render prop `children` จึงได้ input, กล่องโต้ตอบโจทย์ซ้ำ และการแบ่ง batch ชุดเดียวกัน ไม่มีทางแยกให้ต่างกันได้

### นำเข้าจากไฟล์ Word — มีโค้ดรองรับ

- `/questions/import/word` รับไฟล์ `.docx` แล้วแตกเป็นร่างโจทย์ให้ครูตรวจ ก่อนส่งต่อเข้า `importQuestionsFromFile` ตัวเดิม จึงได้การตรวจซ้ำ การจับคู่หมวดหมู่ และกติกา tenant ชุดเดียวกับการนำเข้า `.korkru.json`
- **หน้านำเข้าไม่มีเอดิเตอร์ของตัวเอง** ร่างโจทย์ถูกถือเป็น `Question` เต็มรูป (`lib/docx-import/to-question.ts`) กด "แก้ไข" แล้วเลือกชนิดโจทย์ จากนั้นเปิด **ฟอร์ม ปรนัย/อัตนัย/บรรยาย ตัวจริง** พร้อมข้อมูลที่อ่านมาแล้ว ได้ทั้ง validation, ตัวแทรกสัญลักษณ์, อัปโหลดรูป และหน้าตัวอย่าง โดยไม่ต้องมีเอดิเตอร์คู่ขนานที่ด้อยกว่า
- ฟอร์มถูกส่งค่ากลับแทนการบันทึกด้วย prop `draft` (`lib/question-draft-handoff.ts`) — มีเมื่อไรแปลว่า "ยังไม่บันทึก": ปุ่มเปลี่ยนเป็น "ตกลง", ข้าม `createQuestion`, และซ่อนตัวควบคุมที่เส้นทางนำเข้าทำตามไม่ได้ (การมองเห็น/แชร์ทีม เพราะ import บันทึกเป็น private เสมอ, และตัวเลือกแฟ้มรายข้อ เพราะแฟ้มเลือกครั้งเดียวทั้งไฟล์) `changeType` พักตัวเลือกไว้เมื่อสลับชนิด ข้อที่อ่านเป็นปรนัยแล้วสลับผิดจึงไม่เสียตัวเลือกที่อ่านมา
- **ตัวเลือกปรนัยเก็บเป็นข้อความล้วน ไม่ใช่ HTML** เพราะ `MCQOption.text` เป็นช่องข้อความล้วนที่ครูแก้ด้วย input ธรรมดา ตัวยก/ตัวห้อยจึงถูกแปลงเป็นอักขระ Unicode ("10 เมตรต่อวินาที²", "m₁") — ใส่ markup ตรงนี้จะโชว์แท็กดิบให้ครูเห็นและทำให้โจทย์ที่นำเข้าไม่เหมือนโจทย์อื่นในคลัง ส่วนเนื้อโจทย์และข้อย่อยยังเป็น rich text ตามเดิม
- **รูปถูกอัปโหลดตอนอ่านไฟล์เสร็จ ไม่ใช่ตอนกดนำเข้า** เพื่อให้ตั้งแต่จุดนั้นรูปเป็น URL ธรรมดา วิดเจ็ตรูปในฟอร์มจริงจึงใช้ได้โดยไม่ต้องรู้ว่ามาจาก .docx — แลกกับการที่ถอยออกกลางคันจะทิ้งไฟล์ไว้ ซึ่งกวาดได้ที่ ตั้งค่า → พื้นที่จัดเก็บไฟล์ เหมือนไฟล์ค้างอื่น
- **ทั้งหมดทำงานในเบราว์เซอร์ ไม่มี AI และไม่มีการเรียก service ภายนอก** — ไฟล์ไม่ออกจากเครื่องครู มีแต่รูปที่ครูยืนยันแล้วเท่านั้นที่ถูกอัปโหลด จึงไม่มี API key, โควตา หรือค่าใช้จ่ายต่อไฟล์ผูกกับฟีเจอร์นี้
- โค้ดอยู่ที่ `lib/docx-import/` แยกตามสิ่งที่อ่าน: `zip.ts` (ตัวอ่าน ZIP เขียนเอง ใช้ `DecompressionStream` — โปรเจกต์ไม่มี zip dependency ของตัวเอง), `xml.ts` (ตัวอ่าน XML เล็ก ๆ เพราะ vitest รันบน `environment: 'node'` ที่ไม่มี DOM), `omml.ts`, `docx.ts`, `draft.ts`, `to-question.ts` — ทุกไฟล์เป็น pure และมีเทสต์
- **เลขข้อไม่ได้อยู่ในข้อความ** Word วาดเองจาก `numbering.xml` การตัดข้อจึงใช้ระดับนอกสุดของ list ที่เอกสารใช้นับข้อ ส่วนระดับที่ลึกกว่าเป็นข้อย่อย และป้าย ก) ข) ค) คำนวณจาก `numFmt` + ลำดับ มีทางสำรองสำหรับไฟล์ที่พิมพ์เลขเอง (รับเฉพาะเมื่อเลขไล่จาก 1 จริง)
- **เฉลยปรนัยอ่านจากการจัดรูปแบบ** ครูมักทำเครื่องหมายข้อถูกด้วยสีแดง ปากกาเน้นข้อความ หรือตัวหนา — ไล่ตามลำดับ แดง → highlight → สีอื่น → ตัวหนา → ขีดเส้นใต้ และสัญญาณที่ตัวเลือก**ทุกข้อ**มีเหมือนกันไม่นับ (ทั้งหมดตัวหนา = สไตล์ ไม่ใช่เฉลยสี่ข้อ) การจัดรูปแบบนี้ไม่ถูกคัดลอกไปเป็นเนื้อตัวเลือก ไม่งั้นเฉลยจะไปโผล่บนจอนักเรียน
- **สมการของ Word แปลงเป็น TeX** `m:oMath` → `\(...\)` ที่ `lib/math/latex.ts` เรนเดอร์ด้วย KaTeX อยู่แล้ว ถ้าดึงเป็นตัวอักษรตรง ๆ "15√2" จะกลายเป็น "152" และ "⅛g" จะกลายเป็น "18g" คือเลขที่ผิดสิบเท่าโดยไม่มีอะไรฟ้อง สมการที่มีแต่ตัวอักษร (ไม่มีเศษส่วน/ราก/ยกกำลัง) ส่งกลับเป็นข้อความธรรมดา และทุกข้อที่มีสมการจริงจะติดคำเตือนให้ครูตรวจ
- **สิ่งที่ครูแก้ได้จากการ์ดย่อ แก้ได้โดยไม่ต้องเปิดฟอร์ม** — ติ๊กข้อที่ถูกของปรนัย (toggle เดียวกับฟอร์ม ปรนัย ติ๊กได้มากกว่าหนึ่ง) และย้าย/เอารูปออก ไฟล์ที่ครูไม่ได้ทำเครื่องหมายสีไว้เลยจะต้องติ๊กเฉลยทุกข้อ การบังคับให้เปิดฟอร์มเต็มทุกครั้งจึงแพงเกินไป
- **คำเตือนแบ่งเป็นสองชนิด** — `liveWarnings` คำนวณสดจากสถานะปัจจุบัน (ยังไม่ติ๊กเฉลย, ติ๊กเกินหนึ่ง, เรื่องรูป) จึงหายทันทีที่ครูแก้ ส่วนที่เก็บไว้บน `DraftEntry.warnings` คือสิ่งที่ *ไฟล์* บอก (มีสมการ, อ้างข้อก่อนหน้า, ตัวเลือก/ข้อย่อยกำกวม) ซึ่งการแก้บนหน้านี้ไม่เปลี่ยน · คำเตือนที่ยังค้างหลังแก้แล้วสอนให้ครูเลิกอ่านคำเตือน
- **รูปลอย (`wp:anchor`) เกาะย่อหน้าที่ถูกวางใกล้ ไม่ใช่ข้อที่มันเป็นของ** หน้าตรวจทานจึงมีปุ่มย้ายรูปไปข้อก่อนหน้า/ถัดไป และคำเตือนเรื่องรูปคำนวณสดจากตำแหน่งปัจจุบัน ไม่ได้แช่ไว้ตั้งแต่ตอนอ่านไฟล์ — คำเตือนที่ยังค้างอยู่หลังครูแก้แล้วสอนให้ครูเลิกอ่านคำเตือน
- **ข้อที่จะทำให้นักเรียนถูกตัดสินว่าผิดทุกคนถูกกันไม่ให้นำเข้า ไม่ใช่แค่เตือน** — ปรนัยที่ยังไม่ได้เลือกข้อถูกจะแช่ `correct_answer` ว่างไว้ในทุก attempt และอัตนัยที่ไม่มีสูตรจะแช่ข้อความ error ของ `evaluateFormula` ไว้แทนเฉลย ทั้งสองกรณีให้ 0 คะแนนเงียบ ๆ ข้อที่ไม่มีเฉลยจึงเข้ามาเป็น `essay` (ครูตรวจเอง) เป็นค่าเริ่มต้น
- ข้อจำกัดที่ยังอยู่: รองรับ `.docx` เท่านั้น (ไม่รับ `.doc` และ PDF), แปลงได้เฉพาะ mcq / written / essay, รูปที่ Word เก็บเป็น EMF/WMF แสดงและอัปโหลดไม่ได้ต้องแนบใหม่เอง, ข้อที่เขียนว่า "จากข้อที่ผ่านมา" เตือนแต่ไม่รวมข้อให้ และรูปผูกกับข้อ ไม่ผูกกับตัวเลือกรายข้อ
- **วิชาและแฟ้มถามครั้งเดียวทั้งไฟล์ ไม่ถามรายข้อ** — เวิร์กชีตหนึ่งไฟล์คือวิชาเดียว ฟอร์มโจทย์จึงซ่อนช่อง "วิชา" ในโหมด draft (`showSubject`) และข้ามการบังคับกรอกของมันไป หน้านำเข้าบังคับกรอกแทน `entryToPortable` ประทับค่าลงทุกข้อตอนสร้างไฟล์นำเข้า ช่องบนหน้าจึงเป็นแหล่งความจริงเดียว แก้ทีหลังก็ยังมีผลกับข้อที่ตรวจไปแล้ว
- แฟ้มโจทย์บนหน้านำเข้าใช้ `QuestionSetPicker` ตัวเดียวกับฟอร์มสร้างโจทย์ เลือกแฟ้มที่มีอยู่ได้หลายแฟ้ม และติ๊กสร้างแฟ้มใหม่จากไฟล์เพิ่มได้ — `importQuestionsFromFile` รับ `fileIntoSetIds` เพิ่มเป็น argument ที่ห้า ส่งเฉพาะ batch สุดท้าย (แฟ้มควรได้ทั้งไฟล์พร้อมกัน ไม่ใช่ทีละ batch) แล้วเรียก `fileQuestionsIntoSets` ซึ่งตรวจ `created_by` ให้อยู่แล้ว · การเก็บเข้าแฟ้มที่ล้มเหลวรายงานคู่กับความสำเร็จ ไม่ทำให้การนำเข้าล้ม เพราะตอนนั้นโจทย์อยู่ในคลังแล้ว
- แท็กยังตั้งรายข้อ (ต่างกันจริงระหว่างข้อ) และหมวดหมู่ยังตั้งจากหน้านำเข้าไม่ได้ เพราะฟอร์มสร้างโจทย์ปกติก็ไม่มีช่องหมวดหมู่เช่นกัน
- ยังไม่มีเทสต์ที่แตะ Supabase หรือเบราว์เซอร์: `lib/docx-import/` ครอบคลุมด้วย vitest ส่วนหน้าเว็บ การอัปโหลดรูป และการ insert จริงตรวจด้วยมือ

### นำเข้าจาก Moodle — มีโค้ดรองรับ

- `scripts/moodle-mbz-to-korkru.mjs` แปลง Moodle backup (`.mbz`) เป็นไฟล์ `.korkru.json` ที่ปุ่ม "นำเข้าไฟล์" รับได้ และอัปโหลดรูปเข้า bucket `question-images` ด้วย `--upload-images`
- แมป multichoice → mcq, truefalse → true_false, match → matching, essay → essay, shortanswer/numerical → written, formulas → written + สุ่มตัวเลข และ multichoice หลายคำตอบ → composite แบบ "ถูก-ผิดแบบชุด"
- โจทย์ `random` ของ Moodle เป็น placeholder ระดับ quiz ไม่ใช่โจทย์ จึงถูกข้าม
- `varsglobal` ของ Moodle ที่เป็นค่าคงที่แปลงเป็นตัวแปรคงที่ ที่คำนวณต่อจากตัวแปรสุ่มแปลงเป็น `Variable.formula`
- หมวดหมู่ของ Moodle ไม่ถูกสร้างโดยการนำเข้า ต้องให้ admin วางรายการที่ `/admin/categories` ก่อน (ดู `bulkCreateCategories`)

### โจทย์สุ่มตัวเลข — มีโค้ดรองรับ

- มี variable ranges, step, constants, logic rules, Pythagorean groups, formulas และ answer parts
- ตัวแปรระบุค่าเป็นชุดได้ (`Variable.values`) สำหรับค่าที่ระยะห่างไม่เท่ากัน เช่น μ = 0.1, 0.2, 0.5
- ตัวแปรคำนวณได้ (`Variable.formula`) เช่น `l` สุ่ม แล้ว `lm = l*0.4` คำนวณหลังสุ่มเสร็จ ก่อนตรวจ logic rules และถูกตรึงลง `random_values` เหมือนตัวแปรสุ่มปกติ วงอ้างอิงวนกลับจะปล่อยตัวแปรนั้นไว้ไม่มีค่า ไม่ลูปค้าง
- สุ่มค่าตอนเริ่ม submission และเก็บ `random_values` ต่อ answer
- ต้องเพิ่ม automated tests สำหรับ evaluator, tolerance, chained references และ edge cases ก่อน production

### โจทย์จับคู่ — มีโค้ดรองรับ

- สร้าง/แก้ไขในคลัง ทำในหน้าสอบ ตรวจอัตโนมัติ แสดงในหน้าตรวจคำตอบ และพิมพ์เป็นใบงานได้ครบ
- คอลัมน์ขวาสลับลำดับต่อ attempt เสมอ (ไม่ขึ้นกับ `shuffle_options` ซึ่งใช้กับ MCQ) และตรึงไว้ใน `option_order`
- คำตอบเก็บเป็นข้อความฝั่งขวาเรียงตามลำดับข้อฝั่งซ้าย (`MATCH:[...]`) ให้คะแนนรายคู่ ป้ายกำกับที่ซ้ำกันจึงใช้แทนกันได้
- จำนวนคู่ที่ใช้คิดคะแนนอ่านจากเฉลยที่ตรึงไว้ การเพิ่มคู่ทีหลังจึงไม่เปลี่ยนคะแนนเต็มของ attempt ที่ทำไปแล้ว

### MCQ และตัวเลือกหลอก — มีโค้ดรองรับ

- มีโหมดตัวเลือกธรรมดาและโหมดคำนวณพร้อม distractor formulas
- มีตัวช่วยสร้างตัวลวงจากการสลับ operator/ปรับสูตร
- analytics คำอธิบายตัวลวงบางส่วนยังสร้างจากข้อความคงที่และ distribution สังเคราะห์
- ตัวเลือกเก็บเป็นข้อความล้วน (ไม่ใช่ rich text)
- คำตอบเก็บเป็น `MCQ:<ลำดับตัวเลือก>` ไม่ใช่ข้อความ ตัวเลือกที่ข้อความซ้ำกันหรือเป็นรูปล้วนจึงแยกออกจากกันได้ คำตอบเก่าที่เก็บเป็นข้อความยังตรวจแบบเดิม ไม่ต้อง migrate
- หน้าสอบแสดง `MCQOption.image_url` แล้ว

### ห้องเรียนรายวิชา — มีโค้ดรองรับ

- มี teacher/student views, class code join, roster, archive, trash, restore และ pin
- เจ้าของห้องเรียนแก้ได้จากกล่องตั้งค่าห้องเรียนครบทุกช่องที่กรอกตอนสร้าง (ชื่อ คำอธิบาย ระดับชั้น ภาคเรียน แท็ก การเข้าร่วม ที่นั่ง วันเปิด/ปิด) และเก็บเข้าคลังจากกล่องเดียวกัน — ประเภทห้องเรียนกับรหัสห้องเรียนแก้ไม่ได้
- ระดับชั้น ภาคเรียน แท็ก การเข้าร่วม ที่นั่ง และวันเปิด/ปิด ยังไม่มีคอลัมน์ในฐานข้อมูล เก็บเป็นข้อความใน `description` โดย `_components/classroom-meta.ts` เป็นเจ้าของรูปแบบ (compose/parse) ให้ทั้ง wizard และกล่องตั้งค่าใช้ร่วมกัน จึงยังกรองหรือ query ตามค่าเหล่านี้ไม่ได้
- สีหน้าปกเป็นสีพื้นเรียบ (ไม่ไล่เฉด) 9 สี ใช้ token ของระบบ จึงเปลี่ยนตาม style preset และโหมดสว่าง/มืดเอง สูตรเดียวกับการ์ดเลือกประเภทโจทย์: พื้น `/10` ขอบ `/20` ตัวอักษรสีเดียวกัน
- ตัวอักษรบนหน้าปกใช้ `color-mix` ผสมสีหน้าปกกับ `--foreground` (หัวข้อ 60% รอง 45%) ไม่ใช่สีเต็ม เพราะวัดแล้วสีเต็มบนพื้น `/10` ได้ contrast 1.9–4.5:1 ซึ่งตกเกณฑ์ WCAG AA เกือบทุกสี ส่วนการหรี่ด้วย opacity ก็ยังตก (เหลืองส้มได้ 4.14:1 ที่ 90%) — สูตรนี้วัดได้ 5.03:1 ขึ้นไปในโหมดสว่าง และ 11:1 ขึ้นไปในโหมดมืด
- ทั้ง wizard และกล่องตั้งค่าใช้ชุดสีเดียวกัน เลือก “สีอัตโนมัติ” เพื่อกลับไปใช้ไล่สีตามลำดับในรายการแบบเดิมได้
- สีหน้าปกมีผลกับห้อง homeroom ด้วย ทั้งแบนเนอร์ในหน้ารวมและแบนเนอร์หัวห้องเรียน (`HomeroomBanner` เคยตรึงพื้นมืดไว้)
- ทุกจุดที่แสดงคำอธิบายห้องเรียนต้องเรียก `displayDescription()` ไม่ใช่ `classroom.description` ดิบ ไม่งั้นบรรทัด metadata (รวมถึง `หน้าปก:`) จะโผล่ให้ผู้ใช้เห็น — ครอบคลุมหน้ารวมฝั่งครู/นักเรียน ถังขยะ คลังห้องเรียน มุมมองนักเรียน และตัวเลือกห้องเรียนในหน้าสร้างงาน (ตัวหลังนี้ตัดให้เหลือแค่ระดับกับภาคเรียน ไม่ใช่ทั้งบรรทัด)
- ห้องเรียนที่บันทึกไล่สีแบบ hex ไว้ก่อนหน้านี้จะอ่านค่าไม่ได้แล้วและกลับไปแสดงเป็น “ยังไม่ได้เลือกสี”
- รูปภาพหน้าปกที่อัปโหลดใน wizard ยังไม่ถูกบันทึก
- มีโพสต์ ความคิดเห็น และการแจ้งเตือน — ประกาศอยู่ **บนสุดของแท็บภาพรวม** ไม่มีแท็บ “ประกาศ” แยกอีกแล้ว กล่องประกาศมีช่องเขียนติดอยู่ด้านบนและรายการเลื่อนอยู่ในกรอบสูงสุด 360px ประกาศทั้งเทอมจึงไม่ดันตัวเลขในหน้าให้หายไป
- หน้านักเรียนใช้กรอบเดียวกัน (`variant="panel"`, หัวข้อ “ประกาศจากครู” / “ประกาศจากครูที่ปรึกษา”) ประกาศจึงไม่ดันงานที่ต้องส่งให้ตกจอ — และเพราะกรอบตัดเนื้อหาที่เลื่อนพ้นออกไป ประกาศที่ยังไม่ถูกเลื่อนมาเห็นก็ยังไม่ถูกนับว่า “เห็นแล้ว”
- ชื่อผู้โพสต์ที่ผู้อ่านไม่มีสิทธิ์ query (นักเรียนที่เข้าห้องด้วยรหัสแต่อยู่คนละ org กับครู — `users_select_org_members` ไม่ครอบคลุม) ถูกเติมฝั่งเซิร์ฟเวอร์ ไม่งั้นทุกประกาศจะลงชื่อว่า “ครูผู้สอน” ทั้งที่หัวการ์ดบนหน้าเดียวกันขึ้นชื่อครูอยู่แล้ว
- ประกาศแนบไฟล์ได้สูงสุด 6 ไฟล์ (รูป PDF Word Excel PowerPoint txt/csv zip · สูงสุด 10 MB ต่อไฟล์ · รูปย่อในเบราว์เซอร์ก่อนอัป ไฟล์อื่นอัปตามจริง) รูปแสดงในประกาศเลย ไฟล์อื่นเป็นปุ่มดาวน์โหลดที่ได้ชื่อไฟล์เดิมกลับไป และ URL ที่พิมพ์/วางในข้อความจะกลายเป็นลิงก์เปิดแท็บใหม่อัตโนมัติ — ตัวข้อความยังเป็น plain text ไม่มี markup ให้เรียน และไม่มี HTML ให้ escape
- โพสต์ประกาศเดียวไปหลายห้องพร้อมกันได้ (เลือกห้องในกล่องเขียน) — เขียนเป็นคนละแถวต่อห้อง แต่ละห้องจึงมีความเห็น การปักหมุด และสถิติการเห็นของตัวเอง แก้/ลบห้องหนึ่งไม่กระทบอีกห้อง · เลือกได้เฉพาะห้อง active ที่ครูเป็นเจ้าของ และ RLS เป็นด่านจริง ไม่ใช่รายการใน UI
- **“เห็นแล้ว X/Y” ต่อประกาศ** พร้อมรายชื่อคนที่ยังไม่เห็น — นับเมื่อประกาศปรากฏบนจอนักเรียนจริง (IntersectionObserver) ไม่ใช่แค่โหลดหน้า และไม่ได้แปลว่าอ่านจบ ข้อความใน UI จึงเป็น “เห็นแล้ว” ไม่ใช่ “อ่านแล้ว”
- ยังไม่ได้ทดสอบด้วยบัญชีนักเรียนจริง: เส้นทางเขียน `post_reads` (RLS `post_reads_own_insert`) ยังไม่เคยรันจากฝั่งนักเรียน ตรวจแล้วเฉพาะฝั่งครูที่อ่านและแสดงผล
- ปักหมุดประกาศได้ในคลิกเดียวจากไอคอนหมุดบนโพสต์ (เดิมซ่อนอยู่ในเมนู ⋮) ประกาศที่ปักหมุดลอยขึ้นบนสุดและมีพื้นหลังอ่อนกำกับ
- ผู้ช่วยสอนสิทธิ์ `view` เห็นแท็บภาพรวมที่มีเฉพาะกระดานประกาศ (อ่านอย่างเดียว) ไม่ใช่หน้าเปล่าที่ดูเหมือนห้องไม่มีงาน
- มี assignment tab และคะแนนระดับห้อง
- แท็บแรกของครูที่จัดการห้องได้คือ **ภาพรวม** (`_components/classroom-overview.tsx`) ทั้งห้องเรียนวิชาและ homeroom เรียงเป็น: กระดานประกาศ → ปุ่มลัด → “ต้องดำเนินการ” → รายการงานที่มอบหมาย → นักเรียนที่ควรติดตาม ทุกอย่างคำนวณจากข้อมูลที่หน้านี้โหลดอยู่แล้ว ไม่มีตัวเลขสมมติ
- **ไม่มีการ์ดตัวเลข 4 ช่องแล้ว** (นักเรียนในห้อง / งานที่มอบหมายแล้ว / อัตราการส่งงาน / ครบกำหนดใน 7 วัน) — เจ้าของผลิตภัณฑ์สั่งเอาออกเพราะทุกช่องชี้กลับไปที่รายการงานอยู่ดี เหลือเป็นบรรทัดเล็กข้างหัวข้อ (`N ชิ้น · ส่งแล้ว X%`) แทน
- รายการงานเป็นกรอบเลื่อนสูงสุด 420px แสดง **ทุกงาน** ไม่ใช่ 5 ชิ้นล่าสุด เรียงตามความเร่งด่วน: เลยกำหนดและยังส่งไม่ครบ → ใกล้ครบกำหนด (วันใกล้สุดก่อน) → ไม่มีกำหนดส่ง (ใหม่สุดก่อน) → ปิดแล้ว · กดแถวไหนก็เข้าไปหน้างานนั้นได้ และงานที่ปิดแล้วมีป้าย “ปิดแล้ว” กำกับว่าทำไมอยู่ล่างสุด
- การ์ด “ใกล้ครบกำหนด” แยกถูกยุบเข้าไปในรายการเดียวกัน เพราะแถวงานบอกวันครบกำหนดอยู่แล้วและงานที่ใกล้ครบกำหนดลอยขึ้นบนสุดเอง
- อัตราการส่งงานนับงานที่ถึงมือนักเรียนแล้ว (`published` + `closed`) และครบกำหนดแล้ว ต่อนักเรียนที่อยู่ในห้องตอนนี้ — ฉบับร่างและงานที่ยังไม่ถึงกำหนดไม่ทำให้ทั้งห้องดูเหมือนค้างส่ง ห้องที่ยังไม่มีงานครบกำหนดแสดง “—” ไม่ใช่ 0% ส่วนงานที่ปิดแล้วยังนับในอัตราและรายการ (เป็นประวัติของห้อง) แต่ไม่ขึ้นใน “ใกล้ครบกำหนด” และไม่ถูกทวงถาม เพราะส่งเพิ่มไม่ได้แล้ว
- งานที่ไม่มีวันครบกำหนดถือว่า “ถึงกำหนดแล้ว” (กติกาเดียวกับหน้าการบ้าน homeroom เดิม) จึงไม่มีวันขึ้นเป็นงานเลยกำหนด — รายการ “ต้องดำเนินการ” จึงมีบรรทัดนับนักเรียนที่ส่งงานไม่ครบด้วย ไม่งั้นห้องที่งานค้างครึ่งห้องจะขึ้นว่าไม่มีอะไรค้าง
- กติกาการนับอยู่ใน `lib/classroom-progress.ts` (มี unit test) ใช้ร่วมกับแท็บงานที่มอบหมาย — ลดเป็น attempt “ตัวจริง” ตาม `score_strategy` ของงานนั้นก่อนเสมอ นักเรียนที่ทำหลายครั้งจึงนับเป็นคนเดียว
- ช่อง “รอครูตรวจ” นับจาก `submission_answers.is_correct IS NULL` ของงานในห้องนี้ (กติกาเดียวกับหน้าผลการส่ง) อ่านสูงสุด 1,000 แถวต่อครั้ง เกินกว่านั้นแสดงเป็น `n+` — เป็นตัวเลขขั้นต่ำ ไม่ใช่ยอดจริง
- เส้นทางหน้าห้องเรียนโหลด profile/classroom และชุดข้อมูลอิสระของครูแบบขนาน เพื่อลด database round-trips ที่รอต่อคิว
- หน้ารวมห้องเรียนอ่านจำนวนนักเรียนและงานจาก relation ใน query ห้องเรียนชุดเดียว โดยนับงานผ่าน `assignment_classrooms`; มุมมองนักเรียนโหลดงาน published กับสถานะที่ส่งแล้วพร้อมกันหลังทราบ roster
- กราฟทักษะตัวอย่างบนการ์ดใช้ CSS ขนาดเล็กและระบุว่าเป็นข้อมูลตัวอย่าง จึงไม่โหลด chart library ขนาดใหญ่หรือทำให้ผู้ใช้เข้าใจว่าเป็นผลวิเคราะห์จริง
- ต้องทดสอบการแยกข้อมูลข้าม organization และ lifecycle ลบถาวร

### ครูผู้สอนร่วม — มีโค้ดรองรับ

- มี invitation และ permission `admin/manage/view`
- Server actions และ migrations มีเส้นทางจัดการสิทธิ์
- ต้องทำ authority matrix และทดสอบทุก mutation ของ classroom/assignment

### งานและข้อสอบ — มีโค้ดรองรับ

- **ระบบสอบปลอดภัยเฟส 1–7 — SEB รองรับ Windows, macOS และ iOS/iPadOS; Android ใช้ monitored mode แยกที่ความมั่นใจต่ำกว่า** — ครูเปิด `secure_browser_mode = seb_required` ได้เฉพาะข้อสอบออนไลน์ ระบบบังคับเปิดห้องคุมสอบสด, นักเรียนได้หน้าแนะนำเปิด `.seb`, และ server ตรวจ CK + BEK ของ exact challenge URL ผ่าน SEB JavaScript API ก่อนออก HttpOnly session ที่ผูกผู้ใช้กับข้อสอบ
  - ตรวจ session ซ้ำที่ `startSubmission`, `getExamTakingData`, autosave/รูปวิธีทำ/ไฟล์แนบ, proctor heartbeat และ `submitSubmission`; การปลอม UI หรือเรียก Server Action ตรงจึงไม่ข้าม gate ส่วน forced-finalize ของ attempt หมดเวลายังทำงานได้
  - submission และห้องคุมสอบเก็บเฉพาะ verified timestamp/platform/version; ครูเห็นป้าย “SEB ยืนยันแล้ว” แบบ realtime โดยค่าฝั่งห้องคุมสอบถูก trigger คัดจาก submission ไม่รับจาก client
  - ห้ามเปลี่ยน browser ↔ SEB หลังมี submission แรก ป้องกันการล็อกนักเรียนกลางข้อสอบ และ SEB kiosk ไม่ซ้อน DOM fullscreen overlay ซึ่งเคยมีโอกาส false-block บน Apple platform
  - เฟส 2 เพิ่ม teacher readiness checklist ที่ไม่เปิดเผย key, กัน create/publish/แก้ข้อสอบ SEB ที่เผยแพร่อยู่เมื่อ production URL หรือ secret/CK/BEK ไม่พร้อม และเพิ่ม assignment-specific system check ที่ตรวจ roster + purpose-bound challenge โดยไม่โหลดโจทย์ ไม่ถาม access code ไม่สร้าง submission และไม่เริ่ม timer
  - เฟส 3 เพิ่ม `android_exam_mode = monitored`: นักเรียน Android รอโดยยังไม่สร้าง attempt/timer ครูตรวจเครื่องจริงและอนุมัติรายคนจากห้องคุมสอบ จึงได้ signed HttpOnly session; ทุก read/write ตรวจ session ซ้ำและ audit แยก `android_monitored` จาก SEB อย่างชัดเจน ระบบไม่เก็บ user-agent/IP/device fingerprint และไม่กล่าวอ้างว่าป้องกัน screenshot ระดับระบบ
  - เฟส 4 เพิ่มคิวสัญญาณ “รอรับทราบ/ครูรับทราบแล้ว” ที่ใช้ร่วมกันข้ามเครื่องครูแบบ first-ack-wins, ตัวนับ exact ทั้ง assignment, filter/รับทราบทีละรายการหรือไม่เกิน 100 รายการที่แสดง และเสียง/Browser Notification แบบ opt-in ต่อการเปิดหน้า; event เก่ายังเป็น backlog จริง ไม่ backfill ว่าครูเคยเห็น และการรับทราบไม่ใช่คำตัดสินว่าปกติหรือทุจริต
  - เฟส 5 เก็บเฉพาะ **ผล system check ที่ผ่านล่าสุด** หนึ่งแถวต่อ assignment + นักเรียน (`verified_at`, `valid_until` ไม่เกิน 12 ชั่วโมง, platform และ version) โดยไม่สร้าง submission/attempt หรือเริ่ม timer ห้องคุมสอบแสดง roster ก่อนสอบเป็น “พร้อม/หมดอายุ/ยังไม่ตรวจ” และ refresh ผ่าน RLS ทุก 10 วินาที/เมื่อกลับเข้าแท็บ; ไม่ publish ตารางนี้ผ่าน Postgres Changes เพราะ RLS ไม่ครอบคลุม payload ของ `DELETE` บันทึกนี้ไม่ใช่ device identity, ไม่ใช่หลักฐานว่าทุจริต และยังไม่ใช้เป็น hard gate ตอนเริ่มสอบ
  - เฟส 5 ไม่เก็บผลตรวจที่ไม่ผ่าน, raw CK/BEK/request hash, IP, user-agent หรือ device fingerprint; browser เขียนตารางตรงไม่ได้ การบันทึกใช้ service-role-only RPC ที่ตรวจซ้ำว่าข้อสอบเผยแพร่และบังคับ SEB พร้อมตรวจ roster ของ student + assignment ส่วน RLS เปิดอ่านเฉพาะครูที่จัดการข้อสอบและ super admin ข้อมูลถูกลบตามเพดาน 90 วันและร่วมอยู่ในปุ่มล้างข้อมูลคุมสอบรายข้อสอบ
  - เฟส 6 เพิ่มหน้า **รายงานสัญญาณคุมสอบ** แบบอ่านอย่างเดียวจากข้อมูลเดิม แบ่งหน้าฝั่ง server และกรองด้วยนักเรียน, attempt, ชนิดสัญญาณ และสถานะการรับทราบที่ผ่าน allowlist ฝั่ง server; assignment ต้องผ่านสิทธิ์ผู้จัดการก่อน query และ RLS ยังจำกัด session/event ซ้ำอีกชั้น จากนั้น admin resolve ชื่อเฉพาะ student IDs ของ retained attempts ที่ได้รับอนุญาตและมี hard cap 2,000 attempts ไม่ค้น roster ทั้ง organization และไม่ส่งประวัติ event ทั้งชุดเข้า Client Component
  - รายงานใช้ `created_at` จาก server เป็นเวลาหลัก ส่วน `occurred_at_client` เป็นข้อมูลจากนาฬิกา client ที่แก้ได้และไม่ใช้ตัดสินลำดับ/ข้อสรุป ถ้อยคำใช้ “สัญญาณ”, “รอรับทราบ” และ “รับทราบแล้ว” โดยไม่สร้าง risk score หรือคำตัดสินว่าปกติ/ทุจริต; การรับทราบยังหมายถึงครูเห็นข้อมูลแล้วเท่านั้น
  - ดาวน์โหลด CSV จะ re-query ตามตัวกรองหลังตรวจสิทธิ์ซ้ำ ไม่เชื่อแถวจาก browser และตรึงขอบเขต event ใหม่ด้วย ID สูงสุดจาก query แรก; ทุก event-derived attempt ต้องยืนยันซ้ำกับ retained session ผ่าน RLS ก่อน resolve ชื่อ/metadata ด้วย admin หากข้อมูลเปลี่ยนจนจำนวนหรือความสัมพันธ์ไม่ตรง ระบบปฏิเสธให้ลองใหม่แทนการส่งไฟล์บางส่วน กลไกนี้ไม่ใช่ transactional snapshot ของ acknowledgement ทุกช่อง จำกัดไม่เกิน 10,000 แถว, 2,000 attempts และไฟล์ UTF-8 ไม่เกิน 4 MiB หากเกินข้อใดจะปฏิเสธทั้งไฟล์ พร้อมป้องกัน spreadsheet formula injection และตอบแบบ `private, no-store` ไฟล์ที่ดาวน์โหลดมีข้อมูลส่วนบุคคล เป็นสำเนาที่แก้ไขได้ ไม่ใช่หลักฐานแบบ tamper-proof และจะไม่ถูกลบตาม retention 90 วันหรือปุ่มล้างข้อมูลใน KorKru ผู้ดาวน์โหลดต้องจำกัดผู้เข้าถึงและลบเมื่อหมดวัตถุประสงค์
  - เฟส 6 ใช้ตาราง, RLS และดัชนีเดิม จึงไม่มี migration ใหม่ แต่ยังพึ่ง migrations สี่ไฟล์ของเฟสก่อนหน้าให้ถูก apply ครบ
  - เฟส 7 apply migrations หกไฟล์ของระบบนี้กับฐาน production ที่เชื่อมอยู่แล้ว รวม hardening constraints ของ Android approval audit และถอนสิทธิ์ `MAINTAIN` ของ PostgreSQL 17 จาก role เว็บบนตาราง proctor/SEB; migration ledger ตรงกัน, database lint ไม่พบ error และ catalog check ยืนยัน RLS/constraints/triggers/ACL กับข้อมูล audit เดิมครบ เพิ่ม `npm run check:seb-readiness` เพื่อตรวจ environment/permission แบบ read-only โดยไม่แสดง secret และไม่เรียก network/ฐานข้อมูล
  - **ฝั่งฐานข้อมูล production พร้อมแล้ว แต่ยังไม่พร้อมเปิดข้อสอบ SEB จริงจนกว่าจะ** กำหนด canonical production URL กับ 4 env ของ SEB ในระบบ deploy, สร้าง/เข้ารหัส `.seb`, เก็บ BEK ของทุก platform/build ที่อนุญาต และทำ staging/device/Wi-Fi mock exam ทั้ง SEB/Android ตาม `docs/SEB_SETUP.md` กับ `docs/ANDROID_EXAM_MODE.md`

- หน้าทำข้อสอบ resume จาก answer snapshot ที่บันทึกในฐานข้อมูล, รวม autosave ขณะพิมพ์ภายในช่วงสั้น, สำรองค่าล่าสุดใน `localStorage` เมื่อ offline/ก่อน debounce และเขียนผลตรวจเป็นชุดย่อยพร้อมกัน โดยยัง flush คำตอบล่าสุดก่อนส่ง; reload หรือหลุดแล้วกลับเข้ามาจึงได้คำตอบ server เดิม และค่าที่ยัง sync ไม่ทันจะกู้จากเครื่องเดิม
  - Autosave retry request ที่ไม่มี response ได้สูงสุด 3 ครั้งเฉพาะ mutation แบบ idempotent ซึ่งตั้ง answer เป็นค่าเดิม การตอบปฏิเสธจาก server เช่นหมดเวลาไม่ถูก retry และข้อความจริงถูกส่งขึ้น UI ส่วน `checkAnswer` ไม่ retry เพราะเพิ่ม `check_count` และ request อาจ commit แล้วหายเฉพาะ response; helper กับขอบเขตนี้มี unit test 5 กรณี
- หลังส่งคำตอบจะโหลดหน้าสรุปจากสถานะล่าสุดของ server และอยู่ที่หน้าสรุปจนกว่านักเรียนจะเลือกกลับหรือเริ่มทำใหม่เอง
- หน้าสรุปผลโหลดเฉพาะข้อมูลคะแนนขั้นต่ำก่อน และโหลดรายละเอียดคำตอบแบบ streaming เฉพาะเมื่อสิทธิ์การแสดงผลอนุญาต โดยไม่ส่ง JavaScript ฝั่ง client สำหรับแผนซ่อมเสริมที่ไม่มี interaction
- มี regression test ของ student-safe DTO ครอบคลุม answer key แบบตรง/ซ้อนและ result-visibility helper แล้ว; ยังต้องเพิ่ม integration test ของ RLS/Server Action, ทุก question type และการ rescale/attempt strategy
- ต้องยืนยันคำจำกัดความของ `submitted` เทียบกับ `graded` สำหรับคำตอบ manual

### โฮมรูม — มีโค้ดรองรับ แต่ข้อมูลอ่อนไหวต้องตรวจเพิ่ม

- มี classroom type `homeroom`
- รวม assignment/submission จาก subject classrooms ของนักเรียนใน roster
- มี calendar, compliance, student view, weekly digest, student notes และ student profile fields
- ตัวรวมข้อมูลโฮมรูม join สมาชิกกับห้องวิชาและงานกับห้องที่มอบหมายโดยตรง ลด query ที่ต้องรอต่อกัน และหน้าครูโหลดการบ้านรวม บันทึกส่วนตัว และโปรไฟล์นักเรียนพร้อมกัน
- หน้าแรกโหลดเฉพาะ JavaScript ของแท็บที่เห็น ส่วนแท็บจัดการรองโหลดเมื่อเปิดใช้งาน และรายงานผู้ปกครองใช้ client island เฉพาะปุ่มพิมพ์
- ต้องทดสอบว่า health/family/guardian/address/notes ไม่รั่วถึงครูหรือสมาชิกที่ไม่เกี่ยวข้อง

## Supporting features

### Dashboard — มีโค้ดรองรับ (ฝั่งครู)

- หน้าหลักของครูแสดงเฉพาะข้อมูลจริงของเจ้าของบัญชี: จำนวนห้องเรียน นักเรียนรวม โจทย์ในคลัง แฟ้มโจทย์ พร้อมรายการล่าสุดของทั้งสามอย่างและปุ่มสร้าง — บัญชีที่ยังไม่มีข้อมูลจะเห็นการ์ดเริ่มต้นใช้งานแทนตัวเลข 0
- จำนวนโจทย์ในชุดนับเฉพาะ id ที่ยังหาโจทย์เจอ (question_ids ค้างได้เมื่อโจทย์ถูกลบ) ให้ตรงกับที่หน้าคลังแฟ้มโจทย์แสดง
- ยอดรวมและรายการล่าสุดของโจทย์/แฟ้มโจทย์มาจาก query เดียวกันด้วย `count: 'exact'` คู่กับ `limit` ส่วนห้องเรียนนับนักเรียนและชุดข้อสอบผ่าน relation เหมือนหน้ารวมห้องเรียน
- ยังไม่แสดงงานที่มอบหมาย การส่งงาน หรือผลวิเคราะห์บนหน้าหลัก — ดูได้จากหน้าห้องเรียนและหน้างานโดยตรง
- Dashboard นักเรียนดึงการตั้งค่าคะแนนพร้อม submission และดึงงานผ่าน `assignment_classrooms` โดยตรง พร้อมโหลดประกาศคู่ขนาน เพื่อลด query ที่รอต่อกัน
- มี migration เติม index สำหรับ question/classroom/assignment/submission read paths และลดการประเมิน `auth.uid()` ซ้ำใน RLS โดยคงขอบเขตสิทธิ์เดิม
- App shell โหลดจำนวนแจ้งเตือนพร้อมโปรไฟล์จาก server เพื่อตัด request หลังเปิดหน้า, polling เฉพาะเมื่อแท็บมองเห็น และไม่ขอนับซ้ำหลังอ่านทีละรายการ
- Protected layout และหน้าหลักใช้ผลตรวจ Supabase Auth ร่วมกันเฉพาะใน server render request เดียว และ app shell ส่งเฉพาะชื่อ อีเมล และบทบาทที่ UI ใช้
- การ์ดข้อมูลจำลองบนหน้าหลักฝั่งครู (สถิติปลอม นักเรียนกลุ่มเสี่ยง heatmap เรดาร์สมรรถนะ งานค้าง แม่แบบ โควตา เคล็ดลับ command palette) ถูกลบออกแล้ว หน้าหลักไม่มีข้อมูลจำลองเหลืออยู่

- **“เงื่อนไขจบงาน” แบบถูกติดต่อกัน N ข้อ — อนุมัติแบบแล้ว ยังไม่เริ่มเขียน** เจ้าของผลิตภัณฑ์เคาะสามข้อนี้เมื่อ 31 สิงหาคม 2026:
  1. ใช้ได้ทั้ง `exercise` และ `exam` (ข้อสอบไว้ทำ Quiz เก็บคะแนนเล็ก ๆ) เฉพาะโหมดออนไลน์
  2. บันทึกลงสมุดคะแนนเป็น ผ่าน = เต็มตาม `display_max_score` / ยังไม่ผ่าน = 0 — ผ่านเร็วผ่านช้าได้เท่ากัน และ `score_strategy` ถูกล็อกเป็น `best` เพราะค่าเฉลี่ยของ 0 กับ 10 ไม่มีความหมาย
  3. ตอบผิดแล้วเริ่มนับใหม่จาก 0 ไม่มีตัวเลือกถอยหลัง 1 ในเวอร์ชันแรก
  - ต้องแยก **ผลรายข้อระหว่างทาง** (คอลัมน์ใหม่ `streak_feedback` = `verdict` | `verdict_and_solution`) ออกจาก `show_results` ซึ่งคุมแค่สรุปตอนจบ ไม่งั้นข้อสอบจะรั่วเฉลยให้คนที่ทำเสร็จก่อน · ข้อสอบเริ่มต้นที่ `verdict` แบบฝึกหัดเริ่มต้นที่ `verdict_and_solution`
  - คอลัมน์ที่ต้องเพิ่ม: `assignments.completion_rule` (`fixed` | `streak`), `streak_target`, `streak_question_cap`, `streak_recycle_pool`, `streak_feedback` และ `submissions.current_streak` / `best_streak` / `streak_reached` — ตั้งใจไม่แตะ `passing_type`/`passing_value` เพราะ `computePassed()` หน้าผลลัพธ์ หน้าวิเคราะห์ สมุดคะแนนห้อง และไฟล์ส่งออกพึ่งพาอยู่
  - “ถูก” หมายถึงได้คะแนนเต็มของข้อนั้น ถูกบางส่วนไม่นับ · ข้อที่ระบบตรวจเองไม่ได้ (`essay`, `file_upload`) ต้องถูกกันออกตั้งแต่ตอนสั่งงาน ไม่ใช่ตอนดึงข้อ · การตัดสินถูก/ผิดและการนับต้องอยู่ฝั่ง server ทั้งหมด
  - แบบร่างหน้าจอและกรณีขอบอยู่ในเอกสารออกแบบของเจ้าของผลิตภัณฑ์ ยังไม่มีโค้ด ไม่มี migration และไม่มีอะไรใน UI ที่อ้างถึงโหมดนี้
